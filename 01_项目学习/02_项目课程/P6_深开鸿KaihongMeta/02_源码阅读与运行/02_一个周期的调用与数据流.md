# 一个周期的调用与数据流：逐步精读


> **先读白话总览：**先读[一次设备动作怎样走过软件平台](../00_项目全貌与学习路线/03_P6一次设备动作怎样走过软件平台.md)。这里的周期是一项软件动作从校验、排队、协议转换，到返回设备状态的过程，不是一个固定毫秒的机械控制周期。读每一步时分清等待的是函数结果、通信确认还是物理完成。

## 0. 系统对象是什么

该副本支持设备handler、协议adapter、属性上报、线程池和轮询。它是设备软件框架，不是机械臂雅可比控制器。材料中的M-DDS/M-Robots机器人发现/任务同步源码未定位，需保留缺口。[文件地图](01_源码版本与文件地图.md)给当前可读范围。

## 1. 分层接口的原因

调用方发送deviceId/cmd/input，BaseDeviceHandler找命令handler，具体设备handler解释能力，adapter编码Modbus等协议，设备回复再转成属性/错误码。上层不需要每次拼寄存器，但设备能力差异不能被通用字符串掩盖。

## 2. 初始化的真实顺序

BaseDeviceHandler::Init 先创建插件专属线程池。源码默认是 2 个短任务线程、2 个长任务线程和 10000 ms 默认轮询间隔，子类可用 GetPluginConfig 改配置；然后初始化上报处理器、调用子类 OnInit。OnInit 成功后，基类把 deviceId 加入列表、调用 SetDeviceOnline、为设备建 schedule，并在存在 pollTask 时启动 scheduler。

这里有一个容易误读的事实：这段 Init 顺序里，SetDeviceOnline 发生在“初始化回调成功”之后；它本身不是从设备新读一帧的证据。要描述实时在线或健康，必须继续查心跳、轮询返回码和状态数据的时间戳。

## 3. 设备专属命令优先

ExecCommand先拒绝空deviceId/cmd，再持deviceCmdMutex查设备专属map；没有才查通用map；仍没有返回不支持。通用map注释假设仅初始化写、运行只读，若扩成动态注册需要同步，不能无条件说所有map都线程安全。

## 4. 一个请求的具体字段

真实接口收到 deviceId、cmd、input 字符串和 output 引用。地锁场景可用 deviceId=lock7、cmd=up 作心智例子：input/output 是接口载荷，不代表 BaseDeviceHandler 已经解析出参数或替你完成授权、模式、限位检查。Base 层检查 deviceId/cmd 是否为空并找到 handler；真正的参数含义由具体 handler 决定。

因此要分别回答：请求字符串有没有通过 Base 层入口、设备 handler 有没有接受它、适配器有没有成功写协议、设备有没有报告状态变化。只看到 handler 存在，不能推出动作合法或已完成。

## 5. 异步内部、同步返回

创建promise，拿future；提交HIGH任务，队列线程调用handler，设置promise；外部resultFuture.get等待结果再return。内部使用线程池，不意味着API对调用者非阻塞；get无deadline，handler阻塞可能使调用无限等待。

## 6. 捕获引用为什么当前重要

lambda捕获deviceId、cmd、input、output、promise引用，handler按值。正常get等任务完成，局部promise还活着；若直接把get改成wait_for超时后return，后台仍可能引用已经销毁的对象，造成悬空访问。

改造应把输入/结果状态变成有明确共享所有权的对象，并定义取消/迟到结果/设备对象寿命。仅添加timeout字段不能解决寿命问题。原始源码不改，本教材C++例用独立所有权演示。

## 7. 优先级的边界

HIGH优先队列可改变等待任务选择，不能抢占一个已经在串口里阻塞的handler，也不能保证deadline。短/长任务隔离能减少相互拖累，仍需队列长度、资源锁和协议超时预算。

源码还不只是“两个队列按优先级排序”：短任务 worker 开始处理第一项短任务时会清掉等待中的长任务；长任务 worker 在开始前也会检查短任务运行计数。因此排队中的轮询可能被取消/跳过，但已经开始的轮询不会因为一个 HIGH 命令而被强行中断。scheduler 已推进 nextRunTime 的话，被跳过的一次采样也不保证马上补做。

## 8. SmartFarm连接锁

查设备→连接对象→按连接同步协议请求。全局锁适合短时间维护映射，连接锁适合同一协议通道串行收发；在全局锁内做慢I/O会让不相关设备都等待。每设备一锁也未必够，因为多个设备可能共享一条物理连接。

## 9. Modbus读取例

GroundLockHandler::ReadAllRegisters 构造功能码 0x03、起始地址 0x0000、数量 0x0011（17 个寄存器）的读取请求。17 个 16-bit 寄存器代表 **34 个寄存器数据字节**，不包括地址、功能码、字节数、CRC 等协议字段。

这份 handler 检查返回 vector 是否恰有 17 个值。随后 ReadLockStatus 把状态读成 allData[7]，源码注释称它对应寄存器地址 0x0006。请把“协议寄存器地址”和“C++ vector 下标”分开：从地址 0 开始的普通零基数组通常会让地址 6 对应下标 6；这里代码实际取下标 7，是否正确取决于 Modbus service 返回 vector 的布局。现有 handler 片段不足以单独证明该映射正确，需把 service 的返回约定与设备寄存器表核对，不能把注释当成验证。

读请求失败时，ReadLockStatus 会尝试把 currentStatus 缓存写进输出参数 status，但函数仍返回读取错误码。调用方必须先检查返回码；不能因为 status 变量有数值，就当它是本次新读到的状态。**当前ListeningTask自身还有传播问题：读取错误分支里的立即return被注释，之后继续用status更新缓存并上报。若ReportPropertyImpl成功，最终poll返回可能是OK，从而掩盖原读取错误。**

RTU 和 TCP 的帧字段不同：Modbus TCP 有 transaction ID；RTU 一般用从站地址、功能码、长度和 CRC 等字段校验，不能把 TCP transaction ID 当作 RTU 必须字段。要确认具体校验由 handler、adapter 还是底层 Modbus service 执行。

## 10. 写入与物理动作

GroundLockHandler 使用功能码 0x06 向地址 0x0006 写一个寄存器。Modbus 写操作返回成功，只能说明当前软件/协议路径报告此次写操作成功；不能自动证明地锁已经抬到目标位置。

还要注意源码里的状态处理：WriteLockCommand 在写成功后，将 currentStatus 更新为 controlValue，再调用事件/属性上报。这是一次“命令后立即更新缓存”的路径；除非后续读寄存器或独立限位传感器确认，否则上报值可能代表软件刚发出的目标/推定状态，而非机械到位的测量状态。读到的函数返回 EM_ERR_OK 也必须按该函数的实现阶段解释。

### 10.1 用一次“升起地锁”串起接口、协议和状态

1. 上层以 deviceId 和命令名调用 BaseDeviceHandler::ExecCommand。
2. Base 层查找设备专属 handler；GroundLock 的 Up 再找设备端口信息。
3. Up 调 WriteLockCommand，使用控制值写单寄存器；ModbusAdapter 把命令字段转换成 DataOption，调用 RTU 服务。
4. 写函数返回成功后，GroundLock 更新内存 currentStatus 并上报。这个时点不能单独证明机械行程完成。
5. 后续轮询再次读寄存器或传感器。如果读回值与目标一致，才有更强的“设备状态已到位”证据；如果读失败，缓存状态即使仍有数，也必须连同错误码和数据年龄一起看。

建议日志把 action/device ID、handler 返回码、RTU 写返回码、写入寄存器和值、状态缓存来源、最后一次成功读回时间、读回值分别记录。这样才能区分“命令没到 handler”“协议写失败”“写成功但设备未到位”和“状态读回失败”。

## 11. 一个请求时间线

t0请求；t1入队；t2开始handler；t3协议回复；t4promise完成；t5返回。排队延迟t2−t1、协议延迟t3−t2、接口总延迟t5−t0不同。设备机械到位t6可能更晚。日志只记t5无法说明控制/物理动作延迟。

## 12. 轮询调度与上报

ExecutePollTask 扫描每台设备的 nextRunTime。到期后，若没有短任务正在运行，scheduler 会把轮询回调提交为 LOW 长任务；随后将下一次运行时间设为当前扫描时刻加 interval。若当时有短任务，源码仍推进 nextRunTime，所以这次轮询可能跳过，不会把每个错过周期都排队补发。

另一个静态细节：短任务在运行池开始后会调用 ClearPendingLongTasks，清除仍排队的长任务并设置取消标记；长任务 worker 如果已经取到工作但检测到短任务正在运行，也会跳过这项任务。应把“排队、已取出未开始、已经在执行”分开记录，不能用“高优先级抢占轮询”一句话概括。ClearPendingLongTasks 弹出的任务不再走 worker 的常规清理，其 `taskCancelFlags_` 条目在该函数内也没有 erase；反复发生可能累积已取消任务标记，直到线程池对象销毁。用 map 大小和清理计数验证是否实际增长。

SetPollingInterval 的参数名是 intervalSec，内部乘 1000 后存毫秒。全局接口更新 defaultPollingInterval；已创建的各设备 schedule 是否同步变化，应查表更新代码。设备级接口直接更新该设备 intervalMs，但保留当下 nextRunTime，因此新的间隔不会把当前已排定时刻强行改为“马上执行”。notify_one 只是发出通知。当前wait_until的predicate仅检查停止标志；若只是改周期而停止标志仍为false，带predicate的等待可能继续到原期限，不能据此断言立即重新扫描。

轮询实际到达设备的时间还包括 scheduler 延迟、长任务队列等待、worker 空闲时间、锁竞争、协议通信和设备响应。配置 10 秒周期不等于每次测得正好 10.000 秒；要声称周期表现，需要记录计划时间、实际开始/完成时间和跳过原因。

## 13. 属性、新鲜度与在线状态

ReportProperty可能先置online再上报属性；该动作不能替代有效读数来源。缓存应标采样/接收时间和valid，否则旧温度仍显示平滑却已断线。教学registry的能力/TTL语义不等于原平台已完整实现同样发现协议。

## 14. Release 与关闭顺序

Release 清除 online 缓存，从设备列表和 schedule 表移除 ID，调用子类 OnRelease，注销上报；最后一台设备释放后停止 scheduler，再 Shutdown 并销毁线程池。

源码存在需要认真验证的并发边界：ExecCommand 可在一边访问 threadPool_、一边提交任务；Release 可能在另一边销毁它。接口级调用是否被外层生命周期锁串行化，要沿上层调用者继续追，不能只看这两个函数就宣布线程安全。

ThreadPoolManager 的 Shutdown 设 isShutdown 并唤醒、join worker；worker 外层循环受关闭标记控制。当前实现没有直接展示“把所有短任务排空并给每个等待者明确失败结果”的统一策略。若未完成队列里有 ExecCommand 对应任务，调用方可能继续等 promise。该风险来自静态控制流，需要结合调用并发和运行日志验证，不能当作已经复现的故障。

另一个生命周期检查点：Init 对同一个 ThreadPoolManager 实例只在 isInitialized 为 false 时创建线程，但已读 Init 没有把 isShutdown 重新置 false。若该对象 Shutdown 后再次 Init，worker 的退出条件可能仍然成立。是否存在这种重用路径，应查谁持有该实例以及每次 Init/Release 是否重建对象。

## 16. 故障诊断

- 命令卡住：记录请求提交、worker 开始、handler 进入/退出、协议开始/结束、promise 完成和调用方返回的单调时钟时间。再看任务是否仍在队列、worker 是否阻塞、是否持锁等 I/O。
- 设备状态不对：记录设备 ID、寄存器起始地址、数量、返回值长度、vector 下标、设备寄存器表语义、单位/缩放、错误码和最后成功采样时刻。
- 重连后状态倒退：记录设备 session/boot ID、状态序号和采样时刻；新连接不能直接让旧缓存变成新状态。
- 写命令后界面显示目标值但设备没到位：把“写返回”“软件缓存变化”“设备读回”和“位置传感器到位”分成独立字段。
- 多设备一起变慢：看全局 map 锁、共享物理连接锁、线程池占用和队列等待；不是每设备单独创建锁就一定隔离，因为多个设备可能共用一个通道。

## 17. 英文说明

“The framework separates device commands from protocol adapters. A command is resolved to a handler and submitted to the plugin thread pool, but the public call waits synchronously on a future. I distinguish queue priority from a timing guarantee and a protocol acknowledgement from physical completion. Adding a timeout also requires safe ownership of queued inputs and results.”

## 18. 与CS和机器人面试的联系

CS重点：抽象接口、并发、所有权、协议边界与生命周期；机器人重点：反馈新鲜度、异步执行、设备能力与闭环动作。不要把设备上报当状态估计，也不要把线程池当控制算法。M-DDS缺口用材料/代码差异表诚实表达。

## 19. 自测

1. future.get异步吗？对调用者阻塞。
2. HIGH能抢占正在I/O的任务？不能仅由队列优先级推出。
3. 超时返回能只改一行？引用捕获有寿命风险。
4. 17个寄存器的数据区有多少字节？34字节，不含帧字段。
5. 03与06？读保持寄存器与写单寄存器。
6. RTU 是否有 TCP transaction ID？不是同一种帧格式。
7. GroundLock 代码取哪个 vector 下标？源码为 allData[7]；需要核对它与地址0x0006的布局。
8. 写后缓存变成目标值，能证明机械到位吗？不能，需读回/传感器证据。
9. Shutdown join worker 代表排队 promise 一定完成吗？不能这样推出。
10. ACK是否抬升完成？否。
11. online初始化证明通信？否。
12. 每设备锁够吗？共享连接要同步。
13. 忙时轮询一定补发？当前安排可能跳过。
14. M-DDS名字能证明协议实现？不能。
15. 短任务到来会中断正在运行的长任务吗？不能这样推出；但待运行轮询可能被清除或跳过。

## 20. 调用返回码必须逐层保留：一次读取失败的反例

ReadLockStatus返回ERROR并把旧缓存放进status；ListeningTask打印错误但当前return被注释；它继续更新缓存并调用ReportPropertyImpl。若上报成功，最终返回OK。基类按这个最终返回设置online，因此“轮询返回OK”不证明“本次硬件读取成功”。需要分别记录read_ret、report_ret、poll_ret和最后成功读回时间。此结论来自活动分支静态核查，不是断线实测。

## 21. 停止标志改变后，等待者怎样醒来

当前StopScheduler置isSchedulerRunning为false后直接join，没有在此函数显式notify调度条件变量。调度线程若已在wait_until中等待，可能到旧期限才检查停止条件，导致关闭延迟。设置状态、通知等待者、join等待退出是三个动作；仅写原子标志不会主动唤醒条件变量。其他调用者是否另行通知仍需沿调用链核实，不把这个静态风险说成已经复现的永久死锁。
