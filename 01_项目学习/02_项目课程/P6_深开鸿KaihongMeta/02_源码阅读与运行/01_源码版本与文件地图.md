# P6 源码版本与文件地图

## 1. 先说清这张地图代表什么

这张地图只对应申请材料中保存的 KaiHong-learning 本地快照，不把它等同于 KaihongMeta 产品的全部代码，也不把它自动认定为当时部署到设备上的提交。当前快照可用于精读 C++ 设备处理器、线程池、Modbus 适配器和园艺/地锁组件。

材料里出现的 M-Robots、M-DDS 等专用部分，在这份快照中没有定位到可核对的完整实现。对应结论要继续找历史提交、原始仓库路径、IDL/配置、设备日志和个人改动记录；不能拿目录名相似的组件代替。

阅读快照记录为 **2026-10-02 本地原始源码副本**。表格中的 SHA-256 已对当前本地文件重新计算；若源码文件改动，校验值会变化。构建目录、vendor 文件和不同历史版本不拼成一个“看起来完整”的可运行工程。

## 2. 推荐阅读顺序：先读谁调用谁

~~~text
BaseDeviceHandler::Init
  ├─ 创建插件线程池
  ├─ 初始化上报
  ├─ 调子类 OnInit 注册命令、资源和轮询任务
  ├─ 加入设备表、标 online、加入轮询调度表
  └─ 需要轮询时启动 scheduler

上层调用 BaseDeviceHandler::ExecCommand
  ├─ 检查 deviceId/cmd
  ├─ 先找设备专用 handler，再找通用 handler
  ├─ HIGH 短任务入队
  ├─ worker 调 handler，promise 写入结果
  └─ 调用方 future.get() 等待并返回

scheduler 扫描到期任务
  └─ 将 LOW 轮询任务交给长任务 worker
       └─ 设备 handler → 协议 adapter → 通信服务 → 硬件
            └─ 解析反馈 → 上报属性/改变 online 状态
~~~

读这条链时同时标记三个边界：谁调用、在哪个线程执行、返回结果只证明到哪个阶段。不要把“初始化成功”“函数返回成功”“协议写入成功”和“物理设备已经到位”混成一个“成功”。

## 5. 源码快照中应主动核对的细节

这些是静态阅读发现的检查点，不是已经复现的运行故障：

1. Init 在子类 OnInit 成功后调用 SetDeviceOnline，并把设备加入轮询表。仅凭这段流程不能证明设备已经收到了新反馈。
2. ReportProperty 在缓存显示 offline 时会先调用 SetDeviceOnline 再上报。因此“在线”标志的语义要看上报触发路径，不能一律当作最近一次硬件心跳。
3. ExecCommand 的任务捕获了局部参数的引用，外部随后执行 future.get()。若给等待加超时并提前返回，任务仍可能读写已失效的局部对象；超时改造需同时重做所有权和取消策略。
4. ThreadPoolManager::Shutdown 设关闭标记并 join。两个 worker 函数的外层循环条件都是“尚未关闭”；所以正在执行的工作结束后，worker 不再取下一项。静态代码没有显示关闭时对短任务队列做逐项拒绝/完成通知。若队列中任务持有 promise，调用方可能一直等不到结果。把 join 解释成“排队任务全部做完”是不准确的。
5. ThreadPoolManager::Init 检查 isInitialized 后创建 worker，但已读实现没有在初始化处把 isShutdown 清回 false。同一个对象 Shutdown 后再 Init，worker 可能因为关闭标记仍为 true 而不工作；是否重用该对象必须核对完整生命周期。
6. GroundLockHandler 的读请求从地址 0 读 17 个寄存器，代码把状态赋成 allData[7]，注释对应寄存器地址 0x0006。应对照 Modbus service 返回数组的布局和设备寄存器表核实“协议地址”与“C++ 下标”关系。
7. WriteLockCommand 在 Modbus 写成功后会更新缓存状态并上报属性；这属于命令后的软件状态更新，是否代表机械地锁真实到位，要看后续传感器读回和设备协议语义。
8. 轮询周期接口的参数名为 intervalSec，内部乘 1000 后按毫秒存储。全局 setter 更新 defaultPollingInterval，但当前代码未在该函数中逐一改写已有 schedule；设备级 setter 改 intervalMs，却保留当下 nextRunTime，新的间隔从后续周期体现。不能仅依据函数名说“马上按新周期执行”。
9. 短任务开始时，ShortTaskWorker 会调用 ClearPendingLongTasks 清除等待中的长任务；LongTaskWorker 取到任务后还会检查 runningShortTaskCount。已运行的长任务不会因此被抢占，但排队或尚未开始的轮询可能被丢弃。更细看，ClearPendingLongTasks 会给任务设置取消标志并从队列弹出；这些任务随后不会进入 worker 的常规清理分支，而该函数本身也没有删除 taskCancelFlags_ 对应项。当前快照中标记的其他删除点位于 worker 路径，因此重复清理可能让 map 留下已弹出任务的标记，直到线程池对象销毁。应记录 map 大小和被清理任务数确认增长，不把静态推断说成已测得的泄漏。

10. GroundLock::ListeningTask在ReadLockStatus失败时记录日志，但该分支的return被注释，后续上报成功可使poll最终返回OK。应同时追读取错误、缓存来源和上报返回码，不能仅据最终online判断成功读取。
11. StopScheduler设置运行标志false后直接join；该函数未通知schedulerCv。调度线程在等待时可能直到原期限才醒来；周期更新通知的predicate也只检查停止标志，不能保证立即重排。

## 6. 哪些结论不应从这张地图推出

- 文件在目录中，不等于它已进实际构建目标或在运行时加载。
- ONLINE、EM_ERR_OK、函数返回 success，不自动等于设备动作物理完成。
- 本地可见的 SoftBus、Modbus、Snap7 代码，不自动证明 M-DDS 或申请材料描述的机器人平台专用链路。
- 线程池有 HIGH/LOW 标签，不自动得到硬实时周期、延迟上限或队列有界性。
- 读懂团队源代码，不自动等于本人独立完成该模块。
