# 项目与实习技术深挖：从“做过什么”到“为什么这样做”

> 依据：正式英文 CV/PS 与既有 P1–P7 项目学习材料。只包含已有材料支持的技术职责；面试前将每条经历与本人实际代码版本、日志、实验记录对齐。没有数据的地方明确说没有数据。

## 1. 面试官追项目的通用顺序

一段项目回答最好按这 7 个问题展开：

1. **Task**：机器人要完成什么？环境/硬件是什么？
2. **My part**：你本人负责哪一块？队友/平台负责哪一块？
3. **Input**：算法实际读哪些传感器/命令？单位与坐标系是什么？
4. **Method**：算法或模型做了什么变换？为什么选它？
5. **Output**：输出的是位置/速度/力矩/电机协议值，还是高层任务？
6. **Execution**：谁把它传到控制器、驱动或硬件？反馈从哪回来？
7. **Evidence and limits**：如何验证？有什么限制？哪些数字有记录？

一条可复用的英文结构：

> The system needed to **[task]**. My responsibility was **[module]**. It used **[inputs]** to compute **[output]** through **[method]**. The output was then passed to **[next component]**, and feedback came from **[sensor or service]**. We checked **[verified test]**. One limitation was **[real limitation]**.

## 2. 90 秒主项目回答：按学校方向选一段

### 机器人/控制方向：P1 球形机器人

> At AIRS, I worked on balance control for a three-omni-wheel ballbot carrying a dual-arm upper body. The main challenge was keeping the chassis balanced while arm movement changed the centre of mass. The control chain used IMU and wheel feedback. A position outer loop generated bounded attitude references, and an attitude inner loop produced control outputs that were allocated to the three wheels through the robot’s kinematics. I also built a simplified four-state inverted-pendulum model and used LQR to analyse the balance between state error and control effort. For the arm effect, I estimated centre-of-mass offset from joint states using the robot model and added a gravity-feedforward term. My work also covered state initialization, output limits, CAN execution and fall-recovery handling. The reported test case was fixed arm trajectories; I would not claim a general dynamic-manipulation result or a numerical improvement without matched logs.

**你要能说清的关键点**：姿态 PID 输出是控制器中的中间量；它是否物理单位为 N·m 要看实际标定。ROS 输出与电机速度命令也不是同一物理量。CoM 前馈是可预测重力影响的补偿，不取代 IMU 反馈。

### 操作方向：P2 双臂遥操作与主从教学

> At Future Power, I worked on dual-arm and chassis control, and the work was validated through a ROS 2-to-CAN execution chain. In VR teleoperation, the operator’s controller motion was mapped to a robot end-effector target. The current robot configuration and target pose were then used by a constrained inverse-kinematics solver through MuJoCo and Mink. The solver generated joint-level motion commands while considering task error and joint-motion behaviour near singular configurations. For leader-follower teaching, I used URDF/KDL-based dynamics for leader-arm gravity compensation and follower position-velocity tracking. I also worked on the mobile base, where body-velocity commands were converted to wheel targets and encoder feedback closed the speed loop. The key engineering point was to keep the VR reference, robot coordinate frames, IK output and physical motor command clearly separated.

**你要能说清的关键点**：MuJoCo 是可运行的刚体动力学/运动学仿真引擎和模型计算工具，不是机械臂电机驱动器。它可以依据模型和当前关节状态算正运动学、位姿和 Jacobian；Mink 在这个模型/状态上组织任务误差与优化求解。最终真机运动仍要经过 ROS 2、驱动/CAN、电机和编码器反馈。不要说“MuJoCo 直接控制实机”。

### 具身控制方向：P7 轮腿机器人

> In the wheel-legged project, I worked on balance and motion control for a robot whose leg length could change. The controller used IMU, wheel and joint feedback. The wheel-control path used gains scheduled by leg height to turn pitch, pitch rate, integrated position and wheel speed into bounded left and right wheel-motor targets. In a separate VMC path, leg-end position errors, velocity damping, roll-balance terms and gravity feedforward formed virtual foot forces. The five-bar leg Jacobian transpose then mapped those forces into front and rear joint-torque commands. Both paths ran in the control loop; I would not describe the lesson-code path as LQR directly producing the VMC joint torques. The implementation ran on an STM32H7/FDCAN platform, and I investigated balance anomalies involving state consistency, torque limits and ground-contact transitions. The physical unit of the wheel target must be confirmed from the matching motor-driver implementation.

**你要能说清的关键点**：LQR 用状态反馈把“当前偏差”变成控制器输入；在第十一课代码中，腿高相关的 K 系数作用在俯仰角、俯仰角速度、积分位置和轮速上，形成左右轮目标值。VMC 则先依据腿端位置/速度误差和支撑需求形成虚拟足端力，再用腿 Jacobian 的转置换算成关节力矩。它不是“LQR 之后的一个单纯矩阵乘法”：这份主循环里轮控制与 VMC 分别计算。不要只凭状态数或输出个数给 LQR 下定义，也不要把 VMC 生成的髋/腿关节力矩说成 LQR 矩阵直接输出。

### CS/平台软件方向：P6 Kaihong M-Robots

> At Kaihong, I have been working on an OpenHarmony multi-robot platform. The goal is to make motion and task software work across heterogeneous robots without hiding device-specific behaviour. My work includes a capability model for sensors, actuators and controllers, adapters from ROS or ROS 2 commands to lower-level drivers, and consistent robot state with timestamps, coordinate frames and validity checks. The platform also uses M-DDS for device discovery, capability registration, state synchronization and task dispatch. A high-level task is treated as a proposal; a policy check comes before execution, and state feedback follows the action. This work taught me that distributed coordination and safe actuation require explicit contracts, not just message transport.

**你要能说清的关键点**：把“做了 M-DDS 上的应用级发现/注册/同步/调度”与“实现了 DDS 中间件内部协议”分开；把安全提议链与“已经形式化验证安全”分开。

### AI 方向：P4 OpenHarmony 智能园艺

> I built a personal OpenHarmony smart-gardening project that connected edge vision with irrigation. Camera frames were processed by a YOLOv5 model deployed in INT8 on an RK3588 board. The resulting structured observations fed a LangGraph decision chain, with a rule-based fast path for defined extreme states. A local soil-moisture state machine on a Hi3861 controlled the pump, with separate start and stop thresholds and manual-priority handling. This separation was important: the model or agent could produce a recommendation, while local device logic retained control of pump switching. The project demonstrated an end-to-end application loop, but I would not describe it as large-scale autonomy or claim accuracy and latency numbers without a test report.

**你要能说清的关键点**：YOLOv5 处理图像；INT8 是量化/部署精度方式；LangGraph 组织决策流程；Hi3861 本地状态机控制执行。它们不是一个模型，也没有“agent 直接给泵下电机控制量”。

## 3. 七个项目技术卡

### P1｜三轮全向球形机器人与双臂上身

**系统问题**：球体底盘需要动态平衡；手臂动作会改变总质心与重力矩。  
**输入**：IMU 姿态/角速度、轮反馈、目标位置/速度、双臂关节状态与模型参数。  
**处理**：传感器状态处理 → 位置/速度外环 → 有界姿态参考 → 姿态内环 → CoM 重力前馈 → 三轮运动学分配 → 整体限幅/滤波 → ROS/CAN 执行。LQR 用线性化四状态倒立摆模型分析状态权重和控制用力的权衡。  
**输出**：控制链中的轮命令，经过运动学/驱动层转换后才到电机。  
**实测边界**：简历写“在双臂固定轨迹下保持动态平衡”；不扩写为所有手臂动作、任意速度或无外界扰动都稳定。

**Follow-up: Was LQR the deployed balance controller?**

> The deployed balance loop in my description was cascaded PID. I built a linearized model and used LQR to analyse the state-weight and control-effort trade-off and to inform PID tuning. I would only claim that LQR generated the deployed gains if the matching code and configuration showed that.

**Follow-up: Is the CoM term a torque?**

> Physically, an offset centre of mass creates a gravity moment. In the controller, the feedforward term is added to a control channel before wheel allocation and scaling. I would call it a gravity-moment compensation term only if its units and calibration support that; a variable name alone is not enough to prove that it is a motor torque in newton-metres.

**Follow-up: How would you validate the compensation?**

> I would use the same arm trajectory and starting condition, compare the enabled and disabled cases, and log roll and pitch error, wheel commands, saturation and timing. Without those matched logs, I can describe the test setup but not claim a numerical improvement.

### P2｜VR 双臂遥操作、Leader–Follower 与底盘

**输入到输出**：VR controller pose → reference capture and coordinate mapping → desired wrist pose → position/orientation task error → constrained IK → joint velocity/position targets → simulator/model update or ROS 2-CAN motor execution → joint feedback.  
**机器人学基础**：MuJoCo forward kinematics maps joint state to body pose; a Jacobian describes how joint velocity changes end-effector linear/angular velocity. Mink builds task objectives and solves an optimization problem from model state. Damped optimization can trade exact task tracking for smaller/stabler joint updates near weak Jacobian directions.  
**主从教学**：leader arm gravity compensation reduces the force needed to hand-guide it; follower tracks leader position/velocity. The low-level controller/actuator still enforces its own limits.  
**验证边界**：简历说明真机通过 ROS2-CAN 验证；没有轨迹误差/速度峰值的数字就不报百分比。

**Follow-up: How is the Jacobian obtained?**

> It is computed from the robot model and the current joint configuration. The model provides each joint axis and the transforms from the base through the links to the end effector. For a revolute joint, the linear-velocity column is the joint axis crossed with the vector from the joint axis to the end effector, and the angular-velocity column is the axis itself, expressed in the chosen frame. MuJoCo updates the current geometry from the joint state; a robotics library then exposes or computes the Jacobian. The robot does not need to physically try a small movement to measure it.

**Follow-up: Does MuJoCo have to be present on the real robot?**

> Not necessarily. MuJoCo can provide the model-based kinematics and simulation used during development. A real robot can compute forward kinematics and Jacobians from URDF with a robotics library such as Pinocchio or another model implementation. The physical command must still go to the hardware driver. Whether MuJoCo is in the runtime path depends on the actual system architecture.

### P3｜RoboMaster Hero：云台、发射机构、底盘

**系统输入**：遥控/视觉目标、IMU/AHRS 姿态、陀螺仪角速度、云台/发射电机编码器与速度、电源/缓冲能量反馈。  
**控制链**：云台采用角度-角速度级联 PID；摩擦轮做转速闭环；拨盘用位置-速度双环；根据源码/版本经历 PID、变比例 PID、滑模控制迭代；底盘将速度指令通过麦轮运动学分到四轮，并按功率反馈缩放。  
**嵌入式执行**：STM32F407/FreeRTOS 任务调度、CAN 命令、反馈解码与下一周期闭环。协议里的 `give_current` 是电机命令字段/协议值；无换算与电机参数时不直接称为安培或牛米。  
**团队边界**：全国总决赛三等奖是队伍成绩；个人职责按简历写你负责云台、发射、底盘控制回路，不说成个人获得团队奖项。

**Follow-up: How do you distinguish the gimbal angle and rate loops?**

> The outer angle loop compares the target and measured angle and generates a desired angular rate. The inner rate loop compares that desired rate with filtered gyro feedback and generates a motor command. The motor moves, the IMU and encoder provide new feedback, and the loop repeats. The exact angle reference and signs depend on the source’s coordinate conventions.

**Follow-up: Why did the feeder controller evolve beyond PID?**

> A simple PID can work under a limited operating range, but friction, changing load and speed requirements can make performance vary. Variable-gain or sliding-mode approaches can be considered to change the response, but they also introduce tuning and noise/chattering trade-offs. I would identify the active algorithm and tested version before describing a result, because the controller changed over the project.

### P4｜智能园艺与边缘 AI

**完整链**：相机帧 → YOLOv5/RKNN INT8 推理 → 结构化观测/置信度/时间戳 → LangGraph 决策 → 规则安全快速路径/策略约束 → Hi3861 本地土壤湿度状态机 → 水泵 → 新环境状态/用户交互。  
**核心工程问题**：边缘推理和服务器端 agent 的延迟/失联；水泵启停阈值与滞回；手动优先级；旧观测是否过期；模型不确定时是否允许动作。  
**回答边界**：个人项目、完整原型链路；除非有实验记录，不报准确率、FPS、节水率或长期稳定性。

**Follow-up: Why use different start and stop thresholds?**

> Separate thresholds create hysteresis. The pump does not switch on and off rapidly when the moisture reading fluctuates around one value. The local state machine can therefore make a stable device-level decision, while manual priority provides another explicit control path.

### P5｜智能车自主导航

**模块角色**：EKF/AMCL 估计车辆状态；Hybrid-A* 搜索考虑航向与车辆运动学约束的全局可行路径；TEB 在局部代价地图和路径约束下优化带时间的局部轨迹；MPC 基于车辆模型和约束滚动优化并每周期执行当前第一步，然后用新状态再求解。  
**输入/输出**：IMU、轮编码器、2D LiDAR、地图/障碍物 → 位姿与不确定状态 → 全局 path → local timed trajectory → 速度/转角或控制命令 → 车辆反馈。命令具体单位以实际驱动接口为准。  
**关键问题**：时间戳/坐标系/行驶方向不一致会造成定位漂移或跳变；路径不是时间轨迹；规划可行不代表车辆一定跟踪得上。  
**验证边界**：简历称实车运行；无数值报告就不报定位精度、成功率或延迟。

**Follow-up: Why combine Hybrid-A*, TEB and MPC?**

> They solve different layers of the navigation problem. Hybrid-A* finds a global path that respects vehicle kinematics and obstacles. TEB adapts a local, time-parameterized trajectory to nearby obstacles and timing constraints. MPC uses a vehicle model and limits to track a short prediction horizon. The layers still need compatible coordinates, timing and constraints; the combination is not automatically optimal.

### P6｜OpenHarmony 多机器人平台

**关键概念**：设备抽象描述能力；adapter 做命令与驱动映射；robot state 需要时间戳/坐标系/有效性；M-DDS 承载发现、注册、同步和任务调度；action proposal、policy check、execution、feedback 划分权限与反馈。  
**可能架构追问**：消息队列是否有界？状态快照是否同一时刻？发现的设备能力何时失效？动作超时/重试是否幂等？驱动拒绝动作如何反馈？  
**回答边界**：可以说明你实现的应用/接口层行为；没有代码或安全论证时，不声称实现了 middleware 内核、故障容错证明或形式化验证。

**Follow-up: What is an action contract?**

> It defines what an action means, which state and capability it requires, what limits apply, how long the request remains valid and how success or failure is reported. A message schema alone is not a complete contract. The execution layer must still validate the current state and device capabilities.

### P7｜轮腿机器人 LQR + VMC

**按第十一课代码走一次**：

1. **轮子平衡/运动支路**：当前 `wheel_control` 中可见四个反馈量：`pitch × π/180`（rad）、`gyroY × π/180`（代码按角度/秒转成 rad/s）、累计位置 `position`（源码注释为 m）和轮速 `vel`（源码按电机速度乘轮半径构造；只有输入速度单位为 rad/s 时结果才是 m/s）。代码用足端高度 `h` 计算 `K1(h)`–`K4(h)`，将四项加权，再叠加转向/前后移动项并限幅，写入左右两个 `wheel_motor*_target`。主循环把它们交给 `sendMotorTargets`。所以这段活动调用体现的是“4 个反馈项 → 2 个轮目标命令”；不要把其他课件里的状态排列或维数不加核对地搬过来。
2. **腿端支撑支路**：`calRightVMC` / `calLeftVMC` 先用五连杆正运动学求足端位置与速度，再由高度误差、水平误差、滚转平衡项、速度阻尼和重力前馈得到足端虚拟力 `Fx/Fy`。
3. **虚拟力变关节力矩**：当前关节角决定闭链 Jacobian `J`；用 `τ = JᵀF` 的虚功关系得到每条腿前、后关节的力矩值。`can.cpp` 将这些值放进 MIT 电机参数的 `tor` 字段，再由 CAN 发送。
4. **两条支路汇到同一个控制周期**：主循环分别计算轮目标和左右腿关节力矩，再把它们发往不同执行器。就该代码调用关系而言，不应说成“LQR 输出先进入 VMC，再由 VMC输出轮速”。

**单位边界**：第十一课可见源码称轮量为 `wheel_motor*_target`，并将其交给预编译 `SF_Motor` 库的 `sendMotorTargets(float, float)`；库源码没有随仓库提供。因此，面试中应称它为轮电机目标命令，除非匹配版本的库/电机协议能证明单位，再称 N·m、rad/s 或电流。腿侧字段命名为 `frontTorque/backTorque`，CAN 层放入 MIT 参数 `tor`；仍需区分软件力矩命令和电机最终输出。

**代码版本提示**：第十一课 [`robot.cpp`](../../../gaint_bipedal_wheeled_robot-master/课程代码/第十一课_VMC实现/src/robot.cpp) 的 `wheel_control` 实际按腿端高度计算多项式增益；[`main.cpp`](../../../gaint_bipedal_wheeled_robot-master/课程代码/第十一课_VMC实现/src/main.cpp) 分别调用轮控制、左右 VMC 和电机发送；[`can.cpp`](../../../gaint_bipedal_wheeled_robot-master/课程代码/第十一课_VMC实现/src/can.cpp) 把腿力矩填入 MIT 的 `tor` 字段。第九课同名路径里虽有 `calc_K(h)` 函数，但 `wheel_control` 使用固定的 K 常数。讲面试经历时要说清采用哪份版本，不能把一个版本的调度行为套到另一个版本。

**实时计算量**：`calc_K1(h)`–`calc_K4(h)` 是对高度 `h` 求多项式，随后做少量乘加和限幅。可见控制循环没有每周期重新解 Riccati 方程；更准确的说法是，离线得到/拟合一组随腿高变化的反馈增益，运行时快速计算当前增益并做状态反馈。不要仅凭运算短就声称具体控制频率，实际周期仍需时间戳测量。

**CV 一致性核对**：CV 当前写“LQR … converted … into wheel-hub and hip torques”。本次可见课程代码里，腿关节力矩明确由 VMC 计算；轮侧则只看到目标值传入预编译电机库，无法从接口声明独立确认物理单位。面试前应将 CV 这句话与本人实际使用版本/驱动配置核实，避免把 VMC 输出说成 LQR 直接输出，或把未确认单位的轮命令说成确定的 N·m。

**风险**：腿长改变会改变增益与闭链 Jacobian；分母接近零时机构接近奇异；接触、限幅和状态时效也会影响控制。课程源码能支撑计算调用关系，不能单独证明特定性能数字。

**Follow-up: Why use the transpose of the Jacobian for force mapping?**

> The Jacobian maps joint velocity to foot velocity. Equating virtual work, the joint power τᵀ q̇ must match the foot power Fᵀ v. Since v = J q̇, this equality for any q̇ gives τ = Jᵀ F. This is a force/torque mapping; it is not the same as inverting the Jacobian to get joint velocity.

## 8. 技术面试深挖：不要停在“我用了某算法”

### 8.1 七层追问法

1. **问题**：现实中哪个量或目标没有满足需求？
2. **输入**：传感器/上游模块给了什么？单位、坐标系、时间戳、更新频率是什么？
3. **假设与模型**：小角度、线性化、二维平面、静态参数等简化在哪里？
4. **算法**：关键变量怎样把输入变成输出？
5. **接口**：输出是位置、速度、力/力矩、关节角还是协议整数？谁消费？
6. **验证**：对照、日志、仿真或实测是什么？无指标证据就不说数字。
7. **局限与下一步**：哪项假设最脆弱？下一项可验证实验是什么？

### 8.2 P1–P7 的代表性技术追问

#### P1：球形机器人平衡

**Q: Is the LQR output sent directly to the wheels?**

> No. The LQR gain maps a defined state vector to a control input in a linearised model. That input has a torque interpretation only if the model defines it as torque. A real ROS command may be wheel velocity or another actuator command, so the model input cannot be reused without a verified actuator mapping.

技术主线：四状态 `[x, x_dot, theta, theta_dot]`；连续模型 `A_c,B_c`、代价 `Q,R`、Riccati 解 `P`、反馈 `K`、`u=-Kz`。减号给出负反馈方向；线性模型只在工作点附近成立。CoM 重力项是可预测扰动的前馈估计，仍需反馈；核对轴符号、系数和最终命令单位。

#### P2：VR 双臂、IK、Mink 与 MuJoCo

**Q: How does a hand-controller pose become joint motion?**

> I map the controller's relative displacement and orientation change into the robot base frame. This gives an end-effector target pose. A robot model computes the current pose and Jacobian. The IK solver finds joint velocities that reduce the pose error according to the task formulation. In simulation, MuJoCo updates the articulated state; it is not the motor driver.

顺序：VR世界/手柄坐标 → 初始相对变化 → 轴向标定 → 机器人基座目标位姿 → 当前手腕位姿 → 六维误差 → Jacobian/IK → `q_dot` → 小步积分和新状态。旋转误差要固定坐标约定；位置米与角度弧度不能直接相加，任务权重做权衡。解析 Jacobian 由模型中关节轴、轴心、末端几何关系计算，不必让实机试转。

#### P3：云台、发射与 FreeRTOS

**Q: How would you prove that a nominal 1 kHz loop really runs at 1 kHz?**

> I would timestamp consecutive loop entries and report the mean, percentile range, maximum interval and missed deadlines under stated load conditions. A configured tick rate or `vTaskDelay(1)` alone does not prove the completed control-loop period.

区分反馈、目标、PID输出、CAN协议整数和物理电流/力矩；无协议缩放不可称为安培。堵转不能只凭“电流大”；要说明阈值、持续时间/滞回、保护动作和恢复条件，并按真实代码回答。

#### P4：园艺边缘 AI

**Q: How would you show that INT8 quantisation is acceptable?**

> I would freeze a representative validation set, compare FP32 and INT8 with the same images and preprocessing, report task metrics and target-device latency, and inspect failure cases. Faster inference is not useful if important classes become unreliable.

区分训练/验证/测试集；说明校准样本、预处理、端到端延迟与硬件。检测结果到泵动作之间还要讲清阈值、设备状态、超时/人工停止等保护。不要编造准确率、FPS或节水幅度。

#### P5：定位、Hybrid A*、TEB 与 MPC

**Q: What does each layer contribute?**

> Localization estimates where the robot is. Hybrid A* searches for a feasible global route while accounting for heading and motion constraints. TEB adjusts a local timed trajectory around nearby obstacles. MPC optimises a finite sequence of control inputs under a model and constraints, applies the first input, and replans from new feedback.

追问地图/里程计/激光各自作用、全局/局部规划尺度、离散模型、动作变量和约束。只有日志支持时才说多个模块在同一实机闭环运行；性能数字需要证据。

#### P6：OpenHarmony 多机器人/平台集成

**Q: How do you prevent a module from acting on stale or inconsistent state?**

> I would attach a timestamp, frame or device identity, validity and sequence information to each state update. A consumer should reject stale or mismatched data and define a safe response when a required input is missing. Shared interfaces make this policy explicit across modules.

明确自己负责的接口/状态/安全链，不把系统功能列表说成个人独立实现。只有确实发生过才讲异常案例；否则讲设计原则，不编事故。

#### P7：双足轮腿、LQR 与 VMC

**Q: What is the difference between LQR and VMC?**

> LQR and VMC do different jobs. In the lesson code I studied, the height-scheduled state-feedback gains use pitch, pitch rate, integrated position and wheel speed to compute bounded wheel-motor targets. The VMC path uses leg-end position and velocity errors to form virtual foot forces, then maps them through the Jacobian transpose into front and rear leg-joint torque commands. The main loop calls these as separate wheel and leg-control paths. The wheel target’s physical unit depends on the motor library, so I would verify that interface before calling it a torque.

**Q: Does VMC simply multiply by `Jᵀ`?**

> No. The controller first decides what force the virtual foot should produce. In the studied code, height and horizontal position errors produce force terms; velocity damping, roll-balance correction and gravity feedforward are also included. Only after the virtual force is defined does `Jᵀ` map it to joint torques. The Jacobian depends on the current five-bar geometry.

**Q: What does the wheel-control state vector look like in the code you studied?**

> In the active lesson function, I can point to four feedback terms: body pitch, pitch rate, integrated position and wheel speed. The height-dependent gains weight those terms, and the function writes two bounded wheel-motor targets. That is the implementation view; the state vector in a simplified derivation can use different symbols or ordering. I would identify the exact code path before stating the dimensions of the deployed model.

**Q: Does the robot solve the Riccati equation every control cycle?**

> No. In the lesson code, the gain functions are height-dependent polynomials. The control loop evaluates those functions and applies the resulting gains to the feedback terms. Solving the LQR design problem belongs to the offline design process; this implementation does not visibly run a Riccati solver in each cycle. I would still measure the complete loop before claiming a specific update rate.

**Version and unit check before the interview**：第九课与第十一课的轮增益调用不同；六状态/两输出只描述某个特定模型，不是所有 LQR 的固定形状。回到匹配版本检查状态向量、`B` 矩阵、函数调用和电机驱动接口；不要凭“输出有两项”推断一项是轮力矩、一项是腿力矩，也不要凭变量名猜单位。

### 8.3 一句单位/接口检查
