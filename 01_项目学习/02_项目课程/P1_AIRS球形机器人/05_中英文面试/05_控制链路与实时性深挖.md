# P1 控制链路、LQR 与实时性：面试深挖题

全项目问题归档见[历次问题归纳与完整讲解](06_历次问题归纳与完整讲解.md)。

本题库补充[原理、实现与验证问答](02_原理实现与验证问答.md)，重点练习面试官从一句项目描述一路追问到状态、滤波、控制、驱动和实测证据。

建议顺序：先能用 60 秒说完整个闭环；再练 LQR 与运行 PID 的边界；最后练频率、延迟、效率和验证。每题先用自己的话回答，再用英文参考句练口语。答案中的“源码确认”只表示当前检查的代码快照，不自动证明所有配置与历史实机版本一致。

系统总图和参数含义见[端到端闭环、数据时序与实时性](../00_项目全貌与学习路线/03_P1端到端闭环、数据时序与实时性.md)；逐函数过程见[一个控制周期](../02_源码阅读与运行/02_一个周期的调用与数据流.md)。

## A. 从简历的一句话讲到闭环

<a id="p1-q26"></a>
### P1-Q26 Can you walk me through the complete control loop?

**面试官在检查什么：**你是否理解状态、控制器、运动学分配和电机之间的因果关系，而不只是记住 PID/LQR 名词。

**中文答题逻辑：**先说传感器输入，再说估计量；接着说外环、内环、前馈、轮速分配；最后讲驱动和反馈回来的数据。点明各话题异步，不声称同一时间同步采样。

**English reference:**  
“The controller receives body orientation and angular rate from the IMU, wheel speeds from the chassis driver, and arm joint states through a separate model-based CoM path. It estimates horizontal velocity and integrates position from wheel feedback. The outer position and velocity loops generate bounded roll and pitch references, while the inner attitude loops use angle error and angular rate. The CoM-based gravity feedforward is added to the roll and pitch channels. The resulting command is mapped to three wheel-speed references, limited, filtered and sent through ROS to the CAN driver. New sensor feedback closes the loop.”

**继续追问：**Are all of those measurements sampled at the same instant?  
**回答要点：**No. They arrive through independent callbacks and the loop consumes the latest cached values; exact timestamp alignment is not established by the inspected path.

<a id="p1-q27"></a>
### P1-Q27 What is the controller’s state, exactly?

**中文答题逻辑：**不要把运行 PID 的许多变量和 LQR 分析模型的四个状态混成一套。运行路径用 IMU 姿态/角速度、轮速换算的水平速度和积分位置、目标状态及 CoM 偏移。四状态模型另用 x、x_dot、theta、theta_dot 来研究单一平面下的耦合。

**English reference:**  
“There is not one single state vector shared by every part of the software. The runtime controller uses IMU attitude and angular rate, wheel-derived horizontal velocity, integrated position, command references and the arm-related CoM offset. The separate four-state analytical model uses position, velocity, body angle and angular rate for one simplified plane.”

**继续追问：**Is x a globally localised position?  
**回答要点：**No. In this path it is obtained by integrating wheel-derived velocity, so slip and velocity bias accumulate; it is not corrected by GPS, vision or a global localisation filter here.

<a id="p1-q28"></a>
### P1-Q28 What filtering and sensor fusion did you use?

**中文答题逻辑：**具体说信号、滤波公式和更新位置。当前姿态四元数直接复制，IMU角速度、轮速、CoM的x/y以及最终电机v_des使用约0.8 Hz的一阶低通；线加速度、轮位置、effort、CoM theta等滤波截止频率为0，因此在本节点直接通过。传感器和CoM滤波在各自消息回调更新，v_des滤波在发布命令前更新。cmd_vel目标速度另用0.25逐消息平滑。滤波系数按配置100 Hz计算，实际回调率不同会改变实际响应；降噪同时会带来滞后。当前链没有整机状态Kalman更新路径。

**English reference:**  
“In the inspected path, orientation is copied directly, while IMU angular rate, wheel speed, CoM x/y and the final motor speed command use first-order low-pass filters with a configured cutoff near 0.8 Hz. The sensor filters update in their message callbacks, whereas the command filter updates before publication. The coefficients assume 100 Hz, so I would check actual topic rates and filter delay. This is not a full Kalman state-fusion path.”

**继续追问：**Why not filter everything more heavily?  
**回答要点：**更强滤波可能让角速度反馈变迟，降低平衡环及时制动的能力；必须比较噪声、延迟和闭环响应。

<a id="p1-q29"></a>
### P1-Q29 How did you handle time alignment between sensors?

**中文答题逻辑：**如实说明当前源码按回调更新最近缓存，控制定时器读取它们；源码检查未建立 IMU、轮速和 CoM 的统一采样时刻，也没有全面的数据年龄门限。提出日志/改进方案时，用“我会”而非“已经实现”。

**English reference:**  
“The current path updates each cache when its message arrives, and the control timer reads the latest available values. That is not the same as timestamp-synchronised fusion. I would log source timestamps, receive times and the age of every value used by a control cycle, then add explicit stale-data handling if the system requirements call for it.”

**继续追问：**Why can the latest value still be stale?  
**回答要点：**“最新”只相对该话题缓存而言；如果一个传感器停止发布，缓存里最后一条仍然是最新值，但可能已经过时。

<a id="p1-q30"></a>
### P1-Q30 Why use cascaded position and attitude loops?

**中文答题逻辑：**位置/速度是较慢的目标，姿态平衡希望更快响应。外环把“去哪、当前速度差多少”变成有限倾角参考；内环跟踪参考并利用角速度阻尼。当前主机两环都在同一个 100 Hz 定时器计算，“内环更快”指设计的响应速度/带宽，实际是否满足要测，不能说成源码另设了更高采样频率。倾斜用于改变速度，达到目标速度后可接近直立。

**English reference:**  
“The outer loop converts position and velocity errors into a bounded body-tilt reference. The inner loop tracks attitude and uses angular-rate feedback to brake the body before it overshoots. Both host-side loops run in the same configured timer; the intended difference is response bandwidth, which needs measurement. A temporary tilt changes speed, and the reference can return toward upright as the speed error shrinks.”

**继续追问：**If the target speed is non-zero, why does the robot not stop when it becomes upright?  
**回答要点：**倾斜主要改变速度；速度达到目标后，机身可接近直立，而大球和整机仍保有向前滚动速度。阻力和扰动下可能仍需小量控制。

## B. LQR 的作用、使用方式与计算代价

<a id="p1-q31"></a>
### P1-Q31 What exactly was the role of LQR in this project?

**中文答题逻辑：**回答三层：建立四状态简化倒立摆模型；用 LQR 看状态权重 Q 和输入权重 Ru 如何影响反馈增益；用结果帮助理解/参照级联 PID 增益与饱和。明确它是模型分析，不是已经确认的实机在线控制器。

**English reference:**  
“I used LQR on a linearised four-state inverted-pendulum model as an analysis tool. It helped me study how state penalties and control effort weights change the feedback gains, and gave a model-based reference for understanding the cascaded PID tuning and actuator saturation. The inspected runtime controller still follows the PID path.”

**继续追问：**What does LQR optimise?  
**回答要点：**在给定线性模型和二次代价下，折中状态误差和控制输入的长期代价；它不会自动处理模型外的碰撞、延迟、硬件限幅或传感器过期。

<a id="p1-q32"></a>
### P1-Q32 How did you obtain A, B and K?

**中文答题逻辑：**

1. 从质量、质心高度、轮/球半径和惯量建立简化动力学；
2. 在直立附近小角度线性化，状态取 [x, x_dot, theta, theta_dot]；
3. 由此形成连续模型 zdot=Acz+Bcτ；
4. 选 Q 和 Ru，连续 Riccati 求解得到 P，再算 K=Ru⁻¹BcᵀP；
5. 说明参数和小角度假设的适用边界。

当前脚本使用连续 LQR 接口。它还对一些 K 分量手工缩放，并打印 PID 形式的候选系数，所以缩放后的数值不再是原始 Q/R 的严格最优 LQR 增益。

**English reference:**  
“A and B came from a simplified coupled body-and-ball model linearised around the upright position. I used the continuous-time LQR routine with selected Q and R weights to obtain P and K. The analysis script then manually rescaled some gain components and printed PID-like candidate gains, so I distinguish those adjusted values from the original optimal LQR solution.”

**继续追问：**What assumptions limit this model?  
**回答要点：**小倾角、简化接触和执行器输入、单平面分析；完整三轮耦合、双臂多体动态、打滑、时间延迟和饱和没有全部建入。

<a id="p1-q33"></a>
### P1-Q33 Was LQR run on the robot in every control cycle?

**中文答题逻辑：**不是当前检查到的 C++ 控制链。该节点调用 X/Y、Roll/Pitch/Yaw PID；离线 Python 脚本求连续 LQR 增益并做分析/候选映射。不要把“在项目中使用 LQR 分析”说成“运行机器人由 LQR 控制”。

**English reference:**  
“No, not in the inspected runtime path. The ROS control loop calls the cascaded PID controllers and maps their outputs to wheel-speed commands. The LQR calculation is in a separate model-analysis script; I use it to explain the design trade-offs, not to claim that the robot ran online LQR.”

**继续追问：**How does this match the statement that you used LQR?  
**回答要点：**“Used LQR”可以准确指模型化分析和设计参照；如果没有实机 LQR 的调用、日志和部署版本证据，就不能升级成“LQR was deployed as the runtime controller.”

<a id="p1-q34"></a>
### P1-Q34 Does LQR require solving a Riccati equation every 10 ms?

**中文答题逻辑：**常规固定模型 LQR 在设计时求 P、K；运行时只需要乘 Kx。4 状态、单输入的反馈乘加很小。在线反复求 Riccati 是另一类自适应/时变设计，不是固定增益 LQR 的必要步骤；而本项目检查到的运行周期没有在线 LQR。

**English reference:**  
“A standard fixed-gain LQR solves the Riccati equation during design, not at every sample. At runtime it only multiplies the precomputed gain by the state vector, which is computationally small for a four-state model. In this project, that online multiplication was not the inspected runtime path; the deployed controller path uses PID.”

**继续追问：**So is LQR computationally expensive?  
**回答要点：**离线 Riccati 求解与在线矩阵向量乘法要分开；前者不在固定 100 Hz 控制周期里，后者对四状态系统很小。是否满足具体硬件 deadline 仍应计时，不能靠“矩阵小”当作实测。

<a id="p1-q35"></a>
### P1-Q35 How did LQR relate to the PID gains?

**中文答题逻辑：**脚本把四状态反馈增益分量整理成类似外环位置/速度项和内环姿态/角速度项的候选 PID 形式；但有人工缩放步骤，而且打印候选值不等于写入、部署或实机验证。运行参数另在 PID 配置文件和 ROS 控制器里读取。

**English reference:**  
“The analysis script expressed parts of the four-state feedback gain in a PID-like form, which helped relate the model-based feedback to position, velocity, attitude and angular-rate gains. Some components were manually rescaled, and the script output alone does not prove that those exact values were deployed. I keep the analytical candidates separate from the runtime PID configuration.”

**继续追问：**What would you need to prove a gain was deployed?  
**回答要点：**对应版本的配置文件或提交记录、启动参数、控制器启动日志，以及实机记录；仅有脚本输出或同名参数不够。

<a id="p1-q36"></a>
### P1-Q36 Can LQR guarantee stability on the real robot?

**中文答题逻辑：**它对所建线性模型、选定工作点、输入假设和未饱和反馈给出稳定性分析条件；模型误差、延迟、采样、饱和、打滑、接触状态变化和传感器过期都可能破坏实际保证。要做模型验证和闭环测量。

**English reference:**  
“The LQR result applies to the model and assumptions used in the design. It does not by itself guarantee hardware stability with delay, saturation, slip, contact changes or stale measurements. I would validate the model, enforce actuator limits and evaluate the closed loop under controlled tests.”

## C. 控制周期、滤波和效率

<a id="p1-q37"></a>
### P1-Q37 What does a 100 Hz control frequency mean?

**中文答题逻辑：**launch 默认设定定时器目标频率 100 Hz，名义间隔 10 ms。它不是传感器频率、CAN 频率、电机伺服频率或端到端延迟的证明。真实周期要记录相邻回调开始时间，检查分布、抖动和超期。

**English reference:**  
“The launch configuration requests a 100 Hz controller timer, which corresponds to a nominal 10 millisecond period. It does not prove that every callback runs exactly on time or that the sensors and motor interface share that rate. I would measure the actual period distribution, jitter and end-to-end latency.”

**继续追问：**How would you decide whether 100 Hz is enough?  
**回答要点：**结合机身主要动态、传感器和电机更新率、时延及抖动，观察闭环误差和稳定性；不能只凭配置数字判断。

<a id="p1-q38"></a>
### P1-Q38 How is 10 Hz cmd_freq different from the 100 Hz loop?

**中文答题逻辑：**100 Hz 是控制定时器；cmd_freq=10 Hz 在回调中用来设 cmd_dt=0.1 s，按每条 cmd_vel 更新速度参考和目标位置。cmd_vel 回调由消息到达触发，不是这段控制器代码自己定时发消息。若实际消息频率不同，目标积分的时间假设会失准。

**English reference:**  
“The 100 Hz value schedules the controller timer. The 10 Hz command setting is used to define a nominal 0.1 second command timestep in the callback, where the target velocity is smoothed and the target position is integrated. The callback itself is triggered by incoming messages, so the actual publisher rate must be checked separately.”

**继续追问：**What happens if commands arrive at 20 Hz while the code assumes 10 Hz?  
**回答要点：**每条命令仍按 0.1 s 推进目标位置，但真实间隔只有约 0.05 s，累计目标位移会偏大。

<a id="p1-q39"></a>
### P1-Q39 Why does the timestep affect the controller?

**中文答题逻辑：**dt 决定误差积分每步累积多少、误差差分换算速度时除以多少、位置积分每步走多少，也参与滤波系数。固定 dt 与实际周期不一致，会产生尺度错误；周期抖动还会改变反馈相位和延迟。

**English reference:**  
“The timestep appears in integration, numerical differentiation, position updates and filter design. If the actual interval differs from the assumed timestep, those calculations are scaled incorrectly. Timing jitter also changes the effective feedback delay, so I would measure it rather than treating dt as a harmless constant.”

**继续追问：**Would you use the measured dt instead?  
**回答要点：**基于可靠单调时钟计算实际 dt 可以减少积分/差分时间尺度错误，但还需要处理异常长间隔、数据过期和安全降级；改代码后必须做稳定性验证。

<a id="p1-q40"></a>
### P1-Q40 What is the effect of the 0.8 Hz low-pass filters?

**中文答题逻辑：**约 0.8 Hz 是滤波器截止频率参数；滤波抑制高频噪声，同时引入相位滞后。配置按 100 Hz 算系数，但每个滤波器在消息回调到达时更新；实际数据频率若不等于 100 Hz，实际时间响应会偏离设计。截止频率不能直接换成总延迟。

**English reference:**  
“The low-pass filters reduce high-frequency noise but add phase lag. Their coefficients are designed using the configured 100 Hz sampling rate, while updates occur when messages arrive. If a topic runs at a different rate, its effective filter response changes. The cutoff frequency alone is not the end-to-end delay.”

**继续追问：**Can stronger filtering make the robot less stable?  
**回答要点：**可以。姿态/角速度反馈更平滑但更晚，平衡控制可能来不及制动。需要在噪声、相位延迟和闭环响应之间折中。

<a id="p1-q41"></a>
### P1-Q41 How would you measure timing and real-time performance?

**中文答题逻辑：**用单调时钟记录控制回调开始/结束、输入缓存读取、publish、驱动接收、CAN 发送和反馈返回；记录传感器时间戳与接收年龄。统计周期/执行时间的平均、P95/P99、最大值、抖动、deadline miss、消息年龄和 CPU 占用。跨机器时钟先对齐。

**English reference:**  
“I would timestamp the controller start and finish, command publication, driver reception, CAN transmission and the next feedback arrival using a monotonic clock. I would report the mean, tail percentiles, maximum, jitter, deadline misses and sensor age, together with CPU load. Average execution time alone can hide rare but important overruns.”

**继续追问：**Why is execution time not the same as end-to-end latency?  
**回答要点：**执行时间只测控制器计算；端到端延迟还包含传感器采样、消息排队、等待定时器、驱动处理、CAN 和电机响应。

<a id="p1-q42"></a>
### P1-Q42 Is the controller computationally efficient?

**中文答题逻辑：**可以说算法结构的运算量不大：小型 3×3 矩阵和标量 PID。固定增益 LQR 在线也只是小矩阵乘向量。但没有计时和 CPU 日志，不能给具体毫秒或占用率，也不能把低算术量等同于完整系统实时可靠。

**English reference:**  
“The control arithmetic is small: fixed-size matrix operations, scalar PID updates and filtering. A fixed-gain four-state LQR would also need only a small matrix-vector multiplication at runtime. However, I do not have timing or CPU measurements to quote, and end-to-end real-time performance also depends on ROS scheduling, message handling, CAN and the actuator.”

**继续追问：**What can dominate the loop if the matrix math is small?  
**回答要点：**线程调度、回调积压、内存分配、日志、通信、锁竞争和驱动/电机延迟；要按阶段测量。

<a id="p1-q43"></a>
### P1-Q43 Would increasing the loop to 1 kHz automatically help?

**中文答题逻辑：**不会。传感器和电机如果不更快，循环可能反复读取旧数据；dt 和滤波系数要同步修改；噪声可能更频繁进入；CPU/CAN 负载上升。先测真实数据更新率、闭环带宽、延迟和执行时间，再确定是否需要更高频。

**English reference:**  
“Not automatically. If the sensors or actuator do not update faster, the controller may process repeated or stale data. The timestep and filter coefficients would also need to be reconsidered, and higher rates can increase noise and communication load. I would measure the plant and timing first.”

## D. 安全、效果与项目边界

<a id="p1-q44"></a>
### P1-Q44 Does a queue size of one guarantee command freshness and safe stopping?

**中文答题逻辑：**不保证。队列大小 1 和驱动端取最新命令、清空积压，有助于减少旧命令排队；但当前检查路径没有证明“命令超过某个年龄自动发零/失能”的完整 watchdog。失去新命令后的电机行为要查驱动固件和硬件超时。

**English reference:**  
“A queue size of one and taking the newest buffered command help prevent backlog. They do not by themselves implement a command-age watchdog or guarantee a safe stop. I would trace the driver and motor timeout behaviour and test the fault path before making that claim.”

**继续追问：**The CV mentions command freshness. How do you explain that?  
**回答要点：**说明简历中的职责和已经核实的源码事实分开：可解释最新命令/短队列如何减少积压；若声称有年龄检测或自动停机，需拿出对应实现、日志或硬件验证证据。

<a id="p1-q45"></a>
### P1-Q45 How would you evaluate the arm CoM feedforward?

**中文答题逻辑：**固定相同初始姿态、底盘目标和双臂轨迹，比较前馈开/关；记录 Roll/Pitch RMS/峰值、速度误差、恢复时间、饱和占比和电流。重复试验并控制电池、地面和参数变化。现有材料可以支持“固定轨迹下保持动态平衡”的项目描述；没有数字日志就不要补造百分比。

**English reference:**  
“I would replay the same fixed arm trajectory with matched initial conditions and controller limits, then compare attitude error, speed error, recovery time, saturation and motor current with feedforward enabled and disabled. I would repeat the trials and report the variation. I would not quote a numerical improvement without recorded measurements.”

**继续追问：**Why might feedforward fail even if the CoM model is correct?  
**回答要点：**CoM 与控制器参考点/坐标系不一致、消息过期、双臂状态不同步、前馈量纲/符号不一致、缩放顺序、限幅或接触扰动。

<a id="p1-q46"></a>
### P1-Q46 How would you compare PID and LQR fairly?

**中文答题逻辑：**当前项目不是已确认的实机 PID/LQR A/B 测试。先在同一简化模型和同一输入单位、采样周期、限幅、初态和扰动下比较；再决定是否有经过验证的模型力矩到轮速映射，才能上实机。报告相同指标和重复次数。

**English reference:**  
“I would first compare them on the same model with the same state definition, input units, sample time, saturation and disturbances. The analytical LQR input is an equivalent torque, while the runtime interface primarily sends wheel-speed references, so the actuator mapping must be validated before a hardware comparison. I would report the same tracking and effort metrics for both.”

**继续追问：**Why not compare only the final position error?  
**回答要点：**同样终点误差可能对应不同峰值倾角、超调、恢复时间、饱和和电机电流；应同时看安全、响应和控制努力。

<a id="p1-q47"></a>
### P1-Q47 What were the main limitations, and what would you improve next?

**中文答题逻辑：**优先讲本项目可证实的系统边界：轮速积分会漂移；消息异步且新鲜度保障有限；固定 dt 依赖频率假设；低通可能引入延迟；四状态模型简化且 LQR 不在当前运行周期；性能量化需要更完整日志。下一步提出可测的改进，而不是声称已完成。

**English reference:**  
“The main limitations are wheel-based position drift, asynchronous sensor updates, fixed timestep assumptions and filter-induced delay. The four-state model is useful for analysis but does not capture every contact and actuator effect, and the inspected runtime path remains cascaded PID. My next step would be to instrument data age and timing, validate the model against logs, and run controlled comparisons with explicit safety limits.”

<a id="p1-q48"></a>
### P1-Q48 Does the attitude controller output torque? How does that become wheel motion?

**中文答题逻辑：**先区分物理意图和源码实现。CoM的 \(mgd\) 项来自重力力矩公式，但 tau_roll / tau_pitch 是加了缩放、还要进入 ik 的中间控制量；当前源码没有证明它们严格以 N·m 标定，也没有把它们放进电机扭矩字段。物理上若从力矩算球角速度，需要转动惯量求角加速度、再按时间积分；当前控制周期没有显式做这一步，而是经过 K_t2v 与球轮分配矩阵直接生成 v_des。最终 v_des 的电机接口单位是 rad/s。

**English reference:**  
“The CoM feedforward is based on a gravity-moment expression, but the intermediate tau variables are scaled and mapped to wheel-speed commands. The inspected loop does not explicitly compute angular acceleration from torque and integrate it into a sphere angular velocity. It directly produces motor speed references through configured scaling and the wheel-allocation matrix. The motor interface defines v_des in radians per second.”

**继续追问：**Can you call tau_roll an N·m command?  
**回答要点：**不能只凭变量名。需要控制器增益的单位、K_t2v 的单位/标定和从控制量到驱动字段的完整标定证据。

<a id="p1-q49"></a>
### P1-Q49 Is v_des a wheel linear speed or angular speed, and who tracks it?

**中文答题逻辑：**v_des 是每台电机的轴角速度目标，单位 rad/s，不是轮缘线速度 m/s。整机组合 launch 默认 mode=1，控制器同时发送 v_kp/v_ki，驱动将目标和速度环增益打包发给电机。电机内部速度控制应跟踪该目标，但固件带宽和真实跟踪误差必须查固件资料或测量，不能由主机代码推断出来。

**English reference:**  
“The v_des field is a motor-axis angular-velocity reference in radians per second, not a wheel-rim linear velocity. In the combined launch, the controller and driver use speed mode and the command includes speed-loop gains. The motor controller is expected to track the reference, but its bandwidth and tracking performance require firmware documentation or measurement.”

**继续追问：**How would you estimate the wheel-rim speed?  
**回答要点：**理想情况下用轮半径乘角速度 \(v=r\dot\phi\)；球面接触后的底盘方向速度还要结合三只轮的方向几何。

<a id="p1-q50"></a>
### P1-Q50 Which motor mode is actually selected by the launch files?

**中文答题逻辑：**不能只看一个 launch。独立控制器 launch 默认0，独立 chassis_and_waist.launch 默认1；若直接把两者按默认值一起启动会不匹配。整机组合 arm_chassis_imu_pid_controller.launch 默认 chassis_mode=1，并把同一个参数传给底盘驱动和控制器，所以该组合默认对齐。实际运行仍要核对传入参数。

**English reference:**  
“The standalone controller and driver launch files have different defaults: mode 0 and mode 1. However, the combined arm-and-chassis launch passes one shared chassis_mode argument, defaulting to speed mode, to both nodes. I would always verify the actual launch arguments rather than infer the runtime mode from one file.”

**继续追问：**What can happen if the modes do not match?  
**回答要点：**发送方按一种模式填消息字段，接收方按另一种模式解释。例如控制器 mode=0 不会填 v_kp/v_ki 数组，而 SPEED 驱动会按电机序号读取它们；反向不匹配时阻抗驱动需要的 p_des/p_kp/p_kd/t_ff 也可能缺失。启动时必须同时检查双方模式和字段长度。
