# P5 导航一趟路是怎样走出来的

先不要背 Nav2、EKF、AMCL、Hybrid A* 这些名字。先想象一辆小车要从房间门口开到桌边：它得知道“我现在在哪”，选一条能走的路，边开边修正方向，还得把要求变成电机听得懂的命令。这些工作合起来才叫导航。

## 1. 先分清四个问题

| 人会问的问题 | 机器人要做的事 | 通俗说法 |
|---|---|---|
| 我现在在哪？ | 定位与状态估计 | 综合轮子、IMU、激光等信息猜当前位置和朝向 |
| 目标在哪？ | 全局规划 | 在地图上找一条从起点到目标的大路线 |
| 眼前怎么走？ | 局部规划与跟踪 | 根据附近障碍和车辆转向能力，给出短时间内可执行的动作 |
| 命令怎样到车轮？ | 控制与驱动 | 把速度/转向要求换成设备协议中的数值，再读回电机状态 |

这些模块传递信息，但每个都可能出错。地图上有路，不代表车立刻能到；控制器发了命令，也不代表电机确实执行。

```mermaid
flowchart LR
  A[轮速 IMU 激光] --> B[估计位置与朝向]
  B --> C[地图上的大路线]
  C --> D[眼前可执行的小段路线]
  D --> E[车辆控制与设备换算]
  E --> F[车轮和底盘]
  F --> A
```

## 2. 轮子为什么不能单独告诉车走了多远？

轮子转了多少圈，可以估计车向前走了多少。例如轮周长是 0.5 m，轮子转 2 圈，理想估计是 1 m。但如果轮胎在地上打滑，编码器仍然会报告“转了两圈”，车身可能只移动了 0.6 m。这就是为什么系统会把轮速与 IMU、激光或地图定位信息结合起来。

每种传感器各有盲区：轮速连续但会受打滑影响；IMU能快速感觉转动但积分会漂；激光能和环境地图对齐，却可能受遮挡、重复走廊或反光影响。定位不是挑一个永远正确的传感器，而是检查多种信息能否互相解释。

## 3. 车的转向能力会限制路线

像汽车一样的车通常不能原地横着移动。它主要通过前进速度和转向角改变路径。低速、转向角很小时，可以用简单直觉估算：转得越多，车头方向变化越快；开得越快，同一个转向角带来的转弯速度也越大。常见简化关系是

\[
\dot\psi \approx \frac{v}{L}\tan\delta,
\]

其中 \(v\) 是车速（m/s），\(L\) 是轴距（m），\(\delta\) 是前轮转角，\(\dot\psi\) 是车头转动速度（rad/s）。例如 \(v=1\) m/s、\(L=0.5\) m、\(\delta\approx0.1\) rad 时，\(\tan\delta\approx0.1\)，车头约以 0.2 rad/s 转动。这个模型帮助解释“车不能瞬间横移或掉头”，并不自动证明当前设备接口采用的单位或比例正确。

因此一条地图上看起来很短的路线，若拐弯过急或需要侧移，实际车辆可能开不了。规划器要考虑车的形状和转向能力，跟踪器还要不断用最新定位结果修正。

## 4. 定位中的 map、odom 与时间戳

可以把 `odom` 想成“从刚启动后一路累计的里程草图”：短时间比较平滑，但走久会慢慢偏。`map` 像“对照整张地图重新认位置”：长期不容易无限漂移，但重新匹配时位置可能有修正。

系统需要知道每个数据“在什么时候测的”以及“在哪个坐标系表达”。如果激光在 10:00:00.000 测量，轮速却来自 10:00:00.100，而车正在运动，把两者当成同一时刻就会错配。`TF`负责描述坐标系间的关系和它适用的时间；时间不对时，即使坐标变换公式没写错，结果也可能错。

学习定位时按这个顺序问：数据是谁测的？时间戳是什么？数据在哪个坐标系？定位器输出的是连续里程还是地图位置？再看EKF/AMCL等术语。

## 5. 全局路线、局部路线和控制不是一回事

全局规划器像在地图上画出大方向；局部规划器每次只看前面一小段，尝试选一串当前能走、能转弯、能避障的动作；跟踪器尽量让车跟上局部目标。障碍突然出现时，局部路线可能要重算；若车已经离路线很远，全局规划也可能重新启动。

历史资料中出现 Hybrid A*、TEB、MPC，并不能单凭文件存在就说它们都在当前车辆上同时运行。当前本地Nav2路径可见 Navfn 与 Regulated Pure Pursuit（RPP）等配置；TEB/H-A*/MPC需分别核对版本、启动配置、插件加载和调用证据。面试时把“我学过/分析过的算法”和“当前这份代码实际运行的算法”分开说。

## 6. 跟踪器输出怎样变成车轮动作？

规划器可能给“希望车以多快速度前进、转多快弯”。这仍是目标，不是车轮实际速度。控制器根据当前位置和车头方向的偏差调整目标；驱动适配层再把目标换成协议的字段和单位。板端如果将 `Twist`中的数值继续缩放为设备整数，必须追踪缩放、方向、饱和与反馈，不能看到字段叫 `linear.x` 就直接断定电机收到的是m/s。

一条完整的阅读链应该是：

1. 找到传感器消息和时间戳；
2. 找定位输出及其坐标系；
3. 找规划器插件和它接收的地图/目标；
4. 找跟踪器输出的速度/转角；
5. 找设备适配层的缩放与最终命令；
6. 找电机反馈怎样返回，以及无反馈或超时时发生什么。

## 7. 一个不用代码的故障推理例子

车在地图中明明有路，却一直左右摆。不要马上说“规划器坏了”。依次检查：激光和里程计时间是否对齐；`map→odom`位置是否跳；局部路径是否在两条选择之间频繁切换；跟踪器是否把角度误差的单位当错；底盘是否将正负转向符号反了；驱动反馈是否落后于命令。症状相似，原因可能在不同层。

## 8. 面试先讲一段简单的

中文可以这样组织：

> “我把导航拆成定位、路径规划、局部跟踪和车辆接口。定位综合轮速、IMU与环境观测；规划产生符合车辆运动能力的路线；跟踪器把路线转成短期运动目标；底层接口再转换成设备命令并读取反馈。我会按具体源码版本说明当前加载的算法，不把历史算法配置直接说成已部署。”

英文短版：

> “I explain navigation as four connected tasks: estimating where the car is, planning a feasible route, tracking a short-horizon motion target, and translating it into hardware commands. I distinguish algorithms visible in historical files from plugins confirmed in the current runtime.”
