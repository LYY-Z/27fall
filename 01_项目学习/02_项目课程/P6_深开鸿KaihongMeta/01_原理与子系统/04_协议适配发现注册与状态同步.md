# 04 从设备ID到寄存器：协议适配与状态同步

本章使用本地GroundLockHandler、ModbusAdapter和BaseDeviceHandler解释一条具体链。设备寄存器表和底层服务返回布局尚需核对，不能把教学帧当成已抓到的实机报文。入口见[源码地图](../02_源码阅读与运行/01_源码版本与文件地图.md)。

## 1. 发现、注册、初始化分别解决什么

发现是看到连接或公告；识别是知道型号和身份；注册是把设备与能力、处理器加入软件管理关系；初始化是建立配置、资源与回调；状态同步是取得设备当前报告的信息。

本地`Init(deviceId)`是**接收一个已有ID**，然后调用子类初始化。它没有独立展示M-DDS自动发现过程。地锁OnInit通过AccessInfoManager查询配置，再读出serialPort和subAddr。不要把这个配置查询改说成现场扫描硬件。

## 2. 为什么既有deviceId又有从站地址

教学设`deviceId="lock-A"`，其配置串口为2、从站为1，组合端口字符串`"2_1"`。

- deviceId是平台用来查设备的标识。
- serialPort=2选择哪条通信通道。
- subAddress=1选择这条总线上的哪个从站。
- `"2_1"`是本地处理器约定的配置表达，不是要原样发送的Modbus报文。

ParsePortInfo找到下划线，分别取两侧字符串，再把它们解析成整数。格式不存在、某侧为空或转换异常，都可能失败。`stoi`成功也不自动完成设备协议地址范围验证，要继续查范围与符号处理。

## 3. 命令从字符串变成协议字段

当ExecCommand根据`cmd="up"`选到Up函数后，Up查询该设备端口，调用WriteLockCommand。实际控制值来自LOCK_CONTROL_UP常量，不根据中文“升起”随意猜数值。

写路径构造的命令向量形如：

```cpp
cmd = {subAddress, 0x06, 0x00, 0x06, 0x00, 0x01};
data = {controlValue};
```

这里的vector是给适配器的参数集合，**不是已经包含CRC的完整串口字节帧**。读懂适配器ParseCmd才知道怎样使用它：

| 字段 | 当前ParseCmd如何解释 |
|---|---|
| subId独立参数 | 写入slaveId；不要只以cmd[0]判断最终地址 |
| cmd[1] | 功能码，例如0x03读保持寄存器、0x06写单寄存器 |
| cmd[2],cmd[3] | 高低字节合成寄存器地址 |
| cmd[4],cmd[5] | 读时合成数量；单写时先形成默认数据值 |
| RtuWrite的data | 随后覆盖DataOption.data，提供实际写入值 |

合成地址为什么乘256？一个字节有256种值，高位字节代表多少个256，低位字节代表剩余部分。例如`0x01*256+0x20=288`；`0x00*256+0x06=6`。

读17个寄存器时数量是`0*256+0x11=17`。单寄存器写的num在ParseCmd中固定为1；RtuWrite随后设置实际controlValue。因此不能把写向量末尾的`0x0001`简单解释为本次最终写入值。

## 4. RtuWrite在哪里打开、加锁和关闭

当前适配器按串口号映射到mutex槽位并加锁，打开RTU通道，解析命令，调用系统Modbus服务，再关闭通道并返回。

锁避免相关操作同时破坏通信事务，但“每端口独立锁”仍要看映射：本地使用`portNum % MAX_MUTEX_SIZE`，不同端口可能落在同一个锁槽位，从而被串行化。TCP用IP哈希映射，也可能碰撞。它不是每台设备天然都有一把完全独立的锁。

这层API成功仅说明其服务调用按返回约定成功。串口帧校验、从站异常、重试与响应含义，还要追到底层服务和设备说明。

## 5. 协议地址与C++数组下标为何必须核对

GroundLock读请求从地址0读取17个寄存器，但源码取`allData[7]`，注释写“地址0x0006”。如果返回数组恰好按从地址0到16依次放数据，通常地址6对应下标6；当前用了7，需确认底层是否有偏移或附加项。

“注释这样写”不能代替返回布局。应该核对设备寄存器表、ReadOrWriteModbusRtu怎样填vector，以及一个已知寄存器值的受控读回。本轮没有修改原源码或用硬件验证该映射。

## 6. 新读数、旧缓存和错误码怎样一起判断

ReadLockStatus失败时，可能把上次currentStatus复制到输出参数status，同时返回错误码。所以正确的调用规则是先判断ret，再决定status是否能作本次读数。

教学例：昨天缓存为1；今天设备断线；函数输出status=1、ret=ERROR。数字1只表明上次缓存，不表明今天读到了1。最好用valid、last_success_time和source把它明确表示。

## 7. 当前ListeningTask还有一层错误传播问题

这段是本轮直接核查到的活动代码：

```cpp
ret = ReadLockStatus(deviceId, portStr, status);
if (ret != EM_ERR_OK) {
    // 记录错误
    // return ret;  // 当前副本中被注释
}
// 继续使用status更新缓存
ret = ReportPropertyImpl(deviceId);
// 上报成功后可能返回EM_ERR_OK
```

因此不只是“调用方应该检查ret”：**这个具体调用方虽然检查并打印了错误，却没有在该分支退出**。它继续使用可能的旧缓存，上报成功后可以返回OK。基类按轮询函数最终返回码设置online，可能把这次未成功读回的设备当成在线；ReportProperty本身也有设online的路径。

这是源码静态事实，不是已经复现的断线结果。日志需要同时记录read_ret、report_ret、poll_ret和last_success_read_time，不能只看最后ret。完善方案是保留读取错误、标记旧值来源并避免用上报成功覆盖采样失败；它目前属于改进建议。

## 8. 时间戳怎样支持状态同步

至少分开设备采集时间、服务收到时间、缓存更新时间和最后成功读回时间。应用检查数据年龄，需要约定时间基准；不同机器的时钟不能直接相减，除非已同步并知道误差。

同进程测排队和耗时宜用单调时钟。接收时间说明“什么时候收到”，不能自动说明设备什么时候测量。旧消息到达后是否覆盖新状态，还需要序号或版本规则。

复习顺序：deviceId → 配置端口/从站 → cmd选择handler → 地址/数据参数 → adapter/service → 返回码 → 独立读回 → 状态有效性。英文：*A decoded value is useful only with its return status, source and freshness. An error at the read layer must remain visible to the final consumer.*
