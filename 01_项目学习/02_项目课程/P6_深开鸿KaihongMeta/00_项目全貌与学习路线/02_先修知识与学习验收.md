# P6 先修知识与学习验收

## 先用一次设备动作建立心智模型

先读[一次设备动作怎样走过软件平台](03_P6一次设备动作怎样走过软件平台.md)。想象上层请求“打开设备”，软件必须先识别设备、确认能力、选择接口、排队执行、等待结果，再接收设备状态。接口返回成功可能只表示“请求被接受”，未必表示物理设备已动作。

本章是软件平台与设备接入项目，不要用机器人控制的“传感器→PID→力矩”模式解释所有数据。这里核心是对象身份、能力、在线状态、命令生命周期和异步结果。

## 进入各章节前需要的基础

| 主题 | 需要认识 | 先建立的直觉 |
|---|---|---|
| C++ 对象和接口 | 类、对象、继承、虚函数、访问控制 | 上层通过共同接口调用设备能力，具体设备类负责真正实现 |
| 生命周期与内存 | 构造/析构、智能指针、所有权、RAII | 注册设备不等于设备始终在线；对象销毁时资源也要按所有权释放 |
| 并发基础 | 线程、任务队列、互斥、条件变量 | 多个请求可能同时到达；共享对象需要规则保护，避免数据竞争 |
| 异步结果 | 回调、future/promise、超时 | 函数返回“未来的结果”代表工作还没结束；等待也可能超时或失败 |
| 设备协议 | 发现、注册、适配器、序列化、解析 | 通用命令要经过设备能力与协议适配，才能变成对应设备可理解的消息 |
| 状态同步 | 属性、缓存、报告、时间戳 | 软件缓存表示最近收到的状态；没检查时间戳时，不一定是当前状态 |
| 可靠执行 | 重试、幂等、重复请求、回执 | 网络重试可能让同一动作执行两次；动作需有可识别的请求身份和完成状态 |
| 跨硬件适配 | 共同接口、硬件驱动、平台差异 | 同一个接口名不保证不同设备底层语义完全相同，需核具体适配器和协议 |

通用入口：[基础课程总览](../../../01_通用基础/00_基础课程总览.md)。若 C++ 语法不熟，先看类/指针/生命周期；若线程不熟，先画生产者、队列、消费者三者关系。

## 建议路线：从“请求”追到“可确认的结果”

1. 读平台地图，列出软件对象：设备、能力、状态、动作、适配器、执行器和报告器。
2. 从入口追一次命令：谁构造命令、如何选设备、如何校验参数、如何进入队列。
3. 追异步执行：哪个线程/线程池取任务，如何调用设备处理器，promise 在哪里完成，future 的等待方如何收到结果。
4. 追设备侧：共同接口如何被设备适配器翻译为协议，实际发送/调用失败怎样返回。
5. 反向追状态：协议反馈如何解析成属性，如何更新缓存并通知上层。
6. 最后追异常：设备发现不到、离线、命令参数错误、执行超时、重复重试、回执迟到或状态过期时，系统实际如何表现。
7. 对照仓库文件地图，把核心抽象、具体实现和未完整提供的子模块分开。架构推理不能替代实现证据。

## 一次命令的状态阶梯

看日志或源码时，把下列阶段分别记下来：

**调用方提出请求 → 参数通过校验 → 命令进入队列 → 执行线程开始处理 → 适配器调用/发送成功 → 设备确认收到 → 设备执行完成 → 新状态报告到达并验证。**

不同系统可能只实现其中一部分。不要把“函数返回 true”“future 有结果”“网络发送成功”直接等同于“设备物理动作完成”。若代码没有执行确认或新状态报告，应明确写出证据缺口。

## 学完每章后的验收

1. **讲对象**：设备是谁、能力是什么、状态从哪来、动作由谁执行。
2. **讲类型**：关键接口的输入/输出类型、所有权和错误结果是什么。
3. **画时序**：调用线程、队列、工作线程、设备回调之间谁先谁后；哪里可能阻塞或超时。
4. **讲状态新鲜度**：缓存值由谁更新、何时更新、如何判断是否过期。
5. **讲可靠性**：失败是否重试、重复命令是否安全、回执表示哪一层完成。
6. **核证据**：对每个结论标注实际文件/调用；架构设计、源码现状、教学建议分开。
