# P1 端到端闭环：传感器怎样变成电机动作

本项目多轮追问的总归纳见[历次问题归纳与完整讲解](../05_中英文面试/06_历次问题归纳与完整讲解.md)。

这份文档把 P1 的结构、传感器、状态计算、滤波、级联 PID、双臂质心前馈、轮速分配、驱动器和 LQR 分析接成一条线。它是整机“地图”；每个公式和源代码细节仍回到对应主讲章节。

先记住最重要的边界：

- **当前源码的运行路径：**IMU/轮速反馈 → 状态与位置计算 → 位置外环和姿态内环 PID → 双臂 CoM 重力前馈 → 三轮速度分配 → ROS 驱动命令。
- **LQR 的位置：**连续四状态倒立摆模型的离线分析和候选增益计算。当前检查到的 C++ 控制周期仍调用 PID；没有在每个周期在线求 Riccati 方程，也没有证据表明 LQR 反馈律直接替代了实机 PID。
- **频率的证据：**配置默认控制定时器为 100 Hz、速度指令设计频率为 10 Hz。这是程序配置，不是实测周期、端到端延迟或稳定性证明。
- **系统性能的证据：**现有资料没有给出控制周期分布、最坏执行时间、CPU 占用、传感器到电机延迟或跟踪误差统计。因此本章讲怎样分析和测量，不虚构“效率提升百分比”或真实延迟。

学习路线：先读本章弄清全局，再逐周期读[一个控制周期](../02_源码阅读与运行/02_一个周期的调用与数据流.md)，回到[级联 PID](../01_原理与子系统/03_级联PID与实机执行链.md)、[四状态模型与 LQR](../01_原理与子系统/04_四状态倒立摆与LQR分析.md)、[CoM 前馈](../01_原理与子系统/05_双臂CoM与重力前馈.md)查公式，最后练习[控制链路与实时性面试深挖](../05_中英文面试/05_控制链路与实时性深挖.md)。

## 1. 先把简历中的项目说法变成可解释的工程链

当前 CV/PS 对 P1 的核心说法可以概括为：在双臂沿固定轨迹运动、质心改变时，使用 IMU 和轮速反馈进行球形底盘动态平衡；控制器采用位置外环与姿态内环组成的级联 PID；用 URDF/Pinocchio 估计 CoM，并把重力补偿接入控制；另建立四状态倒立摆模型，用 LQR 分析权重、增益和执行器饱和。

面试官听到这些词，通常会追问“每个名词在系统里具体做什么”：

| 简历/PS 内容 | 需要解释的实现 | 证据边界 |
|---|---|---|
| 动态平衡 | 姿态误差和角速度经内环产生控制作用，球轮把作用变成轮速命令 | 源码说明实现路径；实际效果应由实验记录支持 |
| 位置外环、姿态内环 | 位置/速度误差生成有限的 Roll/Pitch 参考；内环追踪角度并利用角速度制动 | 当前控制器源码所示的 PID 路径 |
| IMU、轮速反馈 | IMU 姿态/角速度与轮子速度从不同话题异步进入；轮速经几何关系形成速度，位置由速度积分 | 不要把积分位置说成 GPS、视觉或全局定位 |
| 双臂 CoM 重力前馈 | 关节状态进入 URDF/Pinocchio，算出 CoM；底盘消费 CoM 位置，形成 Roll/Pitch 补偿 | 已查到位置通路；CoM 速度订阅在该版本被注释 |
| LQR 分析 | 用简化连续线性模型比较状态权重和控制代价怎样影响反馈增益 | 不是当前 C++ 周期在线执行的 LQR 控制器 |
| ROS 到 CAN 电机 | 控制器填充三轮命令消息，驱动节点取命令并调用电机 CAN 接口 | 模式、超时和实机部署版本仍需分别核实 |

个人贡献用语要以自己的实际职责为准。项目源码存在，不自动证明其中每一行均由一个人编写；配置值存在，也不自动证明它们就是最终部署值或性能测量值。详细材料映射见[CV/PS 表述与证据](../04_贡献_证据与材料映射/01_CV_PS表述与证据.md)。

## 2. 一眼看懂整条系统链

把机器人想成每隔一小段时间回答同一个问题：

> 我现在处在什么状态？目标希望我处在什么状态？为了缩小差距，三只轮子下一步各转多快？

信息流如下：

**目标速度/位置**  
→ 速度命令回调：平滑目标速度，并按配置周期更新目标位置  
→ **状态输入并行到达：**IMU 姿态/角速度；轮子速度；双臂关节状态 → URDF/Pinocchio → CoM 位置  
→ 位置外环：位置误差和速度误差 → 有界 Roll/Pitch 参考  
→ 姿态内环：姿态误差和 IMU 角速度 → 三轴虚拟控制量  
→ 加入 CoM 重力前馈  
→ 球轮运动学分配 → 整组限幅 → 命令低通滤波  
→ ROS 命令 → 驱动节点 → CAN 电机接口  
→ 电机改变球和机身运动 → IMU/轮反馈进入下一轮。

这不是单向的“一算完就结束”。电机命令改变大球和机身运动；新运动改变 IMU 与轮速读数；下一轮控制再据此修正。这个反复过程叫**闭环**。

每个模块的输入输出要分开：

| 环节 | 输入 | 输出 | 不要混淆成 |
|---|---|---|---|
| 传感器 | 真实运动和安装关系 | 有噪声、带时间的测量 | 完美真实状态 |
| 滤波/缓存 | 新测量 | 平滑后的最近一次数据 | 多传感器自动同步 |
| 状态计算 | IMU 姿态、轮速、模型几何 | 倾角、水平速度、积分位置等 | 全状态 Kalman 融合 |
| 位置外环 | 目标/估计位置和速度 | 有界的身体倾角参考 | 三个电机的直接命令 |
| 姿态内环 | 目标倾角、当前倾角、机身角速度 | Roll/Pitch/Yaw 中间控制量 | 物理上已标定的电机力矩 |
| 前馈 | CoM 偏移和模型参数 | 对可预测重力影响的补偿 | 对所有扰动的完全抵消 |
| 运动学分配 | 三轴中间控制量 | 三轮目标速度 | 电机内部电流或力矩 |
| 驱动器 | 命令消息和模式 | CAN 电机参数帧 | 已证明的闭环带宽/停机时限 |

### 一个重要的量纲提醒：内环不是直接把力矩发给电机

姿态PID计算的 tau_roll / tau_pitch 是进入后续缩放和轮子分配的中间控制量。双臂前馈中的 \(mgd\) 来自物理重力矩公式，但它在源码里也会与中间控制量合成。当前控制周期没有显式使用 \(I\alpha=\tau\) 求球角加速度、再对时间积分成球角速度；它按源码顺序在轴向中间量与轮命令两处使用 K_t2v，并经过 ik 矩阵，直接形成三只电机的目标速度数值。

整机组合启动默认使用 mode=1。最终消息字段 v_des 是电机轴目标角速度，接口单位 rad/s；它不是轮缘线速度，也不是电机力矩。驱动还会把速度环增益交给电机内部控制器。单独 launch 的默认 mode 可能不同，必须以实际组合 launch 和覆盖参数为准。

完整滤波时机、数值换算、模式分支和“源码哪些单位能确认/哪些不能确认”见[一个控制周期](../02_源码阅读与运行/02_一个周期的调用与数据流.md)的滤波清单、执行器链和单位追踪补充。

## 3. “当前状态”由哪些数据组成？

本项目没有一个唯一的、所有模块都共享的状态向量。运行控制器根据任务使用若干状态量：

| 状态量 | 来自哪里/怎样形成 | 它告诉控制器什么 |
|---|---|---|
| Roll、Pitch、Yaw | IMU 姿态四元数转换成欧拉角，再减去启动时设置的偏置 | 机身当前朝向相对参考差多少 |
| 机身角速度 | IMU 的 angular_velocity；当前源码对角速度低通滤波 | 机身正在以多快速度转动 |
| 三轮角速度 | 驱动反馈的 JointState velocity，再经过轮状态滤波 | 每个驱动轮当前转速 |
| 球角速度 | 三轮角速度乘配置的正运动学矩阵 fk | 大球绕三个轴的角运动估计 |
| 机身水平速度 vx、vy | 球角速度乘有效球半径，并按源码符号换算 | 机器人当前水平运动速度估计 |
| 位置 x、y | 把水平速度按偏航转到世界方向，再用固定 dt 积分 | 从积分起点开始累计的相对位置估计 |
| 目标速度 vx_d、vy_d | cmd_vel 每次到达时用平滑系数更新 | 外环希望达到的速度 |
| 目标位置 x_d、y_d | 对平滑后的目标速度按 cmd_dt 积分 | 速度命令对应的累计目标位置 |
| CoM 水平偏移 | 两臂 JointState + URDF 模型 + Pinocchio，再由底盘回调接收 | 重力会对平衡产生多大可预测的倾覆趋势 |

容易漏掉的边界：

1. 当前控制器里的 x、y 来自轮速积分，不是外部定位；轮子打滑或速度偏置会令位置逐渐漂移。
2. IMU 姿态在当前滤波器中是直接复制，角速度走低通；不能把它说成“项目用 Kalman 融合了 IMU 和轮速”。
3. hasData 表示至少收过一条消息，不等于当前消息新鲜、有效或与其他传感器同一时刻。
4. CoM 来自另一个 ROS 节点；不同话题异步更新。底盘版本消费 CoM 位置，不能因为上游发布过速度就声称速度前馈已参与控制。
5. 四状态 LQR 模型的状态是 [x, x_dot, theta, theta_dot]。它是分析模型，不等同于运行 PID 控制器实际维护的所有变量。

逐项计算见[一个控制周期](../02_源码阅读与运行/02_一个周期的调用与数据流.md)第 2—10 节；状态和传感器基础见[结构、传感器与平衡状态](../01_原理与子系统/01_结构传感器与平衡状态.md)。

## 4. 几个“时钟”并不相同

机器人里没有一个频率能代表整个系统。当前快照能确认的是配置和代码如何使用周期；真实消息频率和硬件时间要靠运行日志测量。

| 时钟/更新来源 | 当前源码/配置能确认什么 | 暂时不能据此声称什么 |
|---|---|---|
| 底盘控制定时器 | launch 默认 freq=100，定时器周期为 1/freq=0.01 s；控制器的 dt 由同一参数得到 | 实际每次恰好 10 ms、无抖动或满足实时 deadline |
| cmd_vel 目标更新 | 默认 cmd_freq=10，代码令 cmd_dt=0.1 s；每条消息到达时平滑速度并用这个 dt 更新目标位置 | 控制器真的创建了 10 Hz 的 cmd_vel 定时器，或发布者实际恰好 10 Hz |
| IMU/轮反馈回调 | 收到消息时更新缓存和滤波器；低通参数按配置的 100 Hz 设计 | IMU/轮反馈传感器自身一定以 100 Hz 到达，或两种消息同步 |
| CoM 回调 | CoM 位置消息到达时更新底盘中的位置和滤波值 | 两臂、IMU、轮状态在同一时间戳 |
| 驱动状态发布 | 驱动代码使用自己的 pub_freq 周期发布电机状态 | 它与控制器 freq 相等；除非对应驱动配置已查明 |
| 电机内部伺服 | 驱动接口按模式发送参数 | 电机内部环频率、最坏延迟或带宽；当前材料没有测量记录 |
| LQR 设计 | Python 离线脚本读取模型与 Q/R 并求反馈增益 | 有一个在线 LQR 控制循环或每个周期都调用求解器 |

### 4.1 控制器配置 100 Hz 代表什么？

100 Hz 表示定时器**计划**每秒调用 100 次。名义时间间隔是：

\[
\Delta t_{\mathrm{nominal}}=\frac{1}{100}=0.01\text{ s}=10\text{ ms}
\]

这 10 ms 同时进入若干离散计算，例如位置积分、误差微分和滤波器系数。它不是说 10 ms 内一定完成传感器采样、ROS 传输、控制计算、CAN 发送和电机动作的全部闭环。

控制代码使用固定 dt，而不是每次拿实测间隔重新计算。如果实际调用间隔忽长忽短：

- 积分误差和位置积分按固定时间累计，实际变化可能对不上；
- 用误差差分的 D 项按固定 dt 换算，实际速度估计可能偏大或偏小；
- 延迟和抖动改变反馈相位，响应可能变钝或更容易振荡。

因此要分别记录**请求的周期**与**真实的周期**。

### 4.2 cmd_freq=10 Hz 代表什么？

这里的 cmd_freq 不是底盘控制循环。它主要定义一条速度命令按多大的时间间隔来理解。源码在每次 cmd_vel 回调时使用约 0.1 s 去更新目标位置：

\[
x_{d,\mathrm{new}}\approx x_{d,\mathrm{old}}+v_{d,x}\times0.1
\]

如果命令实际每 0.05 s 到一次，但程序仍每条按 0.1 s 积分，目标位置会比真实经过的时间走得更远。反过来也会造成目标位置推进不足。0.25 的速度平滑系数也是“每条消息更新一次”；消息频率改变时，速度参考的实际平滑时间也会改变。

所以面试中要说清：控制循环按配置的定时器运行；cmd_vel 回调按消息到达触发；cmd_dt 是代码采用的时间假设，并非实际测得的消息间隔。

### 4.3 滤波采样频率与真实回调率不一致会怎样？

角速度、轮速、CoM 和最终轮命令的滤波器采用约 0.8 Hz 截止频率，并按 100 Hz 配置采样频率构造。以一阶低通为例：

\[
\beta=\frac{\Delta t}{\Delta t+T_f},\qquad T_f=\frac{1}{2\pi f_c}
\]

当设计周期 10 ms、截止频率 0.8 Hz 时，\(\beta\) 约为 0.0479。每次新消息只给新样本约 4.8% 的权重，其余来自上一次滤波输出。

若回调实际更新率不是 100 Hz，程序仍使用同一个 \(\beta\)，每秒更新次数就改变，滤波的实际时间响应也随之改变。比如传感器改为 50 Hz，但继续每条用 100 Hz 设计的系数，滤波会比原设计更慢。0.8 Hz 是滤波设计参数，不等于“总延迟就是 1/0.8 秒”；实际相位延迟要结合采样率和信号频率分析或测量。

滤波能降低高频噪声，但会延迟反馈。对倒立摆来说，延迟的角速度相当于晚踩刹车；不能只看曲线更平滑，就断定闭环更稳。

下面只是当前阅读快照中的 YAML 配置值，帮助你把参数和链路对应起来；它们不是控制频率、真实闭环增益或系统性能的测量结果。

| 配置项 | 当前文件值 | 放在链路中的位置 |
|---|---:|---|
| XLoop/YLoop | Kp=0.06、Ki=0、Kd=0.3，输出限幅约 0.1 | 位置/速度误差变成有界倾角参考 |
| RollLoop/PitchLoop | Kp=161、Ki=0、Kd=46.8 | 姿态角误差与角速度形成内环控制量；之后还会缩放和分配 |
| YawLoop | Kp=3、Ki=0、Kd=3.4，输出限幅 2 | 偏航角控制 |
| WheelVelocityLoop | Kp=6、Ki=10，输出限幅 8 | 使用该对象参数配置轮命令限幅；限幅作用于三轮向量 |

### 4.5 把“某个默认值”追到实际组合 launch

`arm_chassis_imu_pid_controller.launch` 统一传入 `chassis_freq=100` 与 `chassis_mode=1` 给底盘驱动和控制器；其 `arm_freq=50` 同时用于双臂状态发布、固定轨迹节点和 Pinocchio 补偿节点。该组合下的源码配置关系是：底盘控制名义 10 ms、底盘状态名义 10 ms、双臂与 CoM 名义 20 ms，目标积分仍采用 `cmd_freq=10` 对应的 100 ms。

单独 `arm_compensation_pid_controller.launch` 默认 mode=0；因此“项目默认 mode=0/1”必须同时说清哪个入口。这些配置说明软件意图，均不证明实际消息到达率、SDK耗时和电机内部循环。底盘 CoM 滤波系数按其 `freq_=100` 计算、却在 CoM 回调中更新；组合 launch 的 CoM 名义 50 Hz，使它与 100 Hz 系数设计存在可读出的时间尺度差异。若确实每 20 ms 更新一次，0.04786 的系数约需 1.24 s 达到常数阶跃的 95%；这是递推的理论例，不是已测得的闭环延迟。

## 5. 按时间顺序走完一个控制周期

下面描述的是源码快照所示的控制职责。回调、定时器、独立 CoM 节点和驱动线程并不是在一根整齐的“同步流水线”里同时采样；控制周期读取的是各缓存当前保存的最近数据。

### A. 周期开始前：消息先到各自回调

1. IMU 消息到达后，姿态四元数直接存入滤波消息；角速度分量低通滤波。
2. 轮子 JointState 到达后，速度经轮状态滤波写入缓存。
3. cmd_vel 到达后，目标速度按 cmd_smooth 更新，并按固定 cmd_dt 积分目标位置。
4. 双臂消息在独立节点进入模型，Pinocchio 按关节位置更新连杆姿态和 CoM；底盘收到 /com_pos 后更新 CoM 缓存。

这四类消息各有自己的到达时间。若没有时间戳比较和数据年龄检查，最新缓存也可能已过时。

### B. 定时器触发：先决定“这帧能不能算”

控制周期首先检查 ROS 是否正常、控制器是否已使能、IMU 和轮反馈是否至少来过一帧。没有任何数据就返回。跌倒阈值也在运行控制前检查。

一个需要特别留意的实现事实：使能等待超时后，源码会警告并继续置为 enabled；后续 hasData 可以阻止无数据的控制运算，但 hasData 不会检查数据年龄。跌倒分支 reset 后直接返回；是否停止电机要沿后面的 driver 与硬件超时路径另查。

### C. 从传感器量得到当前运动估计

1. IMU 姿态转成 roll、pitch、yaw，并减去启动偏置。
2. 三轮反馈速度经 fk 变成球角速度。
3. 球角速度乘半径换成机身水平速度。
4. 水平速度按偏航旋到世界方向，乘固定 dt 累计到 x、y。

因此 x、y 是“从初始化位置起积分了多少”的估计。它会积累轮速偏差，不具备绝对位置校正。

### D. 外环先问“我应该加速还是减速？”

外环比较目标位置/速度与当前估计，调用 XLoop/YLoop 产生 pitch/roll 参考，并限制参考大小。这个参考的意义是“机身朝哪个方向偏一点，有助于产生所需的加速度”，不是命令身体必须一直保持大倾角。

当速度还低于目标时，外环会要求产生加速作用；速度误差缩小时，倾角参考减小。目标是固定位置时，位置误差还会让系统在终点前提出减速要求。

### E. 内环问“身体离参考多远、冲得有多快？”

姿态内环读取 roll/pitch/yaw 和 IMU 角速度。比例项根据角度差把机身拉向参考；角速度项提供阻尼，允许系统在角度尚未越过目标时提前制动。当前 PID 还有积分、角度环绕和限幅等细节，不能只用教科书上的理想 PD 公式替代源码。

### F. 把双臂重力影响提前加进去

双臂改变 CoM 后，重力相对球/机身支撑参考点产生不同倾覆矩。前馈根据 CoM 位置估计这项可预测影响，把补偿放进 roll/pitch 中间控制通道。IMU 反馈仍然必要，因为模型误差、时序差、外力和轮地接触不会被 CoM 前馈消除。

当前实现还存在量纲要核对的路径细节：姿态 PID 输出先乘一次 K_t2v，CoM 项在此后加入；轴量经过 ik 后整体再乘一次 K_t2v。因此 PID 和 CoM 两项通过的缩放并不相同。不能只看 tau_* 名称断言两项均已校准为 N·m。

### G. 从三轴控制意图变成三只轮的目标速度

合成后的三个轴控制量乘球轮几何矩阵 ik，得到三只轮的命令向量。程序按整个向量的 L2 范数做统一限幅，然后速度命令还经过低通滤波。

整体缩放能保留三个轮之间的比例，但若要求向量超过上限，动作幅度会被压小，姿态或速度跟踪可能变慢。命令滤波器还有历史状态，所以“本周期刚算出的 action”不一定等于最终发布的速度。

### H. ROS 驱动转发，传感器在后面回来

控制器发布三轮命令消息。驱动代码缓存新命令、取最新的一条并清掉积压，再按驱动配置模式把消息字段交给 CAN 电机接口。驱动状态由另外的发布周期返回。

队列只保留最新命令有助于避免排队越来越旧，但它不等于有“命令年龄超过某值就安全刹车”的保证。当前已检查的循环没有证明完整的 command watchdog；电机失去新命令时具体会怎样，需要继续核对电机固件和硬件超时。

## 6. 单线程回调与异步传感器：为什么“一个周期”并非同时刻？

控制器运行入口使用 ros::spin()。在这份代码没有另建 AsyncSpinner 的路径里，订阅回调和定时器回调由默认 ROS spinner 处理；长回调可能推迟其他回调或控制定时器。订阅队列大小为 1 能限制积压，但不能让所有话题采样同步。

设想一个**纯教学时间线**，不是实测记录：

| 时间 | 0 ms | 4 ms | 8 ms | 10 ms | 20 ms |
|---|---|---|---|---|---|
| IMU | 新消息 |  | 新消息 |  | 新消息 |
| 轮反馈 |  | 新消息 |  |  | 新消息 |
| cmd_vel | 新目标；之后约 100 ms 才有下一条 |  |  |  |  |
| 控制环 |  |  |  | 读取各自当时最新缓存 | 再读取最新缓存 |

10 ms 的控制计算可能使用 8 ms 的 IMU、4 ms 的轮反馈，以及更早生成的目标和 CoM。它们都可以是各自“最新”的数据，却不是同一瞬间的状态。这种差异叫时间不对齐；对快速运动系统，它可能表现为控制滞后或抖动。

若要改进或评价，需要记录每条消息的采样时间、回调接收时间、控制周期使用时间，并计算数据年龄。当前 Pose2D 没有 Header 时间戳；Twist 也没有 Header，若需要追查命令延迟，需要在系统边界额外记录单调时钟时间。

<a id="timing-cache-age"></a>
### 6.1 用数据年龄区分重复使用、排队等待和传感器停更

在某次控制开始时刻 \(t_k\)，对消息记录原采样时刻 \(t_s\)、本机收到时刻 \(t_r\)、被本周期使用时刻 \(t_u\)。在时钟可比较的条件下，\(t_u-t_s\) 是采样数据年龄，\(t_u-t_r\) 是接收后等待时间；两者与 `controlLoop` 自身计算耗时不同。最新缓存只表示“最近收到的那份”，并不保证 \(t_u-t_s\) 小。

例如 CoM 名义 50 Hz、控制 100 Hz，两个相邻控制周期复用同一份 CoM 可以是正常现象；连续 500 ms 仍复用同一份，就需要停更检测。订阅队列为 1 能丢掉等待处理的旧消息，但无法给传感器重新采样。驱动取最新命令也只减少排队积压，不能检测根本没有新命令的断流。

IMU 滤波函数未复制 Header，可读原始缓存的时间戳；`Pose2D` 的 CoM 和 `Twist` 的目标消息无 Header，只能先保存本机接收时刻来判断“多久未收到”，无法从这些消息恢复准确采样时间。跨设备使用 Header 前还应确认时钟同步，否则负年龄或过大年龄可能来自时间基准错误。这些打点和拒绝过期数据属于建议验证工作，当前快照没有相应统计结果。

## 7. LQR 在 P1 中究竟做了什么？

这是面试最容易把两个项目事实混为一谈的地方。

### 7.1 它先做“简化模型上的分析”

分析脚本把一个平面方向的球形底盘/机身近似为倒立摆，状态为：

\[
\mathbf z=[x,\dot{x},\theta,\dot{\theta}]^{\mathsf T}
\]

连续线性模型是：

\[
\dot{\mathbf z}=A_c\mathbf z+B_c\tau
\]

其中 \(\tau\) 是模型中的等效输入力矩。模型在直立附近线性化，假设小倾角和简化接触/执行器关系；它没有把完整三轮、双臂所有动力学、打滑、消息延迟和电机饱和全部纳入状态。

LQR 选择反馈增益 K，使状态偏差与控制使用量的长期二次代价折中：

\[
J=\int_0^\infty \left(\mathbf z^{\mathsf T}Q\mathbf z+\tau^{\mathsf T}R_u\tau\right)dt,
\qquad \tau=-K\mathbf z
\]

加大倾角权重，模型设计会更重视压小倾角；加大输入权重，模型会更不愿使用大力矩。它给出的是模型和权重下的反馈方案，不会自动知道实机驱动限值、传感器延迟或接触状态。

### 7.2 当前脚本怎样用这组增益？

当前 linear_model.py 调用连续时间 LQR 接口，对 x/y 两个方向的线性模型分别求 Kx、Ky。配置的候选权重在 lqr_params.yaml，脚本还对部分增益手工缩放，再把状态反馈系数整理成类似位置/速度外环和姿态/角速度内环的 PID 形式打印出来。

当前配置文件中的对角状态权重列表为 Q=[200, 25, 800, 8]，单输入代价为 Ru=[0.5]；脚本把列表变成对角矩阵。四个状态的顺序是位置、速度、倾角、角速度。权重是分析偏好，不是机器人物理参数；也不能只看数值大小判断哪个变量“最重要”，因为各状态单位和尺度不同。

这使 LQR 能用于：

- 观察模型里位置、速度、倾角和角速度怎样耦合；
- 讨论 Q/R 改变时，控制器偏好和候选增益怎样改变；
- 给级联 PID 的增益调整提供一个模型化参照；
- 用模型解释为什么输入代价、执行器饱和和状态偏差需要一起看。

但脚本手动修改 K 后，增益不再是原 Q/R 对应的严格最优 LQR 解；“打印了 PID 形式增益”也不等于它已被写进最终实机配置。

### 7.3 实机每 10 ms 有没有执行 LQR？

在当前检查的运行节点中没有。实机 C++ controlLoop 调用的是 X/Y、Roll/Pitch/Yaw PID 对象，再经过 ik、缩放、限幅和驱动消息；代码中没有在线求解 Riccati，也没有看到该周期调用 tau=-Kz 的路径。

因此，面试可以诚实而有技术含量地说：

> 我在四状态线性化模型上使用 LQR 做分析，并用状态权重和控制代价理解候选反馈增益及其与级联 PID 调参的关系。当前检查到的实机闭环仍是位置—姿态级联 PID；我不会把离线 LQR 分析说成已经部署的在线 LQR。

简历/PS 中 “used LQR to understand…” 表达的是分析用途；不要把它缩写成“the robot was controlled by LQR”，除非另有实机运行证据。

<a id="timing-efficiency"></a>
## 8. 效率要拆成三种问题回答

“效率怎么样？”可能指计算机算不算得过来、机器人动作表现如何，或者能量消耗多少。它们需要不同证据。

| “效率”具体指 | 应看什么 | 当前能不能给实测结论 |
|---|---|---|
| 计算效率 | 每次控制计算耗时、CPU 使用率、内存/分配、最坏执行时间、deadline miss | 不能；当前没有性能日志 |
| 控制效果 | 倾角 RMS/峰值、速度和位置误差、超调、恢复时间、饱和占比 | 不能；当前材料无对应实测统计 |
| 能量/执行器负担 | 电流、电压、温升、力矩/速度峰值、同任务能耗 | 不能；没有同条件能耗数据 |

从计算结构上可作有限度的判断：当前周期有固定大小的 3×3 球轮矩阵乘法、若干标量 PID、低通更新和 ROS 消息操作；这类算术工作规模很小。四状态 LQR 若只是预先算好 K，每帧在线计算 -Kz 也是少量乘加，不需要在线反解 Riccati。

但“运算量看起来不大”不等于“已经证明实时可靠”。ROS 调度、消息队列、内存分配、日志、线程竞争、系统负载、CAN 发送和电机响应都会影响端到端时限。没有计时数据，就不能报“控制器每帧耗时 X ms”或“CPU 占用 Y%”。

<a id="timing-measure"></a>
## 9. 怎样实际回答 100 Hz 是否够、循环是否有效率？

### 9.1 先定义四个时间指标

1. **周期 T_k：**相邻两次控制周期开始时间差。目标约 10 ms；真实值要测。
2. **执行时间 C_k：**一次 controlLoop 从开始到发布命令所花时间。
3. **抖动：**周期相对名义 10 ms 的变化，例如 J_k=T_k-10 ms。
4. **端到端延迟：**传感器实际采样到对应命令发出/电机收到之间的时间。它不等于 controlLoop 执行时间。

面试中应回答测量分布，而不只报平均值：平均、P95/P99、最大周期和最大执行时间、超期次数、消息年龄、丢失/重复消息和 CPU 使用率都更有意义。平均 10 ms 仍可能掩盖偶发 40 ms 的大延迟。

### 9.2 记录哪些时间点？

可用单调时钟在控制计算路径打点：

- 控制回调开始；
- 读取 IMU、轮状态和 CoM 缓存；
- 每个 PID/前馈/矩阵分配完成；
- 限幅和命令滤波完成；
- ROS publish；
- 驱动回调收到消息；
- CAN 参数帧发送；
- 下一帧电机状态收到。

同时记录消息原始 Header 时间戳（有 Header 的消息）、本机接收时刻、控制器使用时刻、数据年龄、当前误差、原始输出、限幅后输出、驱动模式与 enable/fault 状态。跨设备对时不可靠时，不能直接拿两台机器的墙上时钟相减；应先建立共同时间基准或测单机单调时间区间。

### 9.3 100 Hz 应如何判断？

先知道机器人主要动态有多快、传感器和电机实际更新有多快，再确认控制器时限和延迟。采样频率要明显高于闭环需要处理的主要动态，但“把频率设得更高”不是自动变好：

- 传感器没更快，控制器只是反复读同一旧数据；
- 执行器/CAN 跟不上，会积累或丢弃命令；
- 固定 dt 和滤波系数若不一起更新，会造成计算时间尺度不一致；
- 更高频可能让未滤噪声更频繁进入控制，并增加 CPU/通信开销。

因此先用日志测实际回路，再判断提高或降低频率。没有这组测量，最稳妥的回答是“配置为 100 Hz，我会进一步测周期、抖动和传感器到命令延迟来验证它是否足够”，而不是声称 100 Hz 已经证明足够。

## 10. 若闭环不稳，按链路排查，不先盲目加增益

| 现象 | 优先检查 | 为什么 |
|---|---|---|
| 身体越纠越歪 | 轴符号、角度单位、IMU 安装方向、轮序 | 错方向的反馈会把误差推大 |
| 有时稳定、有时抖 | 控制周期分布、消息年龄、单线程回调阻塞 | 同一组 PID 增益在不同延迟下会表现不同 |
| 角度曲线平滑但反应慢 | 0.8 Hz 低通与输出滤波 | 过强滤波减少噪声，也增加反馈延迟 |
| 目标位置越走越偏 | 轮速偏差/打滑、固定 dt 积分、目标命令实际频率 | x/y 是积分状态，会累计偏差 |
| 调大 PID 后反而振荡 | 相位延迟、D 噪声、饱和、驱动模式和实际执行字段 | 增益不能修复过时反馈或错误执行模式 |
| 双臂动作时突然倾斜 | CoM 坐标参考、消息时效、前馈符号/比例、PID 剩余反馈 | 前馈模型与控制器使用的坐标/缩放可能不一致 |
| 发生跌倒后轮子行为不明确 | fall 分支、零命令、driver 缓存、驱动器超时 | reset 内部状态不等于电机收到安全停机指令 |
| CPU 平均占用低但仍超时 | 周期最大值、回调阻塞、日志/内存尖峰、CAN 时序 | 均值不能代表最坏情况 |

一次故障分析至少保留同一时间轴上的 IMU 姿态/角速度、轮速、CoM、目标和估计状态、PID 各项、限幅前后 action、publish/driver/CAN 时间以及 enable/fault 状态。没有这些信号，单看“机器人摇晃”很难区分模型、符号、滤波、延迟和执行器原因。

## 11. 控制效果实验应如何公平比较？

若要比较 PID、模型增益或是否加入 CoM 前馈，先固定条件，再比较输出：

1. 同一台机器人/同一模型、同一初始姿态、同一手臂轨迹；
2. 同一速度或位置目标、同一控制/传感器周期、同一安全限幅；
3. 只改变一个因素，例如 CoM 前馈开/关或两组增益；
4. 记录 roll/pitch RMS 与峰值、速度/位置误差、恢复时间、饱和时间比例、电流和周期抖动；
5. 重复多次，报告均值和波动，并保留失败试次。

若比较 LQR 和 PID，必须先保证输入含义与限幅一致。当前简化模型的 LQR 输入是等效力矩，而实机消息主要是轮速目标；若没有补齐并验证从模型力矩到电机命令的映射，就只能做模型内比较，不能说是在实机对比两个控制器。

## 12. 面试时的一分钟全链路回答

可以先用中文按这五句组织：

1. “我先读取 IMU 姿态和角速度、底盘轮速以及双臂关节状态；不同话题异步到达。”
2. “当前源码对角速度和轮反馈做低通，轮速经球体运动学换成水平速度，再积分得到相对位置；这个位置不是外部定位。”
3. “位置/速度外环生成有界的 Roll/Pitch 参考，姿态内环同时看角度误差和角速度，提前制动身体。”
4. “双臂 CoM 位置提供重力前馈；PID 与前馈的中间量经球轮矩阵、限幅和命令滤波，成为三轮速度目标，再由驱动节点送到 CAN 电机。”
5. “LQR 用于四状态线性模型的离线分析和增益理解；实机运行路径仍是级联 PID。100 Hz 与 10 Hz 是配置假设，我会用周期、抖动、数据年龄和端到端延迟日志来验证实际实时性。”
