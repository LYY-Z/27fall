<a id="p6-q01"></a>
## P6-Q01 平台软件解决什么？

**Question:** What problem does the device platform solve?

**中文理解与答法：** 统一设备能力、命令和反馈接口，让上层少依赖具体协议；设备差异不能全隐藏，单位时效错误仍需上层知道。

**白话拆解：**上层像点同一个菜单，适配器负责把菜单项变成不同设备听得懂的报文。统一的是调用入口，设备支持能力、单位、限位和回执语义仍须保留。


**English reference:** The platform provides common capability, command and feedback interfaces across devices. Hardware details remain in adapters, while units, freshness and errors must still be visible to callers.

**Follow-up:** Which differences should not be hidden by an abstraction?



<a id="p6-q02"></a>
## P6-Q02 能力模型是什么？

**Question:** What is a capability model?

**中文理解与答法：** 声明设备可执行动作、参数范围、反馈，和在线/授权不同；supports_move不代表现在可动。

**白话拆解：**能力是设备规格表，在线/健康是此刻状况，权限是当前用户能不能操作。设备规格支持 move，不代表它现在连着、没有故障或允许这个人移动。


**English reference:** A capability describes supported actions, parameters and feedback. It is distinct from current availability and authorization. Supporting an action does not imply that it is presently executable.

**Follow-up:** How would you represent an unavailable capability?



<a id="p6-q03"></a>
## P6-Q03 接口与实现有什么区别？

**Question:** Why separate an interface from its implementation?

**中文理解与答法：** 调用者依赖契约，具体设备类实现；便于替换和Mock，契约要输入输出错误与生命周期明确。

**白话拆解：**接口规定调用双方约好什么输入、输出和错误；类实现具体怎么做。换成 Mock 可在不接硬件时测试上层逻辑，但前提是 Mock 也遵守同一契约。


**English reference:** The caller depends on a contract, while a concrete adapter implements it. This supports substitution and mocks, provided inputs, outputs, errors and lifecycle behavior are explicit.

**Follow-up:** How could an implementation violate the contract?



<a id="p6-q04"></a>
## P6-Q04 虚析构为何需要？

**Question:** Why use a virtual destructor in a device interface?

**中文理解与答法：** 通过基类指针释放派生对象需正确析构派生资源，否则行为未定义；和普通虚函数用途不同。

**白话拆解：**基类指针只知道自己指向接口，却可能实际指向电机适配器。销毁时虚析构会继续执行具体派生对象清理；少了它，通过基类指针销毁派生对象属于未定义行为。


**English reference:** Deleting a derived object through a base pointer requires a virtual destructor for correct polymorphic destruction. Otherwise resource cleanup can be incorrect or undefined.

**Follow-up:** When would polymorphic deletion occur in this design?



<a id="p6-q05"></a>
## P6-Q05 RAII是什么？

**Question:** What is RAII?

**中文理解与答法：** 资源绑定对象生命期，构造获取析构释放；unique_ptr唯一拥有、lock_guard作用域锁；线程仍需stop/join设计。

**白话拆解：**文件、锁、线程池等资源由对象负责取得和释放，减少提前 return 时忘记清理的路径。RAII 不会自动决定线程何时停止，也不会替共享数据加锁。


**English reference:** RAII ties resource lifetime to object lifetime. Unique ownership and scoped locks simplify cleanup. Threads still need a deliberate stop-and-join policy before dependent state disappears.

**Follow-up:** Can a destructor safely wait forever?



<a id="p6-q06"></a>
## P6-Q06 unique_ptr为什么比裸指针清楚？

**Question:** What does unique_ptr express?

**中文理解与答法：** 唯一所有权，移动转移，析构释放；不自动保证线程安全，指向对象仍可竞争。

**白话拆解：**unique_ptr 表示只有一个对象负责销毁它；shared_ptr 用引用计数让多个使用者共同延长寿命。两者管“活多久”，mutex 管“能否同时改”，不能互相替代。


**English reference:** It expresses exclusive ownership and automatic destruction, with ownership transfer through move operations. It does not make access to the pointed-to object thread-safe.

**Follow-up:** When would shared_ptr be appropriate instead?



<a id="p6-q07"></a>
## P6-Q07 线程池做什么？

**Question:** Why use a thread pool?

**中文理解与答法：** 固定工作线程取队列任务，减少频繁建线程，控制并发；队列不设界会耗内存延迟，不能仅说更快。

**白话拆解：**线程池是固定数量的工人，任务队列是待办清单。线程数量限制同时干活的人数，但如果生产任务比处理任务快，队列仍会变长；需要容量和背压策略。


**English reference:** A pool reuses workers and controls concurrency. Queue capacity and backpressure matter because an unbounded queue can create growing latency and memory use.

**Follow-up:** What policy would you use when the queue is full?



<a id="p6-q08"></a>
## P6-Q08 优先任务一定准时吗？

**Question:** Does a high-priority task guarantee timely execution?

**中文理解与答法：** 队列优先只是取任务顺序，工作线程已有长任务不会自动抢占，OS调度也影响。

**白话拆解：**HIGH 只影响待取任务之间的选择。一个 worker 已经在等待设备回复时，队列优先级不会把它从阻塞调用里拉出来；另一个低优先任务甚至可能已经运行。


**English reference:** Queue priority affects selection of pending tasks. It does not automatically preempt a long task already running, and operating-system scheduling still matters.

**Follow-up:** How would you prevent starvation?



<a id="p6-q09"></a>
## P6-Q09 ExecCommand实际如何走？

**Question:** How does ExecCommand work in the available source?

**中文理解与答法：** 检查命令、查设备/通用处理器、提交HIGH任务、处理器捕异常、promise给结果、future.get等待。要知道等待是同步的。

**白话拆解：**源码顺序是参数检查、找设备专用处理函数、找通用处理函数、投到短任务线程池、设置 promise、调用方 get 等结果。函数内部用了线程池，但调用者仍等到任务返回。


**English reference:** It validates and looks up the handler, submits a high-priority task, captures the result or exception through a promise, and waits on the future. The caller is therefore still synchronously waiting for completion.

**Follow-up:** Where would you add a deadline?



<a id="p6-q10"></a>
## P6-Q10 异步提交为什么仍阻塞？

**Question:** Why can asynchronous submission still block the caller?

**中文理解与答法：** 提交异步只是任务另线程跑，随后future.get仍阻塞到结果；没有超时则设备卡住可挂等待。

**白话拆解：**异步描述工作在哪个线程跑；future.get 描述当前调用线程怎么取结果。工作可异步执行而调用方同步等待，没有 deadline 就可能一直等。


**English reference:** The work runs on another thread, but future.get waits for the result. Asynchronous execution does not imply a nonblocking caller, especially without a timeout.

**Follow-up:** What should happen when the handler never returns?



<a id="p6-q11"></a>
## P6-Q11 引用捕获有何风险？

**Question:** What is the risk of capturing references in a queued task?

**中文理解与答法：** 当前函数等待任务使局部仍活着；若加入超时返回而lambda还用引用，会悬空。参数值或共享任务状态需重新设计。

**白话拆解：**引用捕获没有复制数据，只保存原变量的地址。当前 get 等到任务结束，所以局部变量还在；一旦超时后函数先返回，后台任务可能继续访问已经销毁的变量。


**English reference:** The current wait keeps local variables alive until completion. If a timeout lets the function return while the task still holds references, those references can dangle. A deadline requires redesigning task-state ownership.

**Follow-up:** Would adding wait_for alone solve the problem?



<a id="p6-q12"></a>
## P6-Q12 锁为何保持短？

**Question:** Why keep critical sections short?

**中文理解与答法：** 锁内网络Connect/read阻塞使其他线程都等；复制句柄/状态后释放，再用连接级锁序列化IO，注意句柄寿命。

**白话拆解：**锁适合保护很短的共享表查找或状态复制。若拿着全局表锁等网络、串口或 PLC，其他设备也可能被堵住；连接本身是否还活着则要另有所有权保证。


**English reference:** Blocking network operations inside a shared lock can stall unrelated work. I would obtain a stable handle under a short lock, then use a connection-level mechanism for serialized I/O.

**Follow-up:** How would you keep the handle valid after releasing the lock?



<a id="p6-q13"></a>
## P6-Q13 怎样避免死锁？

**Question:** How would you prevent lock-order deadlocks?

**中文理解与答法：** 给锁统一顺序，减少嵌套，必要scoped_lock，禁止持锁等回调未知锁；源码需完整调用图而非看一个mutex。

**白话拆解：**死锁常见于线程甲先拿 A 再等 B、线程乙先拿 B 再等 A。统一锁顺序、减少嵌套，并避免持锁等待未来任务或回调，可以降低风险。


**English reference:** I would define a consistent lock order, minimize nesting and avoid waiting on callbacks while holding shared locks. Reviewing one mutex is insufficient; the full call graph matters.

**Follow-up:** How could shutdown interact with the lock order?



<a id="p6-q14"></a>
## P6-Q14 共享状态只加锁就够吗？

**Question:** Does a mutex guarantee valid shared state?

**中文理解与答法：** 互斥保证同一时刻不冲突，不保证读数新、语义一致或来源可信；需要序号时间戳版本。

**白话拆解：**互斥锁只说明读取期间没人同时改那块内存，并不说明值刚测到、字段属于同一时刻或消息来自正确设备。时间戳、序号、会话号和来源分别回答不同问题。


**English reference:** A mutex protects concurrent access, but it does not establish freshness, semantic consistency or trust. Sequence numbers, timestamps and state versions address different problems.

**Follow-up:** Can a locked read still return an obsolete value?



<a id="p6-q15"></a>
## P6-Q15 设备注册怎么幂等？

**Question:** How should repeated device registration behave?

**中文理解与答法：** 同ID同版本同能力可重复成功不创建重复资源；旧序号拒，新能力版本触发重新同步，重启会话区分。

**白话拆解：**重复注册同一设备不应重复创建资源，这是注册层的幂等。P6 教学 registry 展示序号和能力一致性检查；不要把它说成已在 M-DDS 生产注册链中部署。


**English reference:** Repeated registration should not create duplicate resources. Old versions should be rejected, and a capability change should trigger state synchronization. Device reboot may require a new session identity.

**Follow-up:** What if sequence numbers restart at zero?



<a id="p6-q16"></a>
## P6-Q16 反馈新鲜度怎么判断？

**Question:** How do you judge whether device feedback is fresh?

**中文理解与答法：** 时间戳与本时钟关系明确，now-sample<=TTL且不未来；同会话递增序号拒乱序；在线标志不等于数据新。

**白话拆解：**先用序号拒绝乱序，再用采样时间算年龄；二者互补。例：序号变大但样本早于当前 1.8 秒，TTL 为 1 秒时仍是过期状态。


**English reference:** I compare observation age against a defined lifetime and check sequence order within a known session. An online flag alone does not establish fresh feedback.

**Follow-up:** What changes when clocks are not synchronized?



<a id="p6-q17"></a>
## P6-Q17 发现、注册、同步区别？

**Question:** How do discovery, registration and synchronization differ?

**中文理解与答法：** 发现知道存在，注册建立ID能力关系，同步获取当前状态；发现成功不应立即凭旧缓存发动作。

**白话拆解：**发现是“看见设备线索”，注册是“把身份和能力放进软件名册”，同步是“确认这次连接下最新状态”。本地 BaseDeviceHandler::Init 接收 deviceId 并初始化 handler，不能替代未定位的专用发现实现。


**English reference:** Discovery finds a device, registration establishes identity and capabilities, and synchronization obtains current state. These are separate stages before normal commands should resume.

**Follow-up:** Which state would you use after reconnection?



<a id="p6-q18"></a>
## P6-Q18 幂等动作是什么意思？

**Question:** What does command idempotency mean?

**中文理解与答法：** 同动作ID重试不重复物理作用，需保存结果；不是同value永远不再执行，新的ID可新动作。

**白话拆解：**同一个动作 ID 重放应返回已有结果或安全拒绝，不重复叠加副作用；新 ID 表示新动作。若设备已执行但确认丢失，仅靠内存去重不能保证进程重启后恰好执行一次。


**English reference:** Retries with the same action identifier should not repeat the physical effect. A new identifier can represent a new action even if the value is unchanged. The result history needs a defined persistence policy.

**Follow-up:** Can you guarantee exactly-once execution after a crash?



<a id="p6-q19"></a>
## P6-Q19 ACK为什么不等于动作完成？

**Question:** Why is acknowledgement different from completion?

**中文理解与答法：** 可能只收到/入队，完成需设备状态或阶段回执；网络中断时结果未知不能盲重试有副作用动作。

**白话拆解：**ACK 可能只代表收到了报文或接受了任务。要证明设备已经到位，需要看协议定义的完成回执、后续状态读回或物理传感器，而不是只看一次函数返回。


**English reference:** An acknowledgement may confirm receipt or queueing rather than completion. Physical completion needs device feedback or a defined completion response. An interrupted connection can leave the outcome unknown.

**Follow-up:** How would you handle an unknown outcome safely?



<a id="p6-q20"></a>
## P6-Q20 Modbus适配做什么？

**Question:** What does the Modbus adapter translate?

**中文理解与答法：** 把抽象动作/读状态映射到功能码和寄存器。GroundLock 源码以 0x03 从地址 0 读 17 个寄存器，代码从 allData[7] 取状态并注释为地址 0x0006；0x06 用于写单寄存器。地址与数组下标的映射需要对照底层返回布局核实。

**白话拆解：**0x03 是读保持寄存器，0x06 是写单寄存器。GroundLock 读取 17 个 16 位寄存器，数据区是 34 字节；源码把状态取自 allData[7] 并注释为地址 0x0006，需核对底层数组布局。


**English reference:** It maps abstract operations to function codes and registers. The available GroundLock path reads registers using function 03 and writes using function 06. Register meaning and scaling still depend on the device specification.

**Follow-up:** What if the device returns an exception response?



<a id="p6-q21"></a>
## P6-Q21 协议校验要哪些？

**Question:** What protocol validation is needed?

**中文理解与答法：** 帧长地址功能码范围校验、CRC视具体封装、超时与重试；TCP无边界，不能以连接成功当命令成功。

**白话拆解：**串口 RTU 与 TCP 帧格式不同，TCP 还是字节流，需要按协议长度组帧。地址、功能码、长度、异常码、CRC/transaction ID 等检查要按具体传输层分别核对。


**English reference:** Validation depends on the transport and framing: lengths, addresses, function codes, ranges, checksums where applicable, timeouts and retries. A connection alone does not prove a successful command.

**Follow-up:** How would partial reads be handled?



<a id="p6-q22"></a>
## P6-Q22 关闭线程池怎么做？

**Question:** How should a thread pool shut down?

**中文理解与答法：** 设计上要拒绝新任务、规定队列任务是排空还是取消、唤醒并 join worker，再释放依赖资源。当前源码的 worker 外层受 isShutdown 控制，静态上看排队项不一定被处理；同一线程池对象再次 Init 前也要核对关闭标志是否复位。

**白话拆解：**安全关闭要停止接收新任务、唤醒 worker、定义队列任务怎么结束，再等线程退出。当前源码的 worker 外层受 isShutdown 控制，静态上不能推断队列里每个任务都会完成并唤醒 promise。


**English reference:** Shutdown should stop acceptance, define whether queued work is drained or cancelled, wake workers, join them and then release dependent resources. Reinitialization must reset relevant lifecycle state.

**Follow-up:** What if shutdown is called from a worker thread?



<a id="p6-q23"></a>
## P6-Q23 如何跨硬件可移植？

**Question:** How would you make device software portable?

**中文理解与答法：** 把协议、硬件、调度和业务分层，稳定契约与Mock，平台GN/SDK依赖单列；普通g++编译教学不是整个平台可构建证明。

**白话拆解：**接口能让业务逻辑少依赖设备协议，适配器仍需显式表达单位、能力、范围和停止行为。Mock 编译只检查教学程序，不能替代 OpenHarmony GN/SDK 的平台构建。


**English reference:** I would separate business logic, interfaces, protocol adapters and platform dependencies. Mocks support isolated learning, while GN and SDK requirements remain explicit for production builds.

**Follow-up:** Which module would you isolate first?



<a id="p6-q24"></a>
## P6-Q24 M-DDS证据在哪？

**Question:** How would you substantiate the M-DDS or M-Robots claim?

**中文理解与答法：** 现有查找未定位对应实现，不能用smart_farm代替；需历史仓库提交、模块路径、消息IDL/日志及本人变更。

**白话拆解：**面试中可以说明材料声称了什么、当前代码能证明什么、缺哪份历史证据。找不到对应源码时应说“本快照未定位”，不能用相似目录证明 M-DDS。


**English reference:** The named implementations have not been located in the current snapshot. I would retrieve the historical repository, commit, module paths and my changes instead of treating smart-farm code as equivalent evidence.

**Follow-up:** How would you explain that gap during an interview?



<a id="p6-q25"></a>
## P6-Q25 如何评价个人软件贡献？

**Question:** How would you evaluate your software contribution?

**中文理解与答法：** 具体接口或故障修复、选择理由、日志指标，延迟尾部分位/队列/恢复/重复执行率；无运行数据只说验证设计。

**白话拆解：**个人贡献要能落到本人负责的函数、变更、决策或调试记录。没有实测数据时可以讲验证方案和指标，但不能编造性能提升或把团队代码写成个人实现。


**English reference:** I would identify the exact interface or fix, explain the design decision and use evidence such as latency distributions, queue behavior, recovery and duplicate handling. Without measurements, I would describe the evaluation plan rather than a verified improvement.

**Follow-up:** What trade-off did your design introduce?

<a id="p6-q26"></a>
## P6-Q26 Init 后的 online 能证明设备在线吗？

**Question:** Does the online flag set during initialization prove that the device is reachable?

**中文理解与答法：** 不能。本地 BaseDeviceHandler::Init 在子类 OnInit 成功后调用 SetDeviceOnline；这是框架状态更新，不等同于刚收到设备心跳或一次成功读数。ReportProperty 在缓存 offline 时也可能先设 online 再上报属性，因此还要查在线状态由什么路径触发、数据最后何时采样。

## P6-Q33 被清掉的轮询任务，其取消标记会怎样？

**Question:** Are cancellation records removed when pending long tasks are cleared?

**中文理解与答法：** 当前快照的 `ClearPendingLongTasks` 会给待执行长任务的取消标记设为 true，再把任务从队列弹出；函数里没有删除 `taskCancelFlags_` 对应项。被弹出的任务不再由 worker 取出，因此也不会走 worker 里的常规 `erase` 清理。反复清除可能让这些标记留在 map 中，直到线程池对象销毁。静态代码支持“可能积累”的判断；要报告实际泄漏或增长量，仍需运行时记录 map 大小、清理次数和线程池生命周期。

**白话拆解：** 任务被扔掉了，但它的“取消标签”可能还放在登记簿里。每次只多一条未必立刻出故障；若不断发生又一直不删，登记簿就会长大。先说源码路径，再用计数验证规模。

**English reference:** In this snapshot, `ClearPendingLongTasks` marks queued tasks as cancelled and pops them, but it does not erase their entries from `taskCancelFlags_`.
