# 03 容器复杂度与数据结构

先修：[02_结构体类RAII与接口](02_结构体类RAII与接口.md)。项目：P5、P6。实验：[数据结构与状态同步](../../03_代码实验/01_基础实验/03_数据结构与状态同步/README.md)。

## 1. 为什么数据结构影响控制周期

一轮控制只有有限时间。需要最新反馈可以保存一个快照；需要按顺序消费命令可用队列；需要找最小代价的搜索节点可用优先队列。选容器先问访问方式，而非背“某容器最快”。

|结构|典型用途|典型复杂度与条件|
|---|---|---|
|连续数组/vector|关节向量、图像|索引O(1)，中间插入O(n)|
|队列/deque|待处理消息|两端操作通常O(1)|
|堆/priority_queue|最低代价节点|取顶部O(1)，入堆/出堆O(log n)|
|哈希表|设备ID查找|平均O(1)，最坏可O(n)|
|平衡树/map|有序设备表|查找/插入O(log n)|

vector扩容会分配更大内存并搬移数据，可能使旧指针和迭代器失效。实时回路通常预留容量、固定最大消息量，减少不可预测分配。复杂度是输入规模增长的关系，不是一次运行的毫秒数。

## 2. 完整手算：寻找下一个节点

未处理节点代价[7,2,9,4]，每次线性扫描需比较约3次才能找2。1000节点每次扫描约999比较；若重复1000次约100万比较。堆入/出操作高度约log₂1000≈10层，1000次操作约万级层数比较，实际常数和内存访问也影响时间。

不能由这个数量级直接宣布“实机快100倍”：需要同一数据、编译选项和硬件的实测。

## 3. 新反馈应排队还是覆盖

电机反馈1000Hz，消费者100Hz，每次只处理一条，积压每秒900条。5秒4500条，消费者读的是过去状态。若控制只需最新快照，可覆盖旧状态；若必须记录每条数据，独立日志队列、容量和溢出策略要明确。

命令不能随便覆盖：急停、模式切换和事务可能需可靠顺序。队列上限需要丢旧/丢新/拒绝/停止的具体策略。环形缓冲区由固定数组和读写索引实现，也需要正确同步。

## 4. 项目与代码

P5搜索开放集使用优先队列；P6设备注册表适合按ID查找；P3/P7控制读取反馈需时效。实验`shortest_path`用heapq，`accept_feedback`决定快照是否可更新。

## 5. 常见失败

无界队列让系统越跑延迟越大；vector扩容后继续使用旧指针可能崩溃；把平均O(1)当最坏延迟保证会忽视碰撞和分配。先记录队列长度、消息年龄、最大耗时，再定位。

## 6. 英文与练习

“The data structure should match the access pattern. A priority queue supports graph search, while a latest-state snapshot avoids processing a long backlog of stale feedback.”

追问：Why can a fast average operation be unsuitable for a real-time loop? Its worst-case latency may still exceed the deadline.

1. 概念：复杂度O(n)表示固定时间吗？答：表示随规模线性增长。
2. 计算：输入500Hz、消费200Hz，2s积压？答：600条，不计启动/丢弃。
3. 代码：搜索中每次用`min(list)`是否合理？答：小图可读性好，大图优先队列更合适；修改后要测耗时。
4. 解释：丢弃旧传感器数据合理吗？答：控制需最新时可能合理，但记录任务/积分算法需另设计，不能无条件丢弃。

## 精读补充：把中间步骤讲清楚

### A. 队列长度与消息年龄怎么联系？

生产100 Hz、消费50 Hz，每秒积压50条。持续2 s后约100条；消费者每秒只能处理50，队尾相对于最新消息会越来越旧。平均处理时间很短也不保证读到当前状态，要记录队列长度与每条数据的年龄。

最新状态缓存只存一帧，能避免控制读取积压；完整日志另用独立通道。若算法需要对所有轮增量积分，直接丢帧需要确认新帧是否含累计位置：累计角度可算跨越的总增量，单帧瞬时速度不能无条件重建所有丢失运动。

### B. priority_queue为什么允许同一节点重复？

图搜索中先把C成本5入堆，后来发现成本3。常见实现再放一条C=3，不在堆中复杂修改旧条。弹出C=5时比较当前best_cost=3，发现旧条就跳过。堆记录是“待处理候选”，距离表才是该节点目前最优值。

### C. 固定容量也要写溢出行为

容量3，已有序号1、2、3，再来4。丢旧策略保留2、3、4；丢新保留1、2、3；拒绝策略通知发送者；阻塞策略使生产者等待。没有一种对所有控制/日志/动作任务都正确，必须按消息是否可替换选择。
