# P6 故障诊断与量化方法

## 1. 先画分层路径，再按证据定位

一次设备动作可拆成这条路径：

```text
调用方请求
  → 参数/设备/能力检查
  → 任务队列与 worker
  → handler 业务处理
  → adapter 编码与通信
  → 设备收到并处理
  → ACK 或设备状态读回
  → 平台缓存/属性上报
  → 调用方或界面看到结果
```

“没有动作”只描述结果，不指出故障位置。应从请求 ID 开始，把同一个请求关联到每一层日志。每一层都记录进入、离开、结果码和耗时，找出最早出现的缺失或异常。

本文列出的是调查方法，不代表下面所有问题都已在真实设备上复现。源码静态风险、教学故障注入、实机现象要分开记录。

## 2. 现象 → 先查什么 → 什么证据能区分原因

| 现象 | 先查 | 能区分原因的字段/证据 |
|---|---|---|
| 调用方一直等不返回 | `ExecCommand` 的 future 是否完成；任务是否进队列；worker 是否卡在 handler/I/O | `action_id`、enqueue/start/end、worker ID、promise 完成、caller return 时间 |
| 命令排队很久 | worker 数、队列长度、同池阻塞任务、锁等待 | 入队时间、开始时间、队列深度、优先级、队首任务年龄 |
| HIGH 命令仍然慢 | 是否已有不可抢占的 handler/设备 I/O；是否争同一连接锁 | 当前执行 task ID、连接锁等待时长、I/O timeout、优先级选择记录 |
| 周期状态偶尔不更新 | scheduler 是否到期、是否提交长任务、任务是否被短任务清除/跳过 | planned time、submit/take/start/end、skip/cancel reason、下个 `nextRunTime` |
| 状态有数值但并非新读数 | 读取返回码、缓存来源、采样年龄 | `read_return_code`、last_success_sample_time、cache_source、feedback_age_ms |
| 状态跳回旧值 | 序号、采样时间、设备重启会话、并发更新顺序 | device/session ID、sequence、sample timestamp、接收时间、拒绝原因 |
| 写地锁后界面显示到位，机械却没动 | 写回执、缓存更新、后续读回和真实位置传感器是否被混为一谈 | register/value、write result、cached source、readback value/time、limit sensor |
| 读地锁失败但输出参数有值 | 调用方是否忽略非成功返回码，输出是否是旧缓存 | function return code、status source、last successful read time |
| 设备断线后重发造成重复动作 | 首次是否已执行但 ACK 丢失；重试 ID 是否相同；设备侧是否去重 | action ID、attempt number、ACK、设备状态变化、去重记录持久性 |
| 一个设备变慢拖累其他设备 | 是否共享同一连接、全局锁、worker 或同步回调 | connection key、锁等待、worker占用、各设备队列/延迟分布 |
| 关闭后调用方永远等结果 | 队列任务是否被清除/留下 promise；等待方是否有退出策略 | shutdown 时间、未处理队列数、promise/future 状态、caller timeout |
| 长期运行内存持续增加 | 短任务是否反复清理长队列、任务取消标记是否被删除 | `taskCancelFlags_` 大小、ClearPendingLongTasks 次数、池对象寿命、进程内存 |
| OpenHarmony 组件普通 g++ 编译失败 | 是源代码语法问题，还是 SDK/GN/module 依赖缺失 | target、GN 配置、SDK版本、缺失头文件/库、构建日志 |

## 3. P6 源码中的几个具体核对点

### 3.1 等待时间不是执行时间

把时间戳都放在同一单调时钟上：

```text
t0 request_created
  t1 enqueued
    t2 worker_started
      t3 handler_started
        t4 protocol_begin
        t5 protocol_end
      t6 handler_finished
    t7 promise_ready
  t8 caller_returned
  t9 physical_state_confirmed (若设备提供)
```

- 排队时间：`t2 - t1`。
- handler时间：`t6 - t3`。
- 协议时间：`t5 - t4`。
- 软件端到端返回时间：`t8 - t0`。
- 物理动作确认时间：`t9 - t0`，只有确实有独立状态反馈时才可计算。

若只能看到 `future.get()` 返回，最多说明软件 handler 返回了结果；不能据此填“地锁实际升起耗时”。

### 3.2 轮询配置周期与实际采样间隔

按设备记录：`scheduled_due`、scheduler检查时间、入长任务队列时间、worker开始时间、读取完成时间、成功状态接收时间、skip/cancel 原因。实际采样间隔应从**两次成功采样时间**相减；配置里的 interval 是调度参数，不是实测值。

源码有短任务和长任务两类 worker。短任务开始时可能清除队列中的长任务；长任务 worker 也可能在开始前跳过任务。scheduler 推进 `nextRunTime` 后，这一次跳过不保证立即补发。因此日志要区分“没有到期”“未提交”“队列中取消”“worker跳过”“协议失败”。

### 3.3 缓存年龄与旧帧

建议把每份状态同时保存：设备 ID、启动会话、sequence、设备采样时间、平台接收时间、值、单位、有效性和最后成功读数时间。sequence 用来判断顺序，timestamp 用来判断年龄；二者不能互相替代。若设备时钟不可信，可以用平台接收时间估算通信后年龄，但不能把接收时间说成设备采样时间。

### 3.4 地锁状态分阶段记录

地锁路径至少区分：动作通过业务 handler、Modbus 请求写出、协议层返回、软件缓存更新、后续读寄存器、限位/位置传感器确认。`WriteLockCommand` 的缓存更新不是独立传感器读回。读失败时即使输出参数里有旧 `currentStatus`，仍须看函数错误码和最后成功读数时间。

协议地址与数组下标也要分别记录。当前 handler 从地址 0 读 17 个寄存器、使用 `allData[7]` 并注释对应 0x0006；最终判定需核对 Modbus service 返回 vector 的布局和设备寄存器表。

### 3.5 关闭与取消记录

`ThreadPoolManager::Shutdown` 会设关闭标志、唤醒并 join worker。静态阅读不能推出所有队列任务都运行完，也不能保证每个调用方拿到结果。另一个细节是 `ClearPendingLongTasks` 对被弹出任务设置取消标志，但该路径没有删除 `taskCancelFlags_` 条目；被弹出的任务不会再走 worker 常规清理。要判断是否造成持续增长，应观察 map 大小、清理次数、池重建/销毁及进程内存曲线。

## 4. 量化指标：写清分子、分母和终点

| 指标 | 计算 | 必须说明 |
|---|---|---|
| 命令排队延迟 | `worker_start - enqueue_time` | 单位 ms；成功/失败任务是否都计入 |
| handler耗时 | `handler_end - handler_start` | 是否包括协议I/O、锁等待或重试 |
| 软件端到端延迟 | `caller_return - request_created` | 完成终点是返回码、ACK 还是读回 |
| 反馈年龄 | `now - sample_time` | 设备时间还是接收时间；设备时钟是否同步 |
| 任务跳过率 | skip/cancel count ÷ 到期轮询次数 | 区分短任务清除、worker跳过、资源失败 |
| 协议成功率 | 成功协议事务 ÷ 总事务 | 事务定义、重试是否作为单独样本 |
| 超时率 | timeout count ÷ submitted request count | 期限、超时是否取消后台任务 |
| 动作完成率 | 有独立完成证据的动作数 ÷ 已接受动作数 | “完成”来自何种传感器或设备协议 |
| 恢复时间 | 首次确认断线到收到新鲜状态 | 不能只用 socket 重连时间 |
| 取消标记存量 | 采样时 `taskCancelFlags_` 中条目数 | 同时记录池年龄与清队列次数，排除对象重建 |

延迟报告建议给样本数、中位数、P95/P99、最大值和失败样本；平均数可能掩盖长尾。每个百分位数都要说明采样窗口和排除规则。没有原始日志就把它写成“拟测指标”，不要放进简历当结果。

## 5. 一个排查示范：调用方等不到地锁结果

按以下顺序检查，找到第一个缺失点就先停在那里：

1. **请求层：** `action_id` 是否存在，deviceId/cmd 是否为空或未注册？记录 handler 返回码。
2. **队列层：** 是否 enqueue？多久后 worker 开始？队列是否不断增长？
3. **执行层：** GroundLock handler 是否进入 `Up`/`Down`？解析设备端口是否成功？
4. **协议层：** RTU 的地址、功能码、寄存器和值是什么？事务返回码是否成功？
5. **结果层：** promise 是否 set，调用方是否从 `future.get()` 返回？
6. **反馈层：** 缓存是否因 write 被直接更新？是否有后续读回？读数年龄和错误码是多少？
7. **物理层：** 独立限位/位置反馈是否确认到位？若没有，只能报告协议/软件阶段的结果。

建议同一日志上下文使用 `device_id + action_id + task_id` 关联。不要只看一行“success”，否则可能把协议成功、缓存目标和真实机械位置混在一起。

## 6. 复盘模板

每个故障或实验写一页：

| 项 | 要记录什么 |
|---|---|
| 环境 | 代码版本/commit、设备和固件、配置、运行环境 |
| 初始状态 | device/session、online来源、最后成功采样时间、队列长度 |
| 输入 | action/device ID、命令、参数和单位、提交时间 |
| 观察 | 逐阶段时间戳、返回码、协议数据、状态回报 |
| 对照 | 正常基线、失败注入、变化的单一条件 |
| 结论 | 静态源码事实、教学实验观察、真实设备证据分别写 |
| 限制 | 还未验证的版本、物理行为、异常路径和个人贡献边界 |

## 读取失败在上层被掩盖的具体路径

当前ReadLockStatus失败可输出旧缓存，但ListeningTask在非OK分支没有立即返回（return被注释），继续缓存更新与ReportPropertyImpl。上报成功可能让最终返回变成OK，并触发基类online更新。因此检查应包括read_ret、report_ret、poll_ret和last_success_read_time，而不是只看上报成功或online。详见[协议章第7节](../01_原理与子系统/04_协议适配发现注册与状态同步.md)。
