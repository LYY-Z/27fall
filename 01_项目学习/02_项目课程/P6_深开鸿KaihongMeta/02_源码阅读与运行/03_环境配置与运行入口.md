# 环境配置与运行入口

## 1. 先分清两种“运行”

P6 有两条性质不同的运行路径：

| 路径 | 内容 | 需要什么 | 能证明什么 |
|---|---|---|---|
| 普通电脑教学实验 | Python 合成数据、C++ MockAdapter | Python 标准库；C++17 编译器 | 只能验证教学模型与程序分支，不证明真实设备或 KaihongMeta 平台运行 |
| 原始 OpenHarmony 组件 | ThingAccessManager、Modbus/SoftBus/MQTT/PLC 等组件 | 匹配的 OpenHarmony SDK、GN 构建环境、平台依赖、对应设备/服务 | 在正确版本上完成构建与设备验证后，才支持相应运行结论 |

本目录只记录可复现的入口和边界。本轮没有运行教学脚本或编译源码，因此下面的输出描述是依据代码静态推演的预期，不是实测日志。

## 2. 教学实验需要的环境

- Python：推荐 Python 3.10 或更高版本。两个 Python 脚本只使用 Python 标准库，不需要 NumPy 或 SciPy。
- C++：需要支持 C++17、std::filesystem 和线程库的 g++ 或兼容编译器。
- 输入：脚本内置的人工构造设备、命令和反馈，不读取真实传感器或网络。
- 输出：通过 --out-dir 指定的目录；CSV 中是教学状态和模拟结果。

详细步骤、命令和预期字段见 [P6 普通电脑教学实验](../../../03_代码实验/02_项目实验/P6/README.md)。先读 [逐函数阅读指南](../../../03_代码实验/02_项目实验/P6/逐函数阅读指南.md)，了解每项输入怎样变成输出。

## 3. PowerShell 入口

先打开 PowerShell，将工作目录切到申请材料目录，再运行脚本。以下命令只创建 P6 教学输出目录，不触碰原始源码：

~~~powershell
Set-Location -LiteralPath "F:/27fall/申请材料"
python "./01_项目学习/03_代码实验/02_项目实验/P6/capability_dispatch.py" --out-dir "./01_项目学习/05_实验与学习记录/输出/P6/capability_dispatch"
python "./01_项目学习/03_代码实验/02_项目实验/P6/freshness_recovery.py" --out-dir "./01_项目学习/05_实验与学习记录/输出/P6/freshness_recovery"
g++ -std=c++17 -Wall -Wextra -pthread "./01_项目学习/03_代码实验/02_项目实验/P6/device_adapter.cpp" -o "./device_adapter_demo.exe"
& "./device_adapter_demo.exe" --out-dir "./p6_cpp_output"
~~~

这些命令在本轮没有执行。若命令失败，先看报错属于“解释器/编译器未安装”“当前目录错误”“权限/路径错误”还是“源码编译错误”，不要通过改原始平台代码来掩盖环境问题。

## 4. Bash / WSL 入口

WSL 中可把 Windows 的 F 盘路径写成 /mnt/f/27fall/申请材料。实际挂载位置若不同，应先确认文件存在：

~~~bash
cd "/mnt/f/27fall/申请材料"
python "./01_项目学习/03_代码实验/02_项目实验/P6/capability_dispatch.py" --out-dir "./01_项目学习/05_实验与学习记录/输出/P6/capability_dispatch"
python "./01_项目学习/03_代码实验/02_项目实验/P6/freshness_recovery.py" --out-dir "./01_项目学习/05_实验与学习记录/输出/P6/freshness_recovery"
g++ -std=c++17 -Wall -Wextra -pthread "./01_项目学习/03_代码实验/02_项目实验/P6/device_adapter.cpp" -o "./device_adapter_demo"
./device_adapter_demo --out-dir "./p6_cpp_output"
~~~

如果 Python 命令实际指向了其他解释器，先用 python --version 和 where.exe python（PowerShell）或 command -v python（Bash）确认路径。若 g++ 找不到 std::filesystem，确认编译器支持 C++17；较旧版本可能还需单独链接 filesystem 库。

## 5. 原始 OpenHarmony 组件为什么不能直接用普通 g++ 编译

原组件使用 GN 构建配置，并依赖 OpenHarmony 平台头文件、ThingAccessManager / ThingModelFwk 等组件，以及 Modbus、SoftBus、MQTT、Snap7 等接口或外部库。普通 Windows/Linux g++ 不能替代这些平台 SDK。即使单独编译一个纯 C++ Mock，也不能证明原组件构建成功。

要重现真实平台构建，先固定：源码提交和 SHA、OpenHarmony SDK/系统版本、GN/Ninja 版本、组件依赖版本、目标架构、配置文件、设备连接方式和构建日志。之后再按 [源码文件地图](01_源码版本与文件地图.md)检查目标是否实际包含所读组件。

## 6. 怎样记实验结果

每次只改一个输入条件，并记录：

1. 源码版本/提交或文件 SHA，解释器或编译器版本，完整命令。
2. 输入设备 ID、动作 ID、能力、序号、采样时间、当前时间、单位。
3. 预期状态与实际状态，输出 CSV 路径，错误码/异常。
4. 这次结果能说明哪个软件阶段；不能说明的部分也写清楚。

例如，教学脚本返回 executed 只说明合成 registry 接受了教学动作；它不证明真实设备收到命令。真实设备若只看到协议写入成功，还需另记设备 ACK、后续状态读回和物理传感器确认。

## 7. 运行前的自查

- [ ] 当前路径下确实存在 P6 教学脚本或目标源码文件。
- [ ] 本次选择的是教学 Mock 还是原始平台构建，结论范围不会混用。
- [ ] Python 脚本没有被误认为会连接网络或设备。
- [ ] 输出目录与原始源码目录分开。
- [ ] 预期输出和实测输出分开记录；未运行时不填写为“通过”。
