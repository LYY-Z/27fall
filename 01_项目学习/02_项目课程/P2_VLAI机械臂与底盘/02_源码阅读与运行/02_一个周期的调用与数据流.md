# 一个周期的调用与数据流：逐步精读


> **先读白话总览：**读这页前先看[三条项目线的全貌](../00_项目全貌与学习路线/03_P2端到端流程与面试地图.md)：VR仿真、主从机械臂、底盘分别选一条，不要把三条拼成同一个闭环。你可以把“一周期”理解成一次完整接力：采样输入→准备目标→计算下一小步→发给仿真或设备→接收下一轮反馈。下面的代码细节只属于对应分支。

## 0. 本章读完应能画出的三条链

本副本包含VR遥操作、主从力反馈、两轮底盘三条分支。它们共用机器人主题，但不是由一个已确认入口自动启动的完整部署。先选一条链逐步读，再比较接口。[源码地图](01_源码版本与文件地图.md)固定文件SHA；[运行入口](03_环境配置与运行入口.md)说明环境边界。

## 1. VR目标首先是什么量

手柄位置是3个数、姿态是4个四元数分量；机器人末端目标则是位置3维与旋转矩阵3×3，最后拼成4×4 SE3。位置通常用m，角度用rad，四元数无单位。MuJoCo的wxyz与SciPy常用xyzw需要显式重排。不要把姿态四个数当4个关节角。

## 2. 按键定义一次相对操作的起点

`_compute_ik_targets`只处理有control_trigger的配置。grip>0.9激活，首次保存当前末端和手柄参考；之后使用手柄相对参考的增量。松开清除参考，下次从新的末端起点开始。这样手柄的房间绝对位置不需要直接等于机器人的工作空间位置。

假设机器人末端起点[.3,.2,.5]m，经过轴转换后的手柄位移[.05,−.02,0]，位置目标[.35,.18,.5]。这不是把世界原点搬过去，而是把同一次操作的增量加到末端起点。

## 3. 轴转换、滤波和姿态增量

`_process_xr_pose`负责输入坐标处理、参考与增量，`geometry.py`负责旋转组合。要追每个R的方向和乘法顺序，不能只读变量名。位置低通α给新样本；四元数分量加权后归一化是nlerp式处理，不自动等于SLERP。若相邻q和−q未统一半球，加权可能接近0，必须识别这个风险；此处不擅自改原始项目。

坐标专章统一 R_AB 把 B 向量映到 A，教学世界轴 C=R_BW，局部映射另记 C_E0H0。源码的 R_HEADSET_TO_WORLD 是固定原始 XR 轴转换，不是已测得房间到基座 C 的证据。矩阵列与左右乘推导见[坐标专章第1、3、5节](../01_原理与子系统/01_VR相对位姿与坐标标定.md)。

## 4. 两种末端控制模式

position模式只改变位置，保持首次参考姿态；另一路把位置和旋转增量一起应用。保存旧姿态不等于姿态永远世界单位阵。单次目标不存在时跳过该臂，不等于设备主动断使能。

## 5. 构造Mink任务

当前q复制到configuration；PostureTask的目标设置为本周期当前q；有left/right目标就添加相应FrameTask。独立求解器默认位置cost1、姿态cost.5、posturecost.01、lm_damping=.05、dt=1/200s。权重是设计设置，不是测得跟踪性能。

Posture目标每步跟随当前配置，抑制本次无必要变化；不能说它在全程拉回一个固定“home姿态”。

## 6. QP求解输出的是关节速度

`mink.solve_ik(configuration,tasks,dt,solver)`返回vel，形状应与模型速度自由度匹配。它通过任务误差、雅可比和权重求局部动作，不是解析一次就到达目标。关节位置qpos与速度nv在含自由/球关节模型时长度可能不同，应使用库积分而不是无条件向量相加。

2026-10-12 核验当前上游 main：内部 build_ik 的 QP 决策变量是切空间 Δq，solve_ik 将解除以 dt 返回 vel；项目再以 vel、dt 调 integrate_inplace，得到下一配置。内部小步和外部速度不能混称，更不能在应用层再除一次 dt。Mink 通过 MuJoCo API 取几何 J、换到任务坐标，再配合 SE(3) Log 的误差导数；任务 J 不必逐数字等于世界几何 J。详细来源见[MuJoCo/Mink专章第5–6节](../01_原理与子系统/02_MuJoCoMink任务约束与求解.md)。历史安装版本未锁定，此核验不代表当时内部实现已确认。

调用未显式列出全部limits；默认限位行为依安装Mink版本与模型。lm_damping不证明已有碰撞约束或速度/力矩保护；部署需读库版本和硬件接口。

FrameTask.lm_damping 是任务特有 LM 的配置；当前上游可同时在 Hessian 加全局 damping 和各任务误差相关 LM，不能把“教学全局项写一次”当成库只支持一种阻尼。详见[阻尼章第3.2节](../01_原理与子系统/03_奇异阻尼限位与异常保持.md)。

## 7. 积分与两份求解器的区别

独立`XarmIKSolver.solve_step`积分configuration后，可同时写data.qpos和data.ctrl并mj_forward，是运动学式状态更新。主遥操作`_solve_and_apply_ik`只把结果写到ctrl，物理模拟随后推进。不能把前者的“q已直接更新”当成后者“电机已经跟踪”。

仅转动关节教学例：q=[.1,.2]rad、vel=[.4,−.2]rad/s、dt=.005，q_next=[.102,.199]。真实模型用对应积分器；200Hz是配置，不是实测频率。

### 7.1 从状态到命令的接力表

| 阶段 | 得到什么量 | 谁消费 |
|---|---|---|
| 读 qpos/编码器 | 当前配置 q，按模型顺序 | FK 与 Configuration |
| FK/关节链递推 | 当前 TCP 的 R/p、轴心 O 与轴向 a | 误差与几何 J 计算 |
| 目标比较 | 世界教学位置差/轴角，或库的局部 SE(3) 残差 | 任务求解 |
| QP/solve_ik | 当前上游内部 Δq、对外 vel=Δq/dt | 配置积分 |
| integrate_inplace | 下一参考配置 q_next | ctrl 或硬件命令映射 |
| position actuator/实机驱动 | 尝试跟踪参考 | 物理仿真/机器人机构 |
| 新反馈 | 实际 q/qdot，而非刚才的参考 | 下一轮重新 FK |

主脚本意图加载 openarm/scene.xml，包含 openarm/openarm_bimanual.xml 的活动 position actuator；assets/openarm 的 motor 副本不能混用。ctrl 的单位取决于实际模型。mj_forward 只刷新派生量，mj_step 才推进物理时间。保存的 Python 主入口 xml_path 行尾有异常文本（zhe'l），当前说明是静态阅读的意图路径，未运行确认。

### 7.2 四种周期与实机三种接口

独立求解器 dt=5 ms、主类 RateLimiter=200 Hz 是配置。仿真物理 h 取 model.opt.timestep 与每轮步进次数，源码未见二者自动绑定；XR 数据间隔、墙钟循环耗时、电机内环周期也另算。不能把附件里“MuJoCo 步也5 ms”作为项目事实。

位置模式发送积分后的 q_next；速度模式可以发送 qdot；力矩模式还需控制器用状态、参考和动力学求 tau。IK 不直接求电机电流或力矩。ROS 发布关节数组后，仍需确认订阅节点、顺序、单位、驱动模式、超时以及真实编码器如何反馈给计算链。

## 8. 失败与收敛

独立solve_step捕获QP异常返回当前q；主遥操作捕获异常后不写新ctrl。旧ctrl可能继续被使用，不能说异常已让硬件停机。`solve_until_converged`先检查Δq，再检查位置mm和姿态degree误差；Δq很小可以是停滞，不能单独当目标已到达。

## 9. 主从链的状态从哪来

主从路径每一轮都先从电机状态读位置/速度，再用 `motor_to_joint` 换成关节坐标。编码器零位、正方向、减速比和关节顺序必须与模型一致。随后分成两路：

- **Leader 路：**用当前 Leader 关节位置 `q` 和 URDF/KDL 算重力项 `g(q)`；
- **Follower 路：**读取位置/速度参考，通过 `joint_to_motor` 换成从臂电机目标。

两臂的物理安装、零位和方向不能靠变量名相同来保证一致；主臂第 i 个关节数组元素不能未经映射就当作从臂第 i 个电机目标。

## 10. 重力补偿和MIT字段

重力补偿 `g(q)` 是当前姿势下支撑手臂重量所需的关节力矩，不是末端速度或关节位置。该 Leader 分支把 `gravity_comp_ratio × g(q)` 写入力矩字段，并把位置、速度、Kp、Kd 设为零。该 Follower 分支把映射后的目标位置、目标速度、Kp、Kd 发给电机，前馈力矩字段设为零。字段零不代表实际电机力矩为零：电机的位置/速度反馈控制仍会为跟踪目标产生作用。参数数值和单位缩放要以实际驱动协议为准。

这条链可以概括为：反馈电机状态 → 转成关节状态 → Leader 算重力矩 / Follower 算电机目标 → 分别发 MIT 命令 → 读取下一轮反馈。KDL 计算耗时、实测周期、消息年龄和控制抖动需要日志或测量；一般经验值不能替代本项目性能数据。

KDL文件有SVD/NullSpace代码但该相关路径未启用，不能据此说当前在线控制已用安全阻尼零空间。活动的求逆/限位也必须按实际分支检查。

上述 Leader/Follower 具体对应所读 unilateral_step：该函数计算了 Coriolis 和摩擦，但手臂 effort 的活动赋值只采用 ratio×gravity，混合赋值被注释；夹爪另有0.3×friction。函数存在、函数被调用、结果被写入命令是三层证据，不能合并。另一控制 step 是否部署要追入口。

## 11. 底盘当前任务顺序

`chassis_task`：选PROTECT/REMOTER/AUTO的Control_Fun→分配/发送→里程计→msg_to_Host→task_delay(3)。该目录使用EZ_RTOS和相应H723平台，不能套另一目录FreeRTOS/F407配置。delay3不是实测周期。

## 12. 底盘的实际分配手算

`mini_car_calc(vy,vw)`当前写speed=[4(vy+vw),4(vy−vw)]；再wheel_ref=[1.5speed0,−1.5speed1]。输入vy=10,vw=2，得到[48,32]再[72,−48]，转int16后MotoSetSpeed。

这是一份代码尺度手算，vy/vw的物理量及speed_pos=4、1.5必须按上位/驱动标定，不能把公式直接称标准m/s差速模型。源码板端pid_calc被注释，speed_send直接等wheel_ref；不能说该任务运行了板端轮速PID。

## 13. 超时为何存在逻辑缺口

AUTO检测host_online>5000，但自增只在<5000发生，若无其他修改，恰好5000时停止增长，>条件无法触发。这是读代码发现的边界问题，不是运行复现。tx_data[8]未初始化就发送，内容也不能当有效速度包。原始源码保留，运行文档列为先修复项。

## 14. 里程计不能仅看变量名

当前ds从moto.speed×固定ratio来，5ms触发；随后按自己的轴/角符号odom_update。变量叫速度不证明其乘ratio后已是位移；dt和编码器字段必须核对。注释称中点，但先更新z又减dtheta/2的实际顺序应逐项检查，不能照抄注释给精度保证。

## 15. 一份可读日志

VR：原始pose、转换pose、trigger、参考pose、target、q、vel、dt、QP状态、ctrl。主从：motor状态、joint状态、g(q)、MIT五字段。底盘：mode、host_online、vy/vw、wheel_ref、speed_send、反馈与里程计时间。不同链不要混用同一个cycle_id假装同步。

## 18. 白板与故障自测

1. q和vel单位？rad与rad/s，积分用s。
2. QP成功是否目标已到？否，检查FK位置/姿态误差。
3. ctrl与qpos？控制目标与模拟状态，依模型不同。
4. 当前Posture是否固定home？否，每步设当前q。
5. 同个位置单位为什么仍要改轴？参考系不同。
6. 关节目标不动先看哪里？trigger、目标、QP状态、下游使能/旧ctrl。
7. 底盘PID有初始化就代表执行？否，读活动调用。
8. host计数到5000会怎样？当前条件可能卡在边界。
9. g(q)与J⁺目标速度同义吗？否，力矩与运动学速度。
10. 200Hz能写成实測？不能，需运行时间记录。
