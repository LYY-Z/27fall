# 硬件反馈与FreeRTOS任务

## 学习目标与入口

本章解决：多个控制环如何分任务运行，为什么周期、优先级和反馈都重要。

相关项目：P3。先修：[基础课程总览](../../../01_通用基础/00_基础课程总览.md)。建议先读本项目全貌，再按章节编号阅读。代码入口：[教学实验与完整命令](../../../03_代码实验/02_项目实验/P3/README.md)；代码未运行核对，输出预期不能当实测。

## 0. 先用白话定位本页

这页不是要证明“所有任务都按某个频率准时运行”，而是看传感器反馈和多个程序任务如何共享处理器。把CPU想成同时处理云台、底盘、IMU与通信工作的工作人员：优先级会影响先后，但一个任务仍可能被通信或长计算拖慢。先画出反馈从CAN进入哪个任务、任务算完把命令交给谁，再区分配置周期与实际测得周期。

读的时候依次做三件事：说出实际物体和目标，标明每个输入/输出的含义与单位，再沿代码确认这一步真实被谁调用。教学示例帮助你理解因果关系，只有源码、日志或实验记录支持的内容才能说成项目事实。

## 1. 把机器人看成并行闭环

云台需要角度/角速，摩擦轮需要转速，拨盘需要累计角与转速，底盘需要四轮转速和裁判功率。IMU、遥控、视觉、裁判、电机CAN以不同频率进入。RTOS使多个任务共享处理器，优先级决定谁可抢占，不等于某任务必然达到固定频率。

<a id="task-create"></a>
## 2. 从任务创建到共享 CPU：先读实际入口

Core/Src/freertos.c建立default、calibrate、chassis、gimbal、imu、detect、usb、decode、ui、led、cap。当前配置gimbal高、chassis低、IMU idle；这只是该副本配置，不是推荐通用优先级。

`osThreadDef` 定义入口、CMSIS 优先级和栈配置，`osThreadCreate` 真正创建任务；它们没有“让两个函数同时占用两个 CPU”的含义。该单核 MCU 在同一时刻运行一个任务；中断可以暂时打断任务。同优先级就绪任务如何轮流运行要看时间片配置；高优先级任务主动阻塞后，较低优先级任务才有机会运行。`osPriorityIdle` 是 CMSIS 优先级标签，不能把用户创建的 IMU 任务当成系统自动建立的 Idle 任务。

`freertos.c` 后半部分有 `__weak` 空壳，例如只 `osDelay(1)` 的 `INS_task`；活动同名实现要继续查 `Atti.c`，其中 IMU 循环用 `ulTaskNotifyTake(pdTRUE, portMAX_DELAY)` 等 DMA 通知，再做解码和 AHRS。因此任务创建表不能单独确定任务频率，更不能拿空壳循环作为控制路径。云台任务还调用发射控制，摩擦轮与拨盘不是另外两个已创建的独立任务。

多速率意味着不同输入到达间隔可以不同：电机 CAN、BMI088 数据就绪、视觉、裁判都按各自链路更新。云台即使重复读相同缓存，也不等于获得了一次新采样。要分别记“任务算了多少次”“传感器产生多少次新值”“命令发送多少次”。

<a id="encoder-units"></a>
## 3. CAN 编码器、转速与协议命令：从原始数到物理量

CAN解码获得编码器计数、speed_rpm、current等。累计编码器需处理过圈；RPM×2π/60变rad/s，电机输出减速比还要再换关节速度。控制器give_current是协议整数，不自动等于安培。记录映射尺度与设备型号。

共享结构可能在多字段读到不同时刻数据。用时间戳/快照/短锁可改善，但不能假定当前源已有这些机制。

`DJI_Motor_Decode` 按高字节在前解出 `ecd`、带符号的 `speed_rpm`、`given_current` 与温度；`give_current` 是控制命令，`given_current` 是反馈，两个名字不能混用。单圈计数 8192 表示转子一圈，累计计数还经过 `DJI_Round_Count`。设上帧 8100、本帧 100，直接差为 -8000；它小于 -4096，源码给圈数加 1，实际连续位移为 8192-8100+100=192 counts，而不是反转了 8000 counts。

教学换算：\(\Delta\theta_m=192/8192\times360\approx8.4375^\circ\)。若减速器为电机转19圈、输出轴转1圈，则输出角约0.444°；输出 RPM=电机 RPM/19。源码 `M3508_DECELE_RATIO=1/19` 使用的是这个倒数定义，不能看到“减速比”就统一再除19。跨圈推断要求相邻有效采样的真实转子位移小于半圈；丢帧、高速或首次历史值无效时可能错算圈数。多圈累计与 [-180°,180°] 单圈相对角是两种用途。

600 RPM 是**每分钟**600圈，等于每秒10圈，\(600\times2\pi/60\approx62.83\) rad/s。协议命令 +502 只是一个带符号整数；本项目功率模型采用 `20/16384` 的电流换算常量，但这不能自动证明所有电机型号、驱动模式和反馈字段都共用这个尺度。需要按实际电调型号、字段定义与标定分别确认。

## 4. `vTaskDelay`、`osDelay` 和 `vTaskDelayUntil`：到底等多久？

先把三个东西分开：

- **CPU 主频**：处理器每秒能执行多少时钟周期；
- **FreeRTOS tick**：操作系统用来计时和唤醒任务的节拍；
- **控制循环周期**：某段控制代码两次开始执行之间的真实时间。

它们不是同一个频率。本源码快照的 `FreeRTOSConfig.h` 把 `configTICK_RATE_HZ` 设成 1000，所以一个 tick 的名义长度是：

\[ T_{tick}=1/1000\text{ s}=1\text{ ms} \]

这只说明系统计时节拍约为 1 ms，并不表示每个任务都以 1000 Hz 执行。控制任务里还要看实际循环、计算耗时、等待、通信阻塞、被更高优先级任务抢占以及中断。

<a id="delay-relative"></a>
### 4.1 `vTaskDelay(n)`：跨 n 个 tick 边界后重新就绪

`vTaskDelay(1)` 可以读作：“我先暂停，直到系统 tick 计数前进一格后，再回到可运行队列。”它不是“从调用时刻起完整睡满 1.000 ms，并保证醒来立刻运行”。如果调用恰好发生在下一格 tick 前很短时间，墙上钟实际经过的等待可能很短；请求的是跨过一个 tick 计数边界，不是完整的一毫秒。

为什么实际等待会变？FreeRTOS 的时间刻度是一格一格跳的。假设 tick 每 1 ms 跳一次：

```text
情况 A：刚过一个 tick 时调用 delay(1)
        还要等到下一个 tick，等待接近 1 ms

情况 B：离下一个 tick 只剩一点点时调用 delay(1)
        等到下一个 tick 就可重新就绪，等待可能很短

重新就绪 ≠ 立刻执行：还可能等待更高优先级任务、临界区或中断结束
```

若一圈计算用了 0.4 ms，再调用 `vTaskDelay(1)`，把请求粗略看成“计算 0.4 ms + 名义等待 1 ms”，得到约 1.4 ms、约 714 Hz，只能作为便于理解的估算。真实值会受 tick 相位和调度影响，甚至某些周期中 delay 的实际阻塞小于 1 ms。要得到实际频率，必须测量，不能拿这个估算冒充实测。

<a id="delay-cmsis"></a>
### 4.2 `osDelay`：CMSIS v1 和 v2 的单位不同

本工程包含 `cmsis_os.h` 与 `osThreadDef/osThreadCreate`，使用 CMSIS-RTOS v1 风格接口。本地 `CMSIS_RTOS/cmsis_os.c` 的实现为：

```c
osStatus osDelay(uint32_t millisec) {
    TickType_t ticks = millisec / portTICK_PERIOD_MS;
    vTaskDelay(ticks ? ticks : 1);
    return osOK;
}
```

这里参数按毫秒换算，整数除法并保证至少1 tick；本地适配甚至会把 `osDelay(0)` 变成1 tick的延时。CMSIS-RTOS2 的 `osDelay(uint32_t ticks)` 则直接以**内核 tick**为单位，不能把项目 v1 的解释推广到所有同名函数。tick 为1000 Hz时两种写法的数字碰巧一样；若100 Hz，v2 的 `osDelay(10)` 请求100 ms，而本地 v1换算 `osDelay(10)` 请求1 tick。此处版本区别依据 [ARM v1 等待接口](https://arm-software.github.io/CMSIS_5/RTOS/html/group__CMSIS__RTOS__Wait.html) 与 [ARM v2 等待接口](https://arm-software.github.io/CMSIS_6/main/RTOS2/group__CMSIS__RTOS__Wait.html)，项目行为以本地封装为准。

读代码时不能只看到 `osDelay(1)` 就写“此任务精确 1 kHz”。还要看它是在循环开头还是结尾、这一轮做了多少工作，以及实际采样日志。`osDelay(100)` 的参数单位是毫秒接口所表达的毫秒数，通常约为 100 个 tick；项目适配版本和 tick 配置要一起确认。

<a id="delay-until"></a>
### 4.3 `vTaskDelayUntil`：绝对相位、工作耗时与超期补跑

普通 `vTaskDelay` 的等待从“这次调用 delay 的时刻”开始，所以循环工作越久，下一轮的计划时刻也越往后挪。`vTaskDelayUntil` 则保存一个**预定唤醒时刻**，每次在原计划上加固定 tick 数：

```c
TickType_t last = xTaskGetTickCount();
for (;;) {
    read_feedback();
    calculate_control();
    send_command();
    vTaskDelayUntil(&last, pdMS_TO_TICKS(2));
}
```

若周期参数是 2 tick，名义计划是 2 ms、500 Hz。与相对延时相比，它不会把本轮计算耗时反复累加到下一次计划时刻，所以更适合稳定周期任务。但它**不能保证**每次都准时开始或完成：高优先级任务、关中断时间、长计算、阻塞和超期仍会造成迟到。若一轮工作本身超过 2 ms，任何 API 都不能让任务同时满足“完整做完”和“每 2 ms 准时完成”；必须缩短计算、调整周期/优先级或重新设计任务。

这个快照启用了 `INCLUDE_vTaskDelayUntil`，但能不能说某个具体控制环使用它，要检查该环的真实调用点。本工程中可见不少循环使用 `vTaskDelay(...)` 或 `osDelay(...)`；启用了 API 只说明可用，不代表每个控制环都用了固定节拍 API。

用 2 ms 周期画时间线：计划启动为0、2、4、6 ms。第0轮工作到0.4 ms，绝对延时只等到2 ms，剩余约1.6 ms，不会在0.4 ms上再叠加完整2 ms。若第0轮直到5.2 ms才结束，则第一次调用把保存计划推进到2 ms；此时间已经过去，函数直接返回，循环会紧接着跑下一轮。下一次把计划推进到4 ms也可能直接返回，直到推进到未来计划时刻才阻塞。这叫程序连续补跑过期迭代；它不补回过去的传感器样本，也不保证补跑时控制对象仍适合原固定dt。官方明确说明过去的唤醒时刻会立即返回：[FreeRTOS vTaskDelayUntil](https://freertos.org/Documentation/02-Kernel/04-API-references/02-Task-control/02-vTaskDelayUntil)。

是否补跑、跳过遗漏周期、重置相位并报警，是系统策略。上述代码只是 API 教学，不表示 P3 已实现其中某种超期恢复策略。周期是连续计划启动间隔；截止期是一次工作必须完成的时间。二者可设相等，但没有天然相等的规则。

<a id="task-states"></a>
### 4.3.1 阻塞、Ready 和 Running 是三个时刻

```text
Running：正在执行控制计算
  → 调用延时/等待通知
Blocked：等待tick或外部事件，不占用任务执行机会
  → 等待条件满足
Ready：具备运行资格，等待调度器分配CPU
  → 高优先级就绪任务、中断、临界区允许后
Running：真正开始继续执行
```

例如在0.95 ms调用 `vTaskDelay(1)`，1.00 ms tick到来后可转Ready，只阻塞约0.05 ms；若其他高优先级任务直到1.30 ms才让出，实际继续执行在1.30 ms。0.05 ms是等待tick，0.30 ms是额外调度延迟；把两者混为“sleep精确1 ms”就解释不了日志。

<a id="timing-measure"></a>
### 4.4 从配置、调用路径到时间戳测量

要分成三层回答：

1. **系统 tick 的配置值**：当前源码配置 1000 Hz，名义 1 ms/tick。
2. **代码要求的等待**：展开完整调用链，而非只看任务末尾。本快照 `GIMBAL_PERIOD=1`、`CHASSIS_PERIOD=1`，但云台 `Send_Gimbal_Data`内两处延时、任务末尾一处；底盘 `Send_Chassis_Data`内同样两处、任务末尾一处。每次活动循环合计**三个1-tick相对等待请求**，并且板间发送之间已有阻塞。宏名“PERIOD=1”不等于控制每1 ms执行。三个请求各受tick相位与调度影响，源码也不单独证明真实间隔恰好3 ms。
3. **运行时测得的周期**：在同一循环位置记录连续时间戳 \(t_k\)，计算 \(T_k=t_k-t_{k-1}\)。平均频率可用 \(f\approx1/\bar T\)，同时要报告最小、最大周期、抖动和超期次数。

例如记录到相邻开始时刻相差 1.3、1.5、1.2、1.6 ms，则平均周期 1.4 ms，平均频率约 714 Hz；更重要的是周期在 1.2–1.6 ms 变化，说明有抖动。若只记录一段时间内的总循环次数，可算整体平均频率，却看不到单次周期抖动。

推荐把时间戳放在控制函数每圈的同一个入口，并记录执行结束时刻、输入数据年龄、输出时刻。高精度周期应用微秒计时器或 DWT，而不是只用 1 ms tick 估计。结论应写成“配置请求为 X，测量平均为 Y，范围为 A–B”，不可只写一个未经测量的频率。

这个调用链直接影响SMC：`Launcher_Control`每个云台任务循环调用一次，却在 `update_system`写死dt=0.001 s；完整循环有三个延时请求，所以不能认为这次误差差分天然来自1 ms采样。AHRS又按sampleFreq常数积分，两个“1000 Hz假设”必须分别核对，不能从RTOS tick推给全部算法。

设计划释放为 \(r_k\)，实际开始 \(t_k\)，完成 \(f_k\)，相对截止期 \(D\)：启动迟到=\(t_k-r_k\)，响应时间=\(f_k-r_k\)，超期条件=\(f_k>r_k+D\)。入口到出口的墙钟时间可能包含被抢占，纯 CPU 执行时间需另外用调度跟踪计算。只有“实际间隔很稳定”也不能证明满足截止期：每轮都稳定迟到1 ms同样可能违约。

### 4.5 延时、任务优先级和频率各自负责什么？

| 项目 | 它回答的问题 | 它不能单独保证什么 |
|---|---|---|
| 延时参数 | 任务想隔多久再运行 | 不能保证准点运行 |
| 优先级 | 多个就绪任务争 CPU 时谁先运行 | 不会自动缩短任务计算，也不等于频率 |
| 任务周期 | 控制器多久更新一次 | 不能证明输入新鲜或输出及时到电机 |
| 实测周期与最坏耗时 | 实际运行表现怎样 | 仍要结合闭环稳定性和通信延迟 |

闭环真正关心的是一整条时序：传感器何时采样、数据何时到、任务何时读取、何时算完、命令何时到驱动器、反馈何时回来。控制器用旧状态做正确计算，也可能得到针对“过去”的动作。

### 4.6 源码阅读时怎么得出一个可负责的周期结论

对每个任务沿这条顺序检查：

1. 找任务创建处：入口函数、优先级、栈大小；
2. 找循环体：控制函数调用和延时 API；
3. 展开周期宏：不要把宏名字当数字；
4. 数出阻塞调用、锁、队列等待和可能的长计算；
5. 查看 tick 频率、毫秒到 tick 的换算、是否使用绝对周期延时；
6. 如要陈述实机频率，找时间戳日志或示波器/逻辑分析仪记录。

因此，源码可以证明“采用了怎样的任务安排和等待写法”；测量才能证明“在指定负载和硬件上跑出了怎样的周期”。

<a id="discrete-pid"></a>
## 5. 离散 PID 没写 dt：为什么参数会随采样变化

连续 PID 积分为 \(K_i^c\int e\,dt\)，微分为 \(K_d^c\dot e\)。按周期 \(T_s\) 离散化可得：

\[I_k=I_{k-1}+K_i^cT_s e_k,\quad D_k=(K_d^c/T_s)(e_k-e_{k-1}).\]

本地 `PID.c` 用 `iout += i*err`、`dout=d*(err_now-err_last)`，所以数值配置已经隐含周期：\(i=K_i^cT_s\)、\(d=K_d^c/T_s\)。若采样由1 ms改2 ms而想保留同一连续近似，则 `i`应约加倍，`d`应约减半，前提是其余离散式和单位一致；运行抖动不能靠一次固定缩放完全补偿。VSP积分还采用前后误差相加，其系数另含求积规则。参数不能只凭 P/I/D 名称跨控制器照抄。
