# P6 一次设备动作怎样走过软件平台

P6重点不是某一个机器人动作，而是软件怎样把不同硬件包装成相似的接口：程序发现设备、记录设备能力、发送动作、等待处理结果，再把设备状态交回来。先把它想成“软件里的插座和转接头”，再学C++虚函数、线程池、协议适配这些词。

## 1. 先区分四种东西

| 名称 | 通俗解释 | 例子 |
|---|---|---|
| 设备 | 真正会动或会测量的硬件 | 电机、底盘、传感器 |
| 统一接口 | 软件约定的共同插口 | `move`、`getState`等抽象操作 |
| 适配器 | 把共同插口翻译成某款硬件协议 | 把“向前0.2”变成特定报文 |
| 执行结果 | 动作处理到哪一步的反馈 | 已收到、已接受、执行完成、失败 |

统一接口的好处是上层不用为每款电机都重写一套策略。但接口相同不表示硬件能力相同：有的设备不能横移，有的没有位置反馈，有的命令单位也不同。适配层必须说明能力和单位，不能只让函数签名看上去一样。

```mermaid
flowchart LR
 A[应用提出动作] --> B[检查设备和动作参数]
 B --> C[任务队列安排处理]
 C --> D[设备适配器翻译]
 D --> E[具体协议和硬件]
 E --> F[设备状态或错误]
 F --> G[更新状态并关联动作]
 G --> A
```

## 2. 为什么平台设计会有“发现”和“注册”设备？

在完整设备平台的概念设计里，程序启动时并不一定已经知道哪些设备连着、各自是什么型号。发现可以理解为“在现场找到一个设备”；注册则是“把它放进软件的设备名册，并告诉系统用哪个适配器和能力描述”。

例如只找到一个串口，并不证明串口后面一定是可用电机；注册成功也不证明电机在线或能完成动作。实际还要区分：发现、身份识别、初始化、在线状态、能力读取和定期反馈。这些是不同阶段。

**对照当前本地源码：** BaseDeviceHandler::Init 接收已经给定的 deviceId，再调用子类 OnInit。它不是 M-DDS 发现流程的证据；专用机器人平台的发现代码仍需在对应版本里定位。

## 3. 一次动作从哪里来、最后怎样返回？

假设上层提出“让设备A向前移动0.2米”。这句话还不能直接发给硬件。一个健壮的动作契约通常还会明确设备A是否存在、是否支持移动、数值单位、请求何时过期、动作编号是什么；这些属于平台设计要求，不能自动当作本地 BaseDeviceHandler 已全部实现。

发送成功只表示程序把数据交给了通信层；设备收到并接受是下一步；物理动作完成又是下一步。面试和读代码时分别寻找：函数返回、传输确认、设备ACK、状态变化和动作完成通知。不要把“无异常返回”直接说成“设备已经移动”。

## 3.1 按本地地锁源码走一次具体路径

本地 GroundLockHandler 给出可读的具体例子，命令不是机器人移动，而是升起地锁：

~~~text
上层调用 ExecCommand(deviceId, "up")
  → BaseDeviceHandler 检查 deviceId/cmd 并找到 handler
  → GroundLockHandler::Up 获取设备端口信息
  → WriteLockCommand 组装 Modbus 0x06 写寄存器请求
  → ModbusAdapter::RtuWrite 交给 RTU 服务
  → 写返回成功后，handler 更新 currentStatus 并上报属性
  → 后续轮询读回状态，才可以确认新的设备读数
~~~

这段流程中，Base 的函数返回、RTU 写返回和地锁物理到位是不同阶段。当前源码写成功后会先更新软件缓存，不能仅凭这个上报值说“传感器已经确认地锁到位”。另外，读失败分支可能把旧 currentStatus 放到输出参数，但返回错误码；调用方要检查返回码和最后有效读回时间。代码把 allData[7] 注释为寄存器地址 0x0006，也应继续核对协议服务如何组织返回数组。

## 4. 线程、任务队列和 `future` 是什么？

如果每个设备动作都让主程序原地等待，慢设备会卡住其他设备。线程池像几位工作人员：任务先进入队列，由空闲线程取走处理。提交任务后得到的 `future` 像一张取件单，之后可以等待结果或读取异常。

但`future.get()`会等待任务完成。如果调用线程正握着其他任务需要的锁，或者等待没有时限，程序可能停住。要检查：任务在哪个线程运行？等待是否有deadline？异常是否被接住？锁有没有跨越通信等待？执行失败时是否更新设备状态？

“异步”不等于“永远不卡”；线程池有队列容量、线程数量和任务时限。任务过多时也可能积压，让新命令排在已经过时的命令后面。

## 5. 设备报告状态与软件缓存有什么差别？

软件可以保存“上次听说设备在运行”，但这个缓存可能是旧的。可靠状态通常需要来源、时间、有效性和设备身份。若一个设备断线了，缓存里仍写着“在线”，控制器就会依据过时信息做决定。

阅读状态同步时问：这是谁报告的？何时报告？断线多久才判为失效？是否把命令回执误当成测量状态？动作ID能否和反馈ID对应？

## 6. 为什么动作需要超时、幂等和唯一编号？

网络可能在设备已经执行动作后丢掉返回包。如果软件简单重试“再向前移动0.2米”，设备可能前进0.4米。给动作编号后，设备或服务可以识别“这是之前那一条”，避免重复执行；这种重复请求不产生重复副作用的性质叫幂等。

超时表示系统等到某个期限仍没收到需要的结果。超时并不能证明设备什么都没做：动作可能已经执行，只是回执丢了。因此动作协议要设计查询状态、去重、取消或补偿策略。

## 7. 这份本地材料能证明什么？

当前本地源码能用于学习C++设备接口、适配层、任务处理和状态同步。M-Robots/M-DDS等申请材料中的平台专用源码当前没有完整定位到，所以不把平台名称当作已核实代码能力，也不虚构其接口、线程模型或执行结果。要讲个人贡献，还需对照提交记录、简历、PS和原始材料。

## 8. 一个简单的故障排查顺序

若上层发了动作，但设备没动，按顺序查：

1. 应用是否真的创建了动作请求？参数和单位正确吗？
2. 目标设备是否被发现、注册并标为有效？
3. 任务是否进入队列，是否一直等待？
4. 适配器是否选对了硬件类型和协议？
5. 命令是否成功写入通信接口？
6. 设备有没有返回ACK或状态变化？
7. 是否超时、重试、重复动作或保存了旧状态？

这比只盯着一个`send()`调用更有用，因为动作要穿过整条软件链。

## 读取失败在上层被掩盖的具体路径

当前ReadLockStatus失败可输出旧缓存，但ListeningTask在非OK分支没有立即返回（return被注释），继续缓存更新与ReportPropertyImpl。上报成功可能让最终返回变成OK，并触发基类online更新。因此检查应包括read_ret、report_ret、poll_ret和last_success_read_time，而不是只看上报成功或online。详见[协议章第7节](../01_原理与子系统/04_协议适配发现注册与状态同步.md)。
