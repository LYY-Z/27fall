## 0. 先看完整系统，而不是先看“AI”

P4 有三条在不同设备上运行、通过网络交换信息的线：

```text
Hi3861 本地控制：ADC → 湿度标定 → 手动/滞回状态 → GPIO 水泵
```

要严格区分五类信息：传感读数、模型观测、建议、命令请求、设备反馈。模型框不等于病害真值；Agent 建议不等于命令；命令请求不等于设备接收；设备接收也不等于水泵确实出水。

## 1. 本地浇水：ADC、滞回、人工优先和 GPIO

ADC 是传感器电路输出的数字采样，不天然就是“真实含水率”。源码用线性映射并截断到 0–100；这个量是依赖探头与标定条件的工程表示，不能没有校准就当通用体积含水率。

滞回用两个阈值保存状态：低于启动线打开，高于停止线关闭，中间保留上一状态。源码若用 `<56` 和 `>65`，那么等于 56 或 65 时仍保持；这避免噪声在单一阈值附近反复切换，但不等于有最短开泵时间、用水上限或传感器故障保护。

人工模式、语音触发与自动模式是状态转换；“关闭一次”未必永久手动关闭。GPIO 低有效意味着逻辑开泵时引脚可能输出 LOW。先追逻辑状态，再追物理电平，不能把 true 直接等同高电平。

### 1.1 ADC 数字怎样变成程序里的湿度量

本项目资料记录的示例标定为：

```text
moisture_raw = ADC × (-0.05) + 147.52
moisture = clamp(moisture_raw, 0, 100)
```

例如 ADC=2000，线性映射得到 `-100+147.52=47.52`，再转为整数时约为 47。ADC 是模数转换器读到的电压采样计数；映射后的 47 是这支探头、当前电路和标定方式下的软件量，不自动等于实验室测得的 47% 体积含水率。要把它称作真实含水率，需要用已知含水条件做标定并记录探头、土壤、温度和电源条件。

### 1.2 滞回状态完整走一遍

假设初始泵状态是 `off`：湿度 55 小于 56，变为 `on`；湿度升到 60、64，仍保持 `on`；到 65 仍保持；只有大于 65（例如 66）才变为 `off`。之后降回 60，仍保持 `off`。阈值相等时不触发，是因为比较符号是严格 `<` 和 `>`。滞回只减少门槛附近的频繁切换；断线读数、卡住的传感器、持续开泵和用水量限制仍须另做保护。

手动模式中自动浇水函数可能直接返回；语音开泵可临时进入手动，语音结束后又恢复自动，因此之后湿度低可能再次开泵。判断人工优先级，要按“命令→模式变量→状态更新→GPIO 电平”追全链，而不能只看一个 `off` 字符串。

细节：[土壤湿度滞回与人工优先](../01_原理与子系统/02_土壤湿度滞回与人工优先.md)。

## 2. V4L2：摄像头缓冲区的所有权循环

V4L2 是 Linux 摄像头接口。典型 streaming + MMAP 流程：查询能力、设置格式、申请并映射多块缓冲区、把空缓冲区排给驱动、启动采集；每轮程序 `DQBUF` 取出已填好的帧，处理后 `QBUF` 归还给驱动。

缓冲区归还之后，程序不应继续把那块内存当作不会变化的帧；驱动可能重新写入。若程序处理慢于相机采样，队列会积压或丢帧。`DQBUF` 是否阻塞取决于阻塞/非阻塞模式。

### 2.1 缓冲区生命周期与像素格式

```text
open
→ QUERYCAP 查询设备能力
→ S_FMT 协商分辨率/像素格式/帧率
→ REQBUFS 申请缓冲区
→ QUERYBUF + mmap 映射每块缓冲区
→ QBUF 把空缓冲区交给摄像头驱动
→ STREAMON
→ 循环：DQBUF 取已完成帧 → 读取/处理 → QBUF 归还
→ STREAMOFF → munmap → close
```

程序和驱动通过队列交接缓冲区所有权：驱动正在填充时，程序不能把它当成稳定图像读取；程序拿到帧后也不能无限期占用，处理结束要尽快归还。常见格式中，YUYV 是打包的 YUV 4:2:2，通常每两个像素共享色度；MJPEG 是压缩 JPEG 帧、长度可变；RGB24/BGR24 每像素三个 8 位通道。实际格式以 `S_FMT` 协商后的返回值为准，不能只看请求值。

细节：[V4L2、YOLO 与 RKNN INT8](../01_原理与子系统/03_V4L2YOLO与RKNNINT8.md)。

## 3. 图像预处理与 YOLO：从像素到候选框

相机格式可能是 YUYV/MJPEG；模型需要的颜色顺序、通道布局和数值范围由训练/导出配置决定。YUYV 转 RGB/BGR、resize 或 letterbox、归一化、HWC/CHW 排列必须一致。

Letterbox 保持长宽比并补边；模型框回到原图时，先减掉补边，再除以缩放比例。例：1280×720 按 0.5 缩放为 640×360，上下各补 140；模型坐标 y=200，去补边后为 60，再除以 0.5 得原图 y=120。

若缩放比例为 `s`，左/上补边为 `pad_x/pad_y`，框坐标每个角都要逆变换：`x_orig=(x_model-pad_x)/s`、`y_orig=(y_model-pad_y)/s`。忘记减补边会把框整体平移；把 RGB/BGR 顺序弄反、把 HWC 当 CHW、或误用训练时的 mean/std，也会让模型输入分布改变。比如 `mean=0,std=255` 对 0–255 像素执行的是除以 255；不能把这一配置推广到所有模型。

YOLO 输出是候选类别分数和边界框，不是已经确认的植物病害结论。输出张量的形状、坐标编码、是否包含 objectness，取决于 YOLO 版本、导出格式和模型配置，不能把某个教程的张量布局套到所有模型上。举例说，某些 640 输入、80 类的 YOLOv8 导出会出现 `[1,84,8400]`：可理解为 batch=1、每个候选包含 4 个框参数加 80 个类别分数、三个检测尺度合计 8400 个候选位置。这只是版本示例，必须以实际模型的输出张量和导出说明为准。

部分 YOLOv8 导出将候选组织为 `(batch, 4+类别数, 候选数)`；旧版本或不同导出可能采用不同轴顺序、锚框/objectness 字段和坐标解码方式。即使看到 `(1,84,8400)`，也要通过模型元数据和后处理代码确认“84 个通道”的具体含义，以及框是像素、网格还是解码后的坐标。若框以中心点和宽高 `(cx,cy,w,h)` 表示，转角点是 `x1=cx-w/2, y1=cy-h/2, x2=cx+w/2, y2=cy+h/2`；若是归一化坐标，再按输入宽高换成像素。坐标恢复到摄像头原图还要撤销 letterbox。

锚框是训练/检测头预设的宽高参考，某些检测头预测相对锚框的偏移；无锚框头则按自己的参数化直接预测框。它属于模型结构选择，不是后处理可以任意切换的开关。学习 P4 时优先掌握模型输入输出约定、坐标恢复、置信度筛选、NMS、量化影响和部署验证；如果没有训练代码及实验记录，不把项目表述成“从头设计或训练 YOLO”。

**IoU 是两个框重叠面积占并集面积的比例**：`IoU = 交集面积 / 并集面积`，范围 0 到 1。非极大值抑制（NMS）通常先按类别分数筛掉低分框，再从高分框开始保留；若同类另一个框与已保留框的 IoU 超过阈值，就把它视为重复候选而抑制。NMS 阈值越低，去重越强，也越可能删掉相邻的真实目标。具体实现还受类别是否分开处理、阈值和框坐标约定影响。

一个可手算的 NMS 例子：框 A=`[0,0,10,10]`、框 B=`[5,0,15,10]`，两框各自面积 100，交集面积 50，并集面积 `100+100-50=150`，因此 IoU=`50/150=1/3`。若 NMS 阈值为 0.3，低分的重叠框会被抑制；阈值为 0.5 时，两框都可能保留。若它们对应不同类别，class-aware NMS 通常不会互相抑制。

Confidence 是单个候选框的模型分数，不是全数据集准确率。评估指标可以从计数理解：`Precision=TP/(TP+FP)`，表示报出的目标中有多少正确；`Recall=TP/(TP+FN)`，表示真实目标中找回多少。改变置信度阈值会改变 Precision/Recall；AP 是 Precision-Recall 曲线下的面积，mAP 是按类别汇总 AP 的平均，具体 IoU 匹配规则（如 mAP@0.5 或多个 IoU 阈值的平均）必须写清。不能把单张图的 confidence 当准确率，也不能用 mAP 代替现场误报/漏报分析。FPS 通常只描述某段推理吞吐，不等于从曝光到服务收到事件的端到端响应时间。

空检测的含义只是“这一帧没有候选通过阈值和后处理”，不能推出叶片健康；遮挡、失焦、光照、视角、模型漏检、阈值过高都可能造成空结果。评估 FP32/INT8 时要用同一测试集、类别映射、图像尺寸和后处理阈值，并报告 mAP/Precision/Recall；性能要分别计采集等待、预处理、NPU 推理、后处理、网络和服务排队。

细节仍以 [视觉推理章节](../01_原理与子系统/03_V4L2YOLO与RKNNINT8.md) 和 [结构化视觉状态章节](../01_原理与子系统/04_结构化视觉状态与时间戳.md) 为准。

## 4. INT8 量化：为什么快一些、哪里会损失

量化用有限整数近似浮点值。常见形式是 `q = clip(round(x/s) + z)`，反量化约为 `x ≈ s(q-z)`；scale 决定一个整数格代表多少数值，zero point 决定浮点零落在哪个整数。超出可表示范围会饱和，误差可能远大于半个量化步长。真实推理输出若仍是量化整数，后处理必须读取运行时张量的 scale、zero-point、数据类型和布局后再解释；不能把整数直接当类别分数或像素坐标。

权重逐通道量化可为不同输出通道保留不同尺度；激活常按工具链和算子支持采用逐层或其他量化粒度。精确粒度、对称/非对称方式和运行时输出类型应查当前 RKNN Toolkit、芯片运行时版本及张量属性，不能从“INT8”三个字推断。校准数据用于估计激活范围，应覆盖真实光照、背景和植物状态。ONNX → RKNN 是部署转换，不是训练；转换成功不证明精度、FPS 或现场效果，需要在同一测试集、同一输入尺寸和一致计时口径下比较量化前后精度与延迟。

手算例：若 `s=0.1,z=0,x=0.26`，则 `q=round(2.6)=3`，反量化约为 `0.3`，误差 `0.04`。误差不总小于半个 scale：若 `x=20,s=0.1`，整数值 200 超过有符号 INT8 上限 127，截断后反量化为 12.7，误差达 7.3。对称量化通常令零点为 0；非对称量化使用非零零点适配不对称数值范围。逐通道权重量化为每个输出通道配置尺度，能减少通道间范围差异造成的精度损失。校准集不是训练标签集；它用于估计推理激活的范围，数据分布偏离现场会使范围不合适。

如果后处理在量化整数域比较分数阈值，必须先把浮点阈值按该输出张量的 scale/zero-point 转成对应整数门槛，并确认张量布局、数据类型和通道量化属性；只有确认这些前提，才可能避免整张量反量化。ONNX 转 RKNN 是计算图/权重部署转换，不是从标注图片训练模型。转换通过只证明转换工具接受了模型，不等于精度保持、推理加速或现场效果达标。

## 5. 结构化视觉事件：内容、置信度与时间

视觉事件应带类别、分数、bbox、相机/植物位置、设备来源和采集时间。事件到服务器的接收时间与相机采集时间是两个时刻；如果设备时间戳为 0 或设备时钟未同步，服务不能把接收时刻冒充采集时刻。新鲜度要按事件源时间与当前时间计算，不能只看分数。

空检测只表示这帧没有通过阈值/NMS 的候选结果，不证明场景中没有病害。事件去重用于抑制重复处理相同观测，但不能天然保证分布式命令“恰好一次”。

```text
建议事件字段：event_id、class、confidence、bbox、location_id、image_size、
source_device、capture_timestamp、server_received_timestamp
```

若事件源时间可信，事件年龄为 `now - capture_timestamp`；超过容许年龄就应拒绝用于当前动作，即使 confidence 很高。若设备时间为 0 或未同步，只能记录“服务何时收到”，不能假装得到精确采集时间。去重通常按 `event_id + scope` 在时间窗内防止重复分析；若处理前先记为已处理而后执行失败，重试可能被挡住，若服务重启后内存表丢失，也可能再次处理，所以这不是端到端 exactly-once。

## 6. 服务器、TCP、线程与 asyncio

TCP 是字节流，不保留发送方一次 `send` 对应一次接收的边界。接收侧必须按协议长度/分隔符累积字节、校验长度并解析完整消息。P4 中 RK3588 与 Hi3861 可能使用不同封装格式，不能假设两端 JSON 前缀完全一样。

线程常用于阻塞式设备 TCP 接收；asyncio 协程适合 WebSocket/异步 I/O。它们可以共存，但跨线程更新事件循环要用安全的线程调度接口。拿到 `future` 不等于调用端不阻塞，`future.get()`/等待结果仍会等；锁不应跨长 I/O 持有。

DataStore 的缓存状态需要来源和时间；WebSocket 广播表示服务把状态送给前端，不代表设备执行。重连后应恢复最新状态并避免盲目重放非幂等动作。

### 6.1 一个长度前缀消息如何被完整收齐

若协议采用“固定长度头 + payload”，接收端先循环读取完整头部，解出 payload 字节数，再循环收够指定字节数，最后才解 JSON。单次 `recv(n)` 可能少于 n 字节，也可能一次带回多条消息；必须保留未解析尾部并继续解析。要验证长度为非负、低于上限，断连时清理半包。RK3588 与 Hi3861 是不同客户端，逐个核对其长度头字节序、长度含义和 JPEG/JSON 组合顺序。

### 6.2 阻塞 TCP 线程怎样通知 asyncio WebSocket

```text
TCP 接收线程：recv → 粘包/半包重组 → JSON 解析 → 更新 DataStore 快照
                                   ↓ run_coroutine_threadsafe(coro, loop)
asyncio 事件循环：创建/调度协程 → WebSocket 广播给订阅客户端
```

`asyncio.create_task()` 应由事件循环线程调用；TCP 工作线程要通过 `asyncio.run_coroutine_threadsafe()` 或合适的线程安全回调把工作提交给指定 loop。协程参数绑定了这条消息，广播函数决定发给所有客户端还是特定 topic。跨线程共享的 DataStore 要做锁保护或用不可变快照；不要持锁等待网络发送。`asyncio` 适合许多主要在等待 I/O 的连接，不会让阻塞代码自动变成异步，也不是多个 CPU 核并行计算。Future 可以用于追踪任务结果，但调用 `.result()` 会等待，可能阻塞 TCP 线程。

可以用两个协程理解 `await`：A 开始后遇到“等 2 秒”的 `await`，它把控制权交还事件循环；事件循环于是运行 B。B 等 1 秒完成时，A 仍在等待；B 完成后，循环继续调度其他就绪任务，A 到 2 秒后恢复。它们是等待期间交错推进，不是两个 Python 代码同时占用两个 CPU 核。一个 TCP 线程收到的数据要成为具体广播内容，是因为它把解析后的对象作为参数传入 `broadcast(data)`；广播到哪些客户端，则由服务的客户端集合/topic 规则决定。

细节：[Web 通信、执行回执与恢复](../01_原理与子系统/06_Web通信执行回执与恢复.md)。

## 7. LangGraph、规则快速路径与执行权限

LangGraph 的 State 是节点之间传递的数据，Node 读取/更新状态，Edge 决定下一步。它是流程编排，不是另一个训练好的神经网络。

规则 fast path 可以快速处理明确事件；fallback/LLM 用于需要解释、上下文或建议的情况。LLM 可以提出候选行动，但执行层必须再检查设备、人工模式、命令白名单、时长和新鲜度。人工 off 不能被建议悄悄覆盖。`execution_summary` 是软件摘要，不是电机/继电器 ACK。

去重可挡住重复事件，但故障重试时仍需命令 ID、幂等语义、设备回执和状态对账，不能声称“只执行一次”。

可把六类节点职责读成：`sensing` 收集传感/检测并试走简单规则；`supervisor` 选择后续分支；`care` 形成护理建议；`alert` 形成告警；`execution` 校验并发出允许的命令；`skip` 记录无需继续处理。实际某节点是否调用 LLM、边怎样连接，要以图的构建代码为准。

**Fast path 和 skip 不是同一条路。**Fast path 是 sensing 中规则明确命中后走短路径（例如满足自动模式和低湿条件后提交开泵请求）；skip 是判断当前无需处理后结束，不给设备发动作。未命中 fast path 也不等于 skip，仍可能进入 supervisor，再走 care/alert。fallback 是主流程或依赖不可用时的替代处理，不应未经检查就等同“安全执行”。无论哪条路，执行层都要验证人工模式、设备能力、命令参数范围、事件新鲜度和幂等 ID。`execution_summary`、Web 广播或 HTTP 成功只能说明软件流程的某个阶段，不等于设备 ACK，更不等于水流真实发生。

细节：[LangGraph 规则、工具与决策](../01_原理与子系统/05_LangGraph规则工具与决策.md)。

## 8. 记忆与 RAG：上下文检索不等于模型学习

把“记忆”拆成三种更容易理解：**当前状态**（最新湿度、设备模式、最近事件，回答此刻是什么情况）、**历史记录**（以前的观测和动作，回答此前发生过什么）、**知识资料**（操作手册、植物知识等，回答一般规则是什么）。三者的更新速度、保留期限和可信度不同，不能都当成同一份聊天记忆。RAG 的基本链是：文档切分并建立索引 → 把用户问题转成检索条件/向量 → 取回相关片段 → 连同来源交给模型生成回答。检索只提供候选上下文，不证明内容正确、最新或适用于当前设备；回答需要保留来源和时间，并由规则/执行层再次检查。

数据库、嵌入模型和向量检索可能有降级分支；源码中有 MemoryStore 或 RAG 类，不足以证明某次运行实际连上数据库或使用向量检索。要检查启动状态、依赖、日志和实际检索结果。数据库断开时，系统可能只剩内存态或退化为关键词检索；这会影响重启后的历史连续性和召回质量。对会触发设备动作的建议，必须再检查数据新鲜度、人工模式、设备能力、命令白名单和反馈状态；RAG/LLM 不应直接绕过执行门。

“谁决定保存什么”和“保存到哪里”是两个独立问题：可以由程序规则挑选后写数据库，也可以让 Agent 提建议后经审核写库；它也可能只保留在进程内存。自动保存会有误存、漏存、存太多、过期未删和检索不到的风险，重要设备状态不应只靠语言模型判断是否记住。

RAG 的检索可以按关键词匹配、向量相似度或两者混合。关键词方法简单、可解释，但不擅长同义表达；向量检索需要 embedding 模型和向量索引，召回取决于切分、嵌入和 top-k 等设置；混合检索再对结果排序/融合。任何方式都要维护知识来源、更新时间和适用范围。若当前项目材料未说明具体数据库、embedding 模型、top-k 或启动配置，就把这些列为未确认项，不补写成已部署事实。

## 9. 把一次“看到问题到泵动作”的链路走完

下面是一条**教学用的端到端追踪例子**。它的用途是训练你分清每一层的数据，不代表项目曾经实际出现这组传感数、时间戳或成功浇水记录。

### 9.1 本地湿度控制：传感器数字到 GPIO

假设 ADC 读数是 2000。按当前学习资料中的线性映射：

```text
raw = 2000 × (-0.05) + 147.52 = 47.52
software_moisture ≈ 47
```

`47` 是映射后的软件湿度量。若自动模式开启、泵当前为 off、启动线是 `<56`，本地逻辑就把泵状态改为 on；如果数值升到 60，泵继续保持 on；只有严格大于 65 才按停止线关泵。随后逻辑状态要转换成 GPIO 低有效电平。此处每一步必须记录：ADC 原始值、映射值、当前模式、泵前态/后态、GPIO 电平。只记录“湿度47”看不出是真实校准值还是裸 ADC，也看不出泵是否真的得电。

### 9.2 视觉事件：图像到结构化观测

假设相机在采集时刻 (t_c) 得到一张 1280×720 图。摄像头驱动把帧放入已排队的 V4L2 缓冲区；程序取出一块缓冲区，完成颜色转换和 letterbox，送入 RKNN 模型。模型输出多个候选框，程序按模型版本规定的张量布局解码，按类别分数阈值筛选，再做 NMS。

为了看清坐标恢复，假设图像缩放到 640×360 后上下各补 140 像素。模型给某框的 y 坐标是 200，则原图 y 坐标是：

\[
y_{original}=(200-140)/0.5=120.
\]

之后程序形成一条类似下面的观测：

```json
{
  "event_id": "camera-01-frame-120",
  "class": "leaf_spot",
  "confidence": 0.82,
  "bbox": [410, 120, 620, 330],
  "capture_timestamp": "t_c"
}
```

`confidence=0.82` 是该候选的模型分数，不是“识别正确率82%”。该 JSON 是观测，不是浇水命令；空框也不等于植物健康。

### 9.3 网络、规则/Agent和设备回执：逐层区分状态

服务接收字节后，按协议长度把 TCP 半包/粘包组装为完整消息，解析出 JSON，检查事件 ID、来源、时间新鲜度和字段范围，再更新有时间信息的状态快照。流程节点可根据明确条件走规则短路径，也可把事件交给进一步分析；模型建议必须经过执行门，检查设备是否在线、用户是否处于手动关闭、命令是否白名单内、动作时长是否越界。

```text
摄像头/ADC观测
→ 事件或本地状态
→ 服务解析和新鲜度检查
→ 规则/Agent建议
→ 执行门生成命令请求
→ 设备接口发送
→ 设备软件回执
→ 传感器/流量反馈确认物理结果
```

这条链至少有五种不同结论：

|记录|能说明什么|不能单独说明什么|
|---|---|---|
|检测框和分数|某帧有候选目标|目标一定真实、疾病已确诊|
|Agent/规则建议|系统建议做什么|动作已获准或已发出|
|命令请求|软件准备/尝试发命令|设备已收到|
|设备ACK/执行摘要|设备软件确认到某阶段|水泵有流量、浇到目标植物|
|流量/电流/水位等物理反馈|存在某种可测执行证据|长期养护效果一定提升|

为了复习或设计日志，可以把状态按 `REQUESTED（生成请求）→ SENT（发送尝试）→ RECEIVED（设备收到）→ ACCEPTED（设备接受）→ COMPLETED（设备报告完成）→ PHYSICALLY_CONFIRMED（传感器确认物理效果）` 逐层记录。它们是帮助区分证据的概念标签，不表示当前仓库一定使用这些英文枚举字段；读代码时要映射到本项目真实消息与回执字段。某一步没有对应证据，就停在已证实的上一阶段。

因此，一次真正的“执行成功”证据要让事件 ID、命令 ID、设备回执和执行后物理反馈能按时间关联。若设备时钟没同步，就记录源时间未知/时钟偏差估计，不能把服务收到消息的时间伪装成相机拍摄时间。若命令发送后回执丢失，也不能盲目重试非幂等开泵命令；先查设备状态或使用带关联 ID 的安全幂等协议。

> 这段例子把本地浇水和服务器视觉/决策放在同一张“信息地图”里，**不表示源代码把植物视觉识别直接接到了湿度阈值控制器**。两条通路是否连接，必须用当前仓库的调用、消息和设备 ACK 证据证明。
