# 第十一课一个控制循环：从输入缓存到下一轮反馈

> 这章追踪指定仓库第十一课的调用顺序。它描述源码，不代表已经在硬件测量过的时序或性能。不同课程目录不是一个程序，先分清当前正在读第十一课。

## 1. 先把循环分成两部分

程序有一条独立 IMU 任务，和 Arduino 的主 loop。它们不是一个锁步序列：

- IMU 任务不断读 MPU6050，更新 pitch、roll、yaw 和 gyro 变量。
- 主 loop 读取当时这些共享变量，计算轮和腿的控制量。
- CAN 任务/调用收发腿关节状态和命令。
- 轮子命令交给静态电机库接口。

因此主循环拿到的是“最近一次写入的缓存”，不保证所有传感器数据严格来自同一时刻。当前源码也没有显示完整的时间戳快照机制。

## 2. 上电初始化做什么

setup() 初始化 I2C 与串口，启动 MPU6050，创建 IMUTask，再初始化 CAN、PPM 和电机接口，随后延时并调用使能。代码阅读可以确认这些函数调用顺序；是否硬件初始化可靠、每个 delay 是否够用，要用设备和运行记录确认。

IMUTask 由 ESP32 FreeRTOS API 创建并固定到指定核心。它的 while 循环没有明显周期 delay，因此不能把它说成已保证某个固定频率；应实测周期并评估忙循环占用。

## 3. 主 loop 逐行追踪

第十一课 main.cpp 的顺序是：

### 第一步：先算轮目标

调用 wheel_control(140+remoteHeight, ...)。它读取当前可见的 pitch、gyroY、motor1_vel、motor2_vel 和 position；并读取右、左腿点的 y 值计算各侧 K1 到 K4，再形成两个轮电机目标。

但这时的腿点由后面的 VMC 函数更新，所以本次 wheel_control 通常先使用前一轮保存的腿几何点。motor1_vel、motor2_vel 在本文件中声明和使用；其赋值完整来源要继续追电机库，当前源码快照不足以单独证明端到端轮速反馈更新。

### 第二步：CAN_Control 收腿状态并发腿命令

CAN_Control 先调用 recCANMessage() 接收 CAN 反馈，再把各关节 torque 字段写进 MIT 命令结构。该调用发生在本轮 VMC 之前，因此此处取到的关节力矩通常是上轮 calRightVMC/calLeftVMC 算出的值。函数按 SEND_INTERVAL 条件发送关节命令；配置值为 1 ms，但这是代码里的发送门槛，不等于实测周期恰好 1 ms。

### 第三步：更新遥控开关，再算两侧腿 VMC

remote_switch 处理开关后，calRightVMC、calLeftVMC 各自读取关节位置/速度、腿目标、腿位置和机身滚转修正，计算虚拟水平/竖直力，再用当前闭链几何系数计算关节 frontTorque/backTorque。

这两个新力矩写入腿节点，等后续 CAN_Control 周期再装入 MIT 发送结构。VMC 内还先调用 footRightVelocity/footLeftVelocity，再调用 forwardKinematicsRight/Left 更新位置和关节角；速度计算所用角度对象可能带有上轮状态，阅读时应核对调用与更新次序，不把它自动视为同时刻状态。

### 第四步：动作状态和轮子输出

snake_case 更新动作相关变量；sendMotorTargets 将轮目标传入 Motor.h 声明的接口。实际实现位于预编译 libSF_Motor.a，头文件没有说明物理单位、内部速度/力矩闭环和保护方式。因此准确表述是“传递轮目标值”，不要直接断言 rad/s 或 N·m。

### 第五步：处理遥控滤波，供后续循环使用

storeFilteredPPMData 对遥控通道做低通滤波，mapPPMToRobotControl 将滤波通道转换为腿高、转向、前后和偏置参数。它位于本轮轮/腿控制计算之后，所以这次新映射值通常从下轮控制开始使用。

## 4. IMU 侧每轮数据怎么来

IMUTask 调用 MPU6050.update()，读取姿态角和陀螺角速度。角度是姿态融合计算结果，不是芯片直接给出的“角度寄存器”。gyroZ 有死区处理，gyroY 用低通滤波。gyroX 的低通调用把 gyroY 传作 previousValue，是代码中需要核对的可疑点。

没有同步锁或一致性快照时，主循环可能在 IMUTask 更新变量的中间读取不同时间的数据。读取周期、任务调度、传感器内部滤波都会影响数据新鲜度。

## 5. 腿部状态从编码器到力矩

CAN 接收 → 解码关节 pos/vel → 处理零位和方向 → 五连杆正运动学求腿点 → 依据目标算腿端虚拟力 → 用几何雅可比转置型映射求两个关节力矩 → 填入 MIT torque 字段 → CAN 发送。

此链要分别检查：电机协议解码区间、关节单位、编码器零点、五连杆参数单位、雅可比定义、左右符号、力矩字段单位和电机限幅。

## 6. 轮平衡反馈链

轮速 → 乘轮半径得到滚动速度估计 → 积分成短程 position → 与 pitch、gyroY 一起乘高度相关的 K 系数 → 左右轮目标限幅到 ±3 → 传给轮电机库。

updatePosition 使用 micros() 的实际时间差积分 position，并将结果夹在 ±0.1 m。它只能提供有限范围的相对位移估计；轮滑和轮反馈标定会造成累计误差。轮电机目标的最终单位仍需静态库或硬件接口文档确认。

## 7. 哪些是源码事实，哪些需要实测

**可从文件确认：** 函数调用顺序、目标字段如何写入、显式滤波/限幅代码、发送条件常量。

**不能只读文件断言：** 主 loop 实际频率、IMU 实际采样率、CAN 抖动、轮电机目标的物理单位、关节实际输出力矩、站立稳定性、失联保护是否完整。

要补证据，应使用同一版本日志记录 IMU 时间戳、关节反馈时间戳、遥控更新时间、轮命令、关节命令、周期统计和限幅状态，并确认所有记录来自同一时钟。

## 8. 读完后应能画出的数据链

IMU 任务：MPU6050 → 姿态融合/角速滤波 → 共享状态

主 loop：共享状态 + CAN 关节反馈 + 遥控缓存
→ 轮反馈计算 → 轮目标
→ 腿部 FK/速度 → VMC 虚拟力 → 关节力矩
→ CAN 腿命令 + 静态库轮目标
→ 下一轮重新读取反馈

关键提醒：轮目标、关节力矩和第八课模型 tau 属于不同接口；本控制循环存在先读后更新造成的一周期数据延迟可能；“设置 1 ms”不是“测得 1 kHz”。
